P02-S022. FACT (published kiteconnect 5.1.0 source, `ticker.py` L522 to L537): with `debug=True`, `twisted_log.startLogging(sys.stdout)` is called. P02-S023. Whether a stopped reactor can be started again by a later `connect()` is Twisted's behaviour: UNKNOWN / NOT ESTABLISHED.

### 3.4 `close()`, `stop()`, `stop_retry()`, `is_connected()`

P02-S024. FACT (published kiteconnect 5.1.0 source, `ticker.py` L546 to L565): `close(code=None, reason=None)` calls `stop_retry()` and then `_close(code, reason)`. `stop_retry()` calls `self.factory.stopTrying()` if `self.factory` is truthy. `_close()` calls `self.ws.sendClose(code, reason)` if `self.ws` is set. `stop()` calls `reactor.stop()`. HISTORICAL (published kiteconnect 5.1.0 source, `ticker.py` L355, L557 to L558): "method `stop_retry` can be used to stop ongoing reconnect attempts"; after `stop()`, "Reconnection mechanism cannot happen".

P02-S025. INTERPRETATION (basis P02-S024): `close()` neither stops the reactor nor ends the library's thread. Because `close()` always calls `stopTrying()` on the factory before it sends the close frame, the library's `close()` is written as a final close, not as a trigger for a reconnect. What `stopTrying()` does to Twisted's retry state, and so whether the `retry()` call that follows the lost connection (P02-S035) schedules another attempt, is Twisted's behaviour: UNKNOWN / NOT ESTABLISHED. (The feed calls `close()` to force a reconnect: section 6.)

P02-S026. INTERPRETATION (Python semantics; published kiteconnect 5.1.0 source, `ticker.py` L403 to L474, L562 to L565): calling `close()` or `stop_retry()` on a `KiteTicker` whose `connect()` was never called raises `AttributeError`, because `self.factory` is not set before `_create_connection` and the class has no attribute of that name.

P02-S027. FACT (published kiteconnect 5.1.0 source, `ticker.py` L539 to L544): `is_connected()` returns `True` only when `self.ws` is set and `self.ws.state == self.ws.STATE_OPEN`; the meaning of autobahn's state values is UNKNOWN / NOT ESTABLISHED.

FACT (published kiteconnect 5.1.0 source, `ticker.py` L567 to L628): `subscribe(tokens)` sends `json.dumps({"a": "subscribe", "v": tokens})`, `unsubscribe(tokens)` sends `{"a": "unsubscribe", "v": tokens}`, and `set_mode(mode, tokens)` sends `{"a": "mode", "v": [mode, tokens]}`, each passed through `six.b(...)` to `self.ws.sendMessage(...)` with no `isBinary` argument. After the send, `subscribe` records each token in `self.subscribed_tokens` with the value `MODE_QUOTE` (`"quote"`), whatever its earlier recorded mode; `unsubscribe` deletes each token (absent tokens are ignored); `set_mode` records each token with the given mode, adding tokens that were never subscribed. If the send raises, each method calls `_close(reason="Error while ...: <error>")` and re-raises the exception. The library does not split token lists into batches, limit their size, or check the mode string or the token types. Whether the frame is sent as text or binary, and what `sendMessage` raises when the connection is not open, are autobahn's behaviour: UNKNOWN / NOT ESTABLISHED.

P02-S029. INTERPRETATION (Python semantics; published kiteconnect 5.1.0 source, `ticker.py` L454, L477, L574, L582 to L584, L650): before the first connection, and after each `connect()` until the protocol's `onConnect` has set it, `self.ws` is `None`, so `subscribe`, `unsubscribe` and `set_mode` raise `AttributeError`; the `except` branch calls `_close`, which does nothing while `ws` is `None`, and re-raises; no token is recorded, because the record is updated only after the send.

P02-S030. FACT (published kiteconnect 5.1.0 source, `ticker.py` L630 to L647, L681 to L690): the library itself resubscribes after a reconnect. `_on_open` calls `resubscribe()` when `_is_first_connect` is false, then sets `self._is_first_connect = False`, then calls the user's `on_open`. `resubscribe()` groups `subscribed_tokens` by recorded mode and, for each mode, calls `subscribe(tokens)` and then `set_mode(mode, tokens)`. So on every open after the first, each token in the library's record is subscribed again in its recorded mode, before the user's `on_open` runs; on the first open nothing is resubscribed.

### 3.7 Reconnect algorithm

P02-S035. FACT (published kiteconnect 5.1.0 source, `ticker.py` L52 to L53, L168 to L201, L490 to L491): the library's own part of reconnection is: (a) the factory's `maxDelay` and `maxRetries` are set from `reconnect_max_delay` and `reconnect_max_tries`; (b) after a failed connection attempt (`clientConnectionFailed`) or a lost connection (`clientConnectionLost`) it calls `on_reconnect(retries)` when `retries > 0`, then `self.retry(connector)` (Twisted's `ReconnectingClientFactory.retry`), then `send_noreconnect()`; (c) each call of the protocol's `onConnect` calls `factory.resetDelay()` after the user's `on_connect` (L49 to L53; the comment at L52, "Reset reconnect on successful reconnect", is HISTORICAL). The delay arithmetic (initial delay, growth, jitter, the cap at `maxDelay`), how `retries` is counted and reset, and what `retry()` does once `maxRetries` is passed are inside Twisted's `ReconnectingClientFactory`, which was not read: UNKNOWN / NOT ESTABLISHED. HISTORICAL (published kiteconnect 5.1.0 source, `ticker.py` L346 to L353, L419 to L420): the docstrings describe an exponential backoff that starts from a "minimum interval which is 2 seconds", grows up to `reconnect_max_delay` and stops after `reconnect_max_tries` attempts.

P02-S036. FACT (published kiteconnect 5.1.0 source, `ticker.py` L192 to L201): when `maxRetries` is not `None` and `retries > maxRetries`, `send_noreconnect` logs "Maximum retries (...) exhausted." at DEBUG and calls `self.stop()` only inside `if self.debug:` (both lines are indented under that check, L195 to L198); then, whatever `debug` is, it calls `on_noreconnect()` if set. With `debug=False` (the default) the library therefore neither stops the reactor nor ends its thread when attempts run out: it only calls `on_noreconnect`. Whether the factory (through its autobahn or Twisted bases) has a `stop` method at all, for the `debug=True` case, is UNKNOWN / NOT ESTABLISHED; `ticker.py` defines none on the factory.

P02-S037. INTERPRETATION (basis P02-S031, P02-S035, P02-S036): `send_noreconnect` runs after every `retry()` call and fires whenever `retries > maxRetries` holds at that moment, so the library does not itself ensure that `on_noreconnect` fires only once; how `retries` behaves after the limit is Twisted's: UNKNOWN / NOT ESTABLISHED. kiteconnect's own code does nothing after `on_noreconnect` to start a new connection; whether Twisted's `retry()` makes further attempts once `retries` exceeds `maxRetries` is UNKNOWN / NOT ESTABLISHED. Within kiteconnect, the only way to start a new connection cycle is a new `connect()` call by the caller (P02-S023).

### 3.8 Liveness: ping, pong, heartbeat and timeouts

P02-S038. ### 3.9 Text messages

P02-S042. FACT (published kiteconnect 5.1.0 source, `ticker.py` L700 to L717): a text payload is decoded from bytes as UTF-8 (Python 3) and parsed with `json.loads`; a `ValueError` from `json.loads` makes the method return silently. ### 3.10 The binary parser

P02-S044. FACT (published kiteconnect 5.1.0 source, `ticker.py` L844 to L863): framing: the first 2 bytes (big-endian unsigned short) give the number of packets; each packet is preceded by its own 2-byte big-endian length, and its bytes are sliced without any check against the bytes that remain. `_unpack_int` reads big-endian unsigned integers with `struct.unpack(">" + byte_format, bin[start:end])`, format `I` (4 bytes) by default or `H` (2 bytes). INTERPRETATION (Python `struct` and slicing semantics): a frame shorter than its declared lengths yields short slices; a slice shorter than 4 bytes makes the token read at L725 raise `struct.error`, and a missing length header makes L859 raise `struct.error`; neither is caught inside `_parse_binary` (P02-S032 applies). A truncated slice whose length happens to equal a handled length (P02-S046) is parsed under that length's layout. A frame that declares 0 packets, or whose packets all have unhandled lengths (P02-S046), gives an empty list, which is still passed to `on_ticks` when the payload is longer than 4 bytes.

P02-S045. FACT (published kiteconnect 5.1.0 source, `ticker.py` L724 to L737): for each packet, `instrument_token` is the first 4 bytes (unsigned) and `segment = instrument_token & 0xff` (the token's low byte). The price divisor is 10000000.0 when the segment is `cds` (3), 10000.0 when it is `bcd` (6), and 100.0 for every other value: NSE (1), NFO (2), BSE (4), BFO (5), MCX (7), MCXSX (8), indices (9) and any value not in `EXCHANGE_MAP`. `tradable` is `False` only when the segment is `indices` (9).

P02-S046. FACT (published kiteconnect 5.1.0 source, `ticker.py` L739 to L842): the packet's length alone decides how it is parsed and which `mode` value is written; the mode the caller subscribed is not consulted. The lengths handled are 8, 28, 32, 44 and 184; a packet of any other length is skipped silently (the `if`/`elif` chain has no `else`). The "(index)" marks below follow the code comment at L747 ("Indices quote and full mode", HISTORICAL); the parser does not check the segment, so any 28-byte or 32-byte packet is parsed this way.

| Packet length | `mode` written | Dictionary keys produced (exact) |
|---|---|---|
| 8 | `"ltp"` | `tradable`, `mode`, `instrument_token`, `last_price` |
| 28 (index) | `"quote"` | `tradable`, `mode`, `instrument_token`, `last_price`, `ohlc` (`high`, `low`, `open`, `close`), `change` |
| 32 (index) | `"full"` | the 28-byte keys plus `exchange_timestamp` |
| 44 | `"quote"` | `tradable`, `mode`, `instrument_token`, `last_price`, `last_traded_quantity`, `average_traded_price`, `volume_traded`, `total_buy_quantity`, `total_sell_quantity`, `ohlc` (`open`, `high`, `low`, `close`), `change` |
| 184 | `"full"` | the 44-byte keys plus `last_trade_time`, `oi`, `oi_day_high`, `oi_day_low`, `exchange_timestamp`, `depth` (`buy`: 5 entries, `sell`: 5 entries; each entry `quantity`, `price`, `orders`) |

P02-S047. FACT (published kiteconnect 5.1.0 source, `ticker.py` L740 to L838; byte offsets as read by the code): 28-byte and 32-byte index packets: last price bytes 4 to 8, high 8 to 12, low 12 to 16, open 16 to 20, close 20 to 24; bytes 24 to 28 are not read; the 32-byte packet adds the exchange timestamp at 28 to 32. 44-byte and 184-byte packets: last price 4 to 8, last traded quantity 8 to 12, average traded price 12 to 16, volume traded 16 to 20, total buy quantity 20 to 24, total sell quantity 24 to 28, open 28 to 32, high 32 to 36, low 36 to 40, close 40 to 44; the 184-byte packet adds last trade time 44 to 48, OI 48 to 52, OI day high 52 to 56, OI day low 56 to 60, exchange timestamp 60 to 64, and ten 12-byte depth entries from byte 64 (the first five go to `buy`, the next five to `sell`; per entry, quantity 4 bytes, price 4 bytes, orders 2 bytes read as `H`; the entry's last 2 bytes are not read).

P02-S048. FACT (published kiteconnect 5.1.0 source, `ticker.py` L745 to L838): the divisor is applied to `last_price`, `average_traded_price`, every `ohlc` value and every depth `price`, which therefore come out as Python floats; it is not applied to the quantities, `volume_traded`, `oi`, `oi_day_high`, `oi_day_low` or the depth `orders`, which stay raw integers. `change` is not read from the packet: it is computed as `(last_price - close) * 100 / close`, or `0` when `close` is 0 (L764 to L767, L801 to L804).

P02-S049. FACT (published kiteconnect 5.1.0 source, `ticker.py` L769 to L776, L806 to L822): time stamps are produced only for full-mode packets: `exchange_timestamp` (32-byte and 184-byte packets) and `last_trade_time` (184-byte packets only), each by the exact call `datetime.fromtimestamp(self._unpack_int(packet, a, b))` with no time zone argument; any exception gives `None`. No tick of any mode has a key named `timestamp`. INTERPRETATION (Python semantics of `datetime.fromtimestamp(t)` without `tz`): the result is a naive `datetime` showing the local wall-clock time, on the machine that runs the code, of that epoch second (whole seconds, from a 4-byte unsigned value); the same packet gives different wall-clock values on hosts with different local time zones, and the value carries no offset. The legacy machine's local time zone setting is not established by this part.

### 3.11 The LTP-mode packet (the provisional checkpoint point)

P02-S050. FACT (published kiteconnect 5.1.0 source, `ticker.py` L739 to L746): an 8-byte (LTP) packet yields exactly four keys: `tradable`, `mode` (`"ltp"`), `instrument_token` and `last_price` (divided by the segment divisor). This settles the provisional point on the library side: in the published 5.1.0 parser, an LTP tick carries no time stamp of any kind and no volume. P02-S051. INTERPRETATION (basis P02-S046, P02-S050): because the parser chooses the keys by packet length, a token subscribed in LTP mode yields the four-key dictionary only when the server sends an 8-byte packet for it; a 44-byte or 184-byte packet would be parsed as `quote` or `full` whatever the subscription. ### 4.3 `_request`: one attempt, response handling and errors

P02-S058. FACT (published kiteconnect 5.1.0 source, `connect.py` L870 to L927): every client method goes through `_get`/`_post`/`_put`/`_delete` to `_request`, which: builds the path from the route table (with `str.format(**url_args)` when there are URL arguments, no URL encoding by the library); joins it to `root` with `urljoin`; sets the headers `X-Kite-Version: 3` and `User-Agent: Kiteconnect-python/5.1.0`; adds `Authorization: token <api_key>:<access_token>` only when both `api_key` and `access_token` are truthy (L902 to L905), so a missing or empty token sends the request without that header and raises nothing on the client side; for GET and DELETE sends `params` as the query string (L911 to L912); and calls `self.reqsession.request(method, url, ..., verify=not self.disable_ssl, allow_redirects=True, timeout=self.timeout, proxies=self.proxies)` exactly once (L915 to L924).

P02-S059. FACT (published kiteconnect 5.1.0 source, `connect.py` L914 to L927; `grep -n -i -E "retry|retries|429|sleep|rate|throttl|backoff"` gives only `generate_session`): the client makes one attempt per call. It has no retry, no backoff, no sleep, no pacing, no rate-limit accounting and no special handling of HTTP 429 or any other status. Any exception from `requests` (for example a timeout or a connection, proxy or SSL error) is re-raised unchanged by `except Exception as e: raise e` (L926 to L927): such failures reach the caller as `requests` exceptions, not as kiteconnect exceptions (INTERPRETATION of which classes: requests' own; the comment at L925 points to requests' exception list, HISTORICAL). How requests applies a single timeout number (to connecting, to each read, or both) is requests' behaviour, not read here.

P02-S060. FACT (published kiteconnect 5.1.0 source, `connect.py` L932 to L956): the response is classified by its `Content-Type` header, not by its HTTP status. (a) If the type contains `json`: the body is parsed with `r.json()`, a `ValueError` becoming `DataException("Couldn't parse the JSON response ...")`; if the body has `status == "error"` or a truthy `error_type`, the client calls the session-expiry hook when one is set and the status is 403 with `error_type` `TokenException` (L943 to L944), then raises `getattr(ex, data.get("error_type"), ex.GeneralException)(data["message"], code=r.status_code)` (L947 to L948); otherwise it returns `data["data"]` (L950). (b) If the type contains `csv`: it returns the raw body bytes `r.content` (L951 to L952). (c) Otherwise it raises `DataException("Unknown Content-Type (...) with response: (...)")` (L953 to L956). The HTTP status code is used only in the debug log (L930), the hook condition (L943) and the exception's `code` (L948).

P02-S061. INTERPRETATION (Python semantics; basis P02-S060 and `exceptions.py` L12 to L80): (a) the exception class is chosen by the server's `error_type` string: a string that names a class in `kiteconnect.exceptions` gives that class, and a string that names no attribute of that module gives `GeneralException` (a string naming a non-class module attribute, such as `__name__`, would make the call itself raise `TypeError`; no such value is expected from the server); (b) an error body with `"status": "error"` but no `error_type` makes `getattr(ex, None, ...)` raise `TypeError` (an attribute name must be a string), not a kiteconnect exception; (c) an error body with no `message` raises `KeyError`; (d) a success body with no `data` raises `KeyError`; (e) a response with no `Content-Type` header raises `KeyError` at L933 (mapping semantics of `r.headers[...]`; requests not read); (f) the two `DataException`s of (a) and (c) of P02-S060 carry the default code 502, because no `code` is passed. A JSON success body is returned whatever the HTTP status (P02-S060).

P02-S062. FACT (published kiteconnect 5.1.0 source, `connect.py` L907 to L908, L929 to L930, L222 to L240): with `debug=True` the client logs each request with its headers (including the `Authorization` header) and each full response body at DEBUG level; no A05 caller passes `debug` (section 4.1). The session-expiry hook, when set, is called before the `TokenException` is raised; it does not replace the exception.

### 4.4 `historical_data`

P02-S063. FACT (published kiteconnect 5.1.0 source, `connect.py` L151, L624 to L653): `historical_data(instrument_token, from_date, to_date, interval, continuous=False, oi=False)` sends one GET to `/instruments/historical/{instrument_token}/{interval}` (route `market.historical`) with the query parameters `from`, `to`, `interval` (the interval appears both in the path and in the query), `continuous` (`1` or `0`) and `oi` (`1` or `0`). P02-S064. FACT (published kiteconnect 5.1.0 source, `connect.py` L639 to L641): a date is formatted with `strftime("%Y-%m-%d %H:%M:%S")` only when `type(value) == datetime.datetime`; any other value is passed unchanged to requests as the query value. INTERPRETATION (Python semantics): (a) the exact-type test is false for a `datetime.date` and for subclasses of `datetime`, which are then passed unchanged and rendered by requests (requests' rendering not read); (b) for an aware `datetime` the format has no `%z`, so the offset is dropped and the wall-clock digits held in the object are sent as they are, with no conversion to another zone; (c) the format has no fraction of a second, so microseconds are dropped. HISTORICAL (published kiteconnect 5.1.0 source, `connect.py` L633 to L634): the docstring describes the dates as "datetime object or string in format of yyyy-mm-dd HH:MM:SS".

P02-S065. FACT (published kiteconnect 5.1.0 source, `connect.py` L655 to L670): `_format_historical` builds one dictionary per element `d` of `data["candles"]`, in the order received: `date` = `dateutil.parser.parse(d[0])`, `open` = `d[1]`, `high` = `d[2]`, `low` = `d[3]`, `close` = `d[4]`, `volume` = `d[5]`, and `oi` = `d[6]` only when `d` has exactly 7 elements. P02-S066. INTERPRETATION (basis: python-dateutil's documented parser behaviour; dateutil's source was not read): `dateutil.parser.parse` returns an offset-aware `datetime` when the string carries an explicit UTC offset (for a `+0530` suffix, a fixed offset of +05:30) and a naive `datetime` when it carries none. Which form the server sent in the legacy period is UNKNOWN / NOT ESTABLISHED (current documentation: section 5). INTERPRETATION (Python semantics): a candle row with fewer than 6 elements raises `IndexError`, a body without `candles` raises `KeyError`, and a time string that dateutil cannot parse raises dateutil's parser error; any of these ends the whole call, so the caller gets either the full list or an exception, never a partial list.

### 4.5 `instruments`

P02-S067. FACT (published kiteconnect 5.1.0 source, `connect.py` L148 to L149, L567 to L579, L951 to L952): `instruments(exchange=None)` sends one GET to `/instruments/{exchange}` (route `market.instruments`) when an exchange is given, or to `/instruments` (route `market.instruments.all`) otherwise; a CSV response comes back from `_request` as the raw body bytes (`r.content`) and is passed to `_parse_instruments`. ## 7. Points the AUDIT may examine (neutral)

1. The feed's forced reconnect calls `close()`, while the library's `close()` calls `stopTrying()` before closing; the feed's comments expect the library to reconnect by itself (P02-S025, P02-S086).
2. The feed passes `reconnect_delay_sec` (5) as the library's `reconnect_max_delay`, which is the ceiling of a growing delay and the library's minimum; the `live_feed` reconnect keys in `config/system_config.yaml` are not passed at the construction site (P02-S085).
3. The `reconnect` parameter is never read; `send_noreconnect` calls a `stop()` only in debug mode, and on the factory, which defines none in `ticker.py`; and by the library's own code `on_noreconnect` is not limited to one call (P02-S018, P02-S036, P02-S037).
4. On a reconnect with tracked tokens, subscribe and mode messages are sent twice, once by the feed and once by the library (P02-S033, P02-S089).
5. A failed send inside the feed's `_on_connect` makes the library begin closing the connection while the feed logs that the feed is live (P02-S089).
6. Library calls that reach autobahn and Twisted are made from threads other than the reactor thread, with no hand-off (P02-S088); the identity the feed stores as `_ticker_thread_id` is the consumer thread's (P02-S087).
7. LTP ticks carry no time stamp and no volume, so the feed's normalised `timestamp` and `volume` are `None` for them, and the feed's `raw.get("timestamp")` fallback matches no key the 5.1.0 parser produces (P02-S050, P02-S090).
8. Full-mode tick times are naive, host-local values from `datetime.fromtimestamp` (P02-S049).
9. Historical requests drop the offset of aware dates; candle `date` values are aware or naive according to the server's string; the daily-candle script drops the offset when it writes them (P02-S064, P02-S066, P02-S091, P02-S092).
10. The client has no retry, pacing or 429 handling; pacing exists only where callers add it (the A04 limiter for C9, a fixed sleep for C13 and C14, none for C11, C12 and C15) (P02-S059, P02-S091, P02-S092, P02-S094).
11. The scripts' clients use the library's 7-second default timeout, unlike the Live client's configured timeout (P02-S054, P02-S094).
12. The instrument dump is not de-duplicated by the library and `exchange_token` stays text; the callers' dictionaries keep the last row per `tradingsymbol`; current documentation recommends exchange plus tradingsymbol as the key and warns that tokens may be reused after expiry (P02-S068, P02-S081, P02-S093).
13. `refresh_instruments.py` reports any `ImportError`, including a missing Twisted or autobahn, as "kiteconnect package not installed" (P02-S012, P02-S093).
14. Error-mapping edge cases: an error body without `error_type` raises `TypeError`; `UserException`, `MarginException` and `HoldingException` would surface as `GeneralException`; network failures arrive as requests exceptions, not `NetworkException` (P02-S059, P02-S061, P02-S083).
15. Whether the WebSocket TLS connection verified the server's certificate depends on Twisted's `ClientContextFactory` (P02-S021).
16. The library's only liveness check is pong-based and depends on pongs arriving; it has no no-data timeout (P02-S038 to P02-S040).
17. The library reads every packet field as unsigned, while the current page types them as signed `int32` and `int16` (P02-S099).
18. The feed's own `unsubscribe()` and `set_mode()` have no caller outside tests (P02-S100).
