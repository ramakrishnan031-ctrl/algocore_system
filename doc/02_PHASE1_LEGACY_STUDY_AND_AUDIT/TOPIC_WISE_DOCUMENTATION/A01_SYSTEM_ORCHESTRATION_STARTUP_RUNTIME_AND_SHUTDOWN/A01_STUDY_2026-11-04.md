## 2. Executive lifecycle summary

The legacy trading process is one Python program, `main.py`. The repository's service file starts it as `main.py --mode live` under systemd; whether that file was installed is not established. On start, `main()` reads the command line and applies two guards before any log file exists: a weekend and holiday guard, which exits 0 on a non-trading day, and a start window, which exits 0 outside 08:00 to 18:15 IST. It then sets up logging and takes a single-instance lock, a file lock plus a local TCP port; a second copy exits 1.

Everything else happens in `_main_locked`, one function of about 2,100 lines. It loads and validates the configuration (exit 5 on failure), opens the database (which may migrate its schema only while the market is closed), builds the event bus and the kill switch, and classifies the start as COLD, WARM, CRASH or HALT from the stored session row and kill state. A HALT stops the start with exit 4 unless `--resume` is given. It then writes today's session row, builds the broker client from the stored token, and runs an aggregate of sixteen startup checks; any blocking result stops the start with exit 3. In live mode it then checks the token file (exit 6, reached only for a token that the broker has just accepted in the clock check) and the broker name (exit 9).

Next it constructs every subsystem and wires them together through constructor arguments, callbacks and two event-bus subscriptions. Some workers start during this construction: the MIS square-off pollers, the webhook sweeper and the optional S&R and V3 workers. After a first, synchronous broker reconciliation (exit 1 if a kill switch is then active), it installs the signal handlers and starts the remaining workers; starting the reconciler runs a second synchronous reconciliation, which no kill check follows. It then starts the webhook server, the health server and three helper threads: a 14:45 pre-alert, a 09:15 margin re-sync and the end-of-day self-exit. It writes a STARTUP event, rewrites the session row and sends a "System Active" alert.

The main thread then waits on one event and does nothing else. The event is set by SIGINT or SIGTERM, or by the self-exit thread once the configured service window has ended and no open position needs the service. The main thread then runs `_shutdown`: it drains any hard-kill flatten for up to 15 seconds, stops the subsystems one by one, cancels pending entry orders, writes a SHUTDOWN event, checkpoints and closes the database, and the process exits 0. A failure during startup ends the process with exit 1 or 2 (or a handled code), without this sequence and without a SHUTDOWN event. No kill-switch activation stops the process.

The most important facts:

- FACT: the only entry is `sys.exit(main())` under `if __name__ == "__main__"` (L4285 to L4293); an uncaught `TradingSystemError` gives exit 1, any other `Exception` exit 2.

### 7.6 Stop requests, kill state, interrupts and worker failures (Q22)

- FACT: stop requests: SIGINT or SIGTERM after L3958 set the event (L1571 to L1573); before L3958 the defaults apply (section 8.2).
- FACT: kill state at startup: HALT gives exit 4 (L2283 to L2290); any kill state active after the startup reconcile gives exit 1 (L3894 to L3899), but no check follows the second reconcile inside `order_reconciler.start()` (L3961; C41). ## 8. Shutdown, cleanup and exit paths

### 8.1 Normal shutdown routes (Q23)

- FACT: the daily end: the self-exit thread sets the event (L1525); the wait returns (L4249); `_shutdown(...)` runs (L4252 to L4277); `_main_locked` returns 0 (L4278); `main()`'s `finally` releases the lock (L2189 to L2190); `sys.exit(0)` (L4287).
- FACT: an operator or supervisor stop: SIGINT (the unit's `KillSignal`) or SIGTERM after L3958 takes the same route from L1573.
- FACT: the diagnostic and guard exits (`--version`, `--status`, `--dry-run`, the holiday guard and the START window) end before the runtime with 0 (section 4.7).

### 8.2 Abnormal shutdown (Q24)

- FACT: a handled startup return (exit 3, 4, 5, 6, 9, or 1 at L3899) skips `_shutdown`; most such returns call `store.close()` first; the returns at L2552 (6) and L2572 (9) do not.
- FACT: an exception that leaves `_main_locked` passes main()'s `finally` (the lock is released) and reaches the guard (exit 1 or 2); `_shutdown` is not run and the store is not closed.
- INTERPRETATION: a SIGINT before L3958 raises `KeyboardInterrupt`, which the guard does not catch, so the interpreter exits with a traceback after the `finally`; a SIGTERM before L3958 ends the process at once.
- FACT: an exception in a worker thread at runtime ends that thread only. An exception inside `_shutdown` outside its guards (L1629 to L1630; L1678 to L1679, with `_invalidate_token`'s L152 to L156; L1805; L1831) ends it part-way, with exit 1 or 2.
- INTERPRETATION (systemd semantics): if `_shutdown` outlasts `TimeoutStopSec`, the SIGKILL that follows could end it part-way.

### 8.3 What is stopped, and in which order (Q25)

- FACT: `_shutdown` (L1599 to L1831) runs 29 steps: set the event; drain the flatten (15 s); emit the census; invalidate the token if flagged; stop the webhook intake; stop the signal processor; stop the optional workers; stop the entry gate, smart TGT, TGT retry and reconciler; cancel pending entry orders; stop the order monitor, probe and token monitor; disconnect the feed; stop the candle store; send "System Stopping"; write SHUTDOWN; checkpoint the WAL; close the store; log "Shutdown complete". Step by step: workers file, section 4.
- FACT: not passed to `_shutdown`, and so never stopped by it: `eod` and its `while True` poller, `mis_notifier`, `mis_autosq`, `fund_manager`, `order_placer`, `broker_adapter`, `event_bus`, `drift_handler`, `shadow_tracker`, `step_executor`, `rate_limiter`, the webhook-server, eod-scheduler and healthcheck-server threads and the gate-release pool.
- FACT: the docstring says "Reverse-order shutdown (MAIN15)" (L1627). The core chain is roughly reversed (intake first, the store last), but the signal processor stops (L1690) before the entry gate (L1748), the reverse of the startup reason (L3972 to L3973); the reconciler stops (L1762) before the entry orders are cancelled (L1768); and the exit managers stop (L1753, L1758) before the order monitor and the feed (L1774, L1788). Comparison table: workers file, section 4.1.

### 8.4 Joins, timeouts and cleanup failures (Q26)

- FACT: `main.py` joins no thread; the joins are inside the owners' `stop()` methods. Their fixed maximum waits add up to 71 s for the steps that always run in live, before the signal processor's executor shutdown with no time bound (`signals/signal_processor.py` L339), the broker calls of the cancel step, the "System Stopping" send and the optional workers' joins (workers file, section 4). These are maxima: a join returns as soon as its thread ends, `drain_flatten` returns at once when no flatten is running (`capital/kill_switch.py` L1282 to L1285), and only the entry gate's 3 s sleep is fixed (`screening/entry_gate.py` L255). The unit file sets `TimeoutStopSec=30` (L25). The real durations are UNKNOWN / NOT ESTABLISHED.
- FACT: each step except 1, 4, 26 (`now_ist_iso()`, L1805) and 29 is inside its own try that logs and continues. In step 4 (L1678 to L1679) only the token rename is guarded (L158 to L165); the existence test and its warning (L152 to L156) are not.
- FACT: the event is set first (L1629), so from then on the rate limiter aborts any wait with `RateLimitAbortedError` (`broker/rate_limiter.py` L236 to L244).
- FACT: there is no re-entrancy guard; in non-test code `_shutdown` is called once (L4252).
- INTERPRETATION (CPython): after `_shutdown` returns, interpreter exit joins any surviving non-daemon thread (the flatten worker) and the executor workers, after running their queued tasks, and abandons daemon threads; the queued file-log records may be lost, because `main.py` never stops the log queue listener (`core/logger.py` L431 to L445, L461 to L472).

### 8.5 Exit codes and the supervisor boundary (Q27, Q35)

- FACT: the exit codes and their sites are in section 4.7.
- FACT: no A01 failure is recovered in-process by a retry or a restart of the process; a failed start, or a stopped process, is recovered only by a new process.
- FACT (file only, A17): the unit file declares `Restart=on-failure`, `RestartSec=10` and `RestartPreventExitStatus=3 4 5`. INTERPRETATION (systemd semantics): the declaration restarts exits 1, 2, 6 and 9 after 10 s, and not 0, 3, 4 or 5; a stop by a stray signal mid-day exits 0, which it does not restart. HISTORICAL (comments): the token watcher (A04) starts the service in-window after the morning token refresh (L2173, L1049 to L1051). Whether the unit or the token watcher was installed or ran is UNKNOWN / NOT ESTABLISHED.

### 8.6 What partial startup can leave behind (Q28)

- FACT: state written before a failure can include the migrated schema (L2233), the kill-switch auto-clears (L2260, L2265), a `CRASH_DETECTED` event (L2277), today's session row (L2308), a `CONFIG_DIFF` event (L2657), a configuration snapshot (L2603), the holiday sentinel, critical sentinels and alerts, and the effects of broker calls (L2451, L2758) and of the two startup reconciles (L3880; L3961, inside `order_reconciler.start()`, `orders/order_reconciler.py` L428 to L442).
- FACT: threads started before the failure keep running until the process exits: from L3355 the MIS workers, from L3407 the webhook sweeper, from L3504 the optional workers, from L3922 the Phase 0g subsystems, and from L4000 the webhook server. The guard returns call only `store.close()`: after a Q4(c) or A5 return (L3443, L3465) the MIS threads and the sweeper can run against a closed store; after the L3899 return the optional workers can too.
- FACT: no failed start writes a SHUTDOWN event. INTERPRETATION: the next start on the same day is classified CRASH, unless an earlier run that day wrote a SHUTDOWN event or today's EOD log is COMPLETE (WARM), a kill state forces HALT, or the session row does not yet carry today's date (COLD), for example when the first start of the day failed before L2308 (`utils/startup_checks.py` L217 to L382).
- UNKNOWN / NOT ESTABLISHED: what any such leftover did at runtime.

## 9. Time authority and market windows

### 9.1 `core/time_authority.py` (Q29)

- FACT: `now_ist()` returns `datetime.now(tz=_IST)`, where `_IST` is a fixed +05:30 timezone named "IST" (L58 to L59, L94 to L99). INTERPRETATION: India has no daylight saving, so a fixed offset represents IST.
- FACT: the default thresholds are warn 2.0 s, alert 5.0 s, halt 30.0 s, startup 30.0 s, at least 3 samples for halt and a window of 10 (L66 to L73). `main.py` calls `configure` once (L370 to L378, from L2254) with the four `system.clock` values (file values 2.0, 5.0, 30.0 and 30.0; `config/system_config.yaml` L184 to L187) and only the critical callback. `configure` merges the thresholds without validation and replaces only the callbacks passed (L125 to L164).

- FACT: `assert_clock_at_startup` (L263 to L301) raises `ClockSkewTooLarge` when the absolute skew exceeds `startup_max_sec` (L283 to L295) and otherwise records the sample (L297 to L299); its only caller is `utils/startup_checks.py` L437.
