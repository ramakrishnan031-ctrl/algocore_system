## 3. `WatchEntry`, the module constant and the constructor

- P06-S018 FACT: the module constant `_MAX_QUOTE_FAILURES = 3` (L46) is the only module-level setting; it is not read from configuration.
- P06-S019 FACT (`WatchEntry`, L53 to L76): a `@dataclass(frozen=True)` with fifteen fields in this order: `signal_id: str`, `symbol: str`, `direction: str` (comment `"LONG" | "SHORT"`), `trigger_price: float` ("scanner-fired price"), `entry_price: float` ("derived entry from _derive_prices"), `sl_price: float`, `tgt_price: float`, `tolerance_pct: float` (comment `strategy.pullback_wait_tolerance_pct`), `timeout_sec: int` (comment `strategy.pullback_wait_timeout_sec`), `strategy_name: str`, `tier: str` ("from screener result"), `scanner_name: str`, `intent: str`, `added_at: datetime` ("naive IST -- set when signal enters gate") and `extras: dict` (default an empty dict, `field(default_factory=dict)`).
- P06-S020 HISTORICAL (docstring L55 to L61): "added_at must be naive IST (consistent with signal_processor convention). extras carries any signal_processor context needed by the on_release callback to resume the post-gate pipeline."
- P06-S021 FACT: the dataclass declares types only; it validates nothing (no `__post_init__`). `frozen=True` prevents attribute assignment, but the `extras` dict itself is mutable; `_release` builds a new entry with `replace(...)` instead of mutating it (L526 to L528, section 7).
- P06-S022 INTERPRETATION (from the field comments L66, L69, L70, L72): the intended producer of a `WatchEntry` is the processor after screening (for `tier`) and after price derivation (for `entry_price`, `sl_price`, `tgt_price`), with the tolerance and timeout taken from the strategy's `pullback_wait_tolerance_pct` and `pullback_wait_timeout_sec`. No non-test code builds a `WatchEntry` outside the rehydration (section 5), so this intent is not implemented at the baseline.
- P06-S023 FACT (constructor, L108 to L138): parameters `quote_fn: Callable`, `logger`, `state_store`, `on_release: Callable` (comment `(WatchEntry, str) -> None`), `poll_interval_sec: float = 5.0`, `worker_count: int = 2`. It raises `ValueError("poll_interval_sec must be > 0")` when `poll_interval_sec <= 0` (L117 to L118); it stores `max(1, worker_count)` (L127), so a value below 1 becomes 1; it resolves the telemetry handle `_effect_handle("entry_gate")` (L124); it creates the empty `_watchlist` dict, one `threading.Lock` (L131), the per-entry consecutive-failure dict `_quote_failures` (L132), `_running = False`, a `threading.Event` `_stop_event`, and `None` for the poll thread and the executor (L135 to L138).
- P06-S024 FACT (the only non-test construction, `main.py` L3839 to L3844, A01's file, interface only): `EntryGate(quote_fn=broker_adapter.get_quote, logger=get_logger("entry_gate"), state_store=store, on_release=_make_gate_release_cb(signal_processor))`. It passes neither `poll_interval_sec` nor `worker_count`, so the constructor defaults 5.0 s and 2 workers apply. No configuration key feeds the poll interval or the worker count: the `EntryGateConfig` model (`core/config_loader.py` L1787 onwards, A02's file) declares slippage, liquidity, R:R and circuit-proximity keys (`slippage_buffer`, `max_entry_slippage_pct`, `max_spread_pct`, `min_depth_qty`, `liquidity_check_enabled`, `min_effective_rr`, `min_pending_rr`, `circuit_proximity_reject_enabled`, `slippage_control`) and no poll or worker key, and `main.py` reads that section only for the placer and the screener (L3011, L3074 to L3076, L3083, L3222, L3246, L3288). The keys themselves are part P08's.
- P06-S025 INTERPRETATION: because the `main.py` call relies on the constructor defaults, which no configuration reaches, the poll interval of 5.0 s and the worker count of 2 are fixed by the code at the baseline; the constructor's `ValueError` cannot be raised by that call. The `entry_gate.*` configuration keys do not govern the gate's own behaviour; their consumers are the order placer (A10) and the screener (part P03).
- P06-S026 FACT (telemetry handle, interface with A15): `core/effect_telemetry.handle` creates or returns a counter under a lock and marks the unit constructed (`core/effect_telemetry.py` L102 to L114); `EffectCounter.inc` is a single integer increment documented "Cannot raise" (L84 to L87). The gate increments its handle only in `add()` (L301); no other gate method increments it (search of `_fx_admit`: L124, L301).

## 4. `start()` and the rehydration from `gate_state`

- P06-S027 FACT (`start`, L144 to L177): if `_running` is already true it logs a WARNING "EntryGate.start() called while already running" and returns (L151 to L153). Otherwise, in this order: `rehydrated = self.rehydrate_from_gate_state()` (L156) with an INFO log only when the count is above 0 (L157 to L160); `_stop_event.clear()` (L162); a `ThreadPoolExecutor(max_workers=self._worker_count, thread_name_prefix="eg-worker")` (L163 to L166); a `threading.Thread(target=self._poll_loop, name="eg-poll", daemon=True)` (L167 to L171); `_running = True` (L172); `self._poll_thread.start()` (L173); an INFO log with the interval and worker count (L174 to L177).
- P06-S028 HISTORICAL (docstring L145 to L150): "Audit 4.4: rehydrates the watchlist from gate_state BEFORE the poll loop spins up. A mid-session restart therefore resumes watching the same signals at the same prices/timeouts they had before the crash."
- P06-S029 FACT (`rehydrate_from_gate_state`, L179 to L239): it calls `self._state_store.get_all_gate_state()` inside a `try`; any exception is logged at ERROR ("EntryGate.rehydrate: get_all_gate_state failed") and the method returns 0 (L189 to L193). For each row it reads `signal_id` with `row.get` (L197), then, inside a second `try`, parses `added_at` with `datetime.fromisoformat` and, when the result carries a time zone, converts it to IST and drops the zone (L199 to L204); parses `extras_json` with `json.loads` when it is truthy, otherwise uses `{}` (L206 to L207); and builds a `WatchEntry` from the row's columns with `float()` for the four prices and `tolerance_pct`, `int()` for `timeout_sec`, and the text columns unchanged (L209 to L225). Any exception in that block logs a WARNING "EntryGate.rehydrate: skipping malformed row signal_id=..." and continues with the next row (L226 to L231). Under the lock it skips a row whose `signal_id` is already in the watchlist ("idempotent") and otherwise inserts it (L233 to L236); it returns the count inserted (L237 to L239).
- P06-S030 FACT (what the rehydration does not do; L179 to L239): it reads no `signals` row and no signal status; it applies no test of age, of `timeout_sec` against the elapsed time, of the trading date, of the direction value, of positive or finite prices, of the tolerance range, or of whether the strategy is still loaded or enabled; it writes no status; and it does not delete a row that it skips as malformed. A row whose time-out has already passed is inserted into the watchlist like any other (its release follows in the first poll cycle, section 6).
- P06-S031 FACT (the store read, A03's method, interface only): `get_all_gate_state` runs `SELECT * FROM gate_state ORDER BY added_at ASC` inside `with self.transaction()` and returns the rows as dicts (`core/state_store.py` L3009 to L3014); A03 AUDIT Q-13 (L2067 to L2075) records that this read takes the write lock (`BEGIN IMMEDIATE`). The columns match the `WatchEntry` fields one for one, with `extras_json` for `extras` (`core/schema.sql` L780 to L798): every column is `NOT NULL` except `extras_json`; `direction` carries the comment "LONG | SHORT" and no CHECK; `added_at` carries the comment "naive IST ISO-8601"; `signal_id` is the primary key and references `signals(signal_id)`.
- P06-S032 INTERPRETATION (current external context: `https://docs.python.org/3/library/functions.html`, `float()`, read 2026-11-21: "The argument may also be a string representing a NaN (not-a-number), or positive or negative infinity"; `int()`: "For floating-point numbers, this truncates towards zero"): the rehydration's `float()` passes a NaN or infinite stored value into the entry without a test, and `int()` truncates a fractional stored `timeout_sec`; `json.loads` of a stored text that is valid JSON but not an object (for example a list or a string) gives a non-dict `extras`, which the dataclass accepts (P06-S021). Neither case can arise from the gate's own writer, which stores `json.dumps` of a non-empty dict or NULL (L347), but the rehydration does not check the stored values against that writer.
- P06-S033 FACT (failure behaviour of `start` as a whole): the store read and the per-row parsing are caught inside the rehydration (P06-S029); the remaining operations are the creation of an executor and of a thread and their start (L163 to L173) and log calls. `start` makes no broker call: the first quote read happens later on an `eg-worker` thread (section 6). INTERPRETATION: `start` raises only if the executor or thread creation or the thread start fails (for example when the interpreter cannot start a new thread); a broker or rate-limiter exception, `RateLimitAbortedError` included, cannot escape from `start`.
- P06-S034 FACT (where `start` runs; interface with A01): `main.py` L3975 calls `entry_gate.start()` once, after `signal_processor.start()` (L3974); the comment L3972 to L3973: "signal_processor BEFORE entry_gate (BLOCKER #5 fix): gate may call continue_from_gate() immediately on release; workers must be ready". The call is not wrapped in a `try` (A01 AUDIT C15, L870 to L881, range L3922 to L3977).
- P06-S035 INTERPRETATION: because the poll thread starts its first cycle immediately (no initial wait, section 6), any rehydrated entry is checked within the first cycle after L3975, on the `eg-poll` and `eg-worker` threads, while the main thread continues the boot (`smart_tgt.start()` L3976, the webhook server later, A01 AUDIT C15 "After L4000 the webhook server is listening"). The code fixes no order between a boot-time release and those later boot steps.

## 5. `add()`, `_persist_gate_state()`, `remove()` and who can create a gate entry

- P06-S036 FACT (`add`, L288 to L323): it first increments the telemetry handle (L301), then under the lock raises `ValueError("signal_id ... already in watchlist")` if the `signal_id` is present, otherwise inserts the entry (L302 to L307). Outside the lock, inside one `try`, it calls `self._persist_gate_state(entry)` and then `self._state_store.update_signal_status(entry.signal_id, "GATE_WAITING")` (L310 to L312); any exception from either is logged at ERROR "gate_state persist failed ... (in-memory add still applies)" and not raised (L313 to L317). It then logs INFO with the entry's direction, entry price, tolerance (`:.4f`) and time-out (L319 to L323). It works whether or not the gate is started (docstring L292).
- P06-S037 HISTORICAL (docstring L294 to L297): "also persists to gate_state and updates signals.status to GATE_WAITING so a mid-session restart can rehydrate the watchlist. Persistence errors are logged but do not abort the add (the in-memory watchlist remains the source of truth for the running session)."
- P06-S038 FACT (order and commit boundaries; A03 P-11 case (5)): the in-memory insert precedes both writes; the row insert and the status update are two separate store calls, so two separate transactions (`insert_gate_state` opens its own `with self.transaction()`, `core/state_store.py` L2961; `update_signal_status` its own, L1422). A failure of the row insert skips the status update (same `try`); a failure of the status update leaves the row written. The status write passes no `reason` and no `ts`, so `rejection_reason` is written as NULL (`core/state_store.py` L1424 to L1425).
- P06-S039 FACT: the telemetry increment at L301 runs before the duplicate test, so a rejected duplicate `add` is still counted.
- P06-S040 FACT (`_persist_gate_state`, L325 to L348): it writes the fifteen fields to `insert_gate_state` as a dict, with `added_at` as `entry.added_at.isoformat()` or, when `added_at` is `None`, `now_ist().isoformat()` (L328 to L331), and `extras_json` as `json.dumps(entry.extras)` when `extras` is truthy, else `None` (L347). The store method is `INSERT OR REPLACE` (`core/state_store.py` L2948 to L2973). INTERPRETATION: `now_ist()` returns a zone-aware time (`core/time_authority.py` L94 to L99), so the fallback would store an offset string, against the column comment "naive IST" (A03 AUDIT H-11 records the forms; the rehydration accepts both, P06-S029).
- P06-S041 FACT (`remove`, L350 to L361): under the lock it returns False if the `signal_id` is absent, otherwise deletes it from the watchlist and from `_quote_failures`; outside the lock it logs INFO "removed externally" and returns True. It calls no store method: the `gate_state` row and the signal's status are left as they are.
- P06-S042 FACT (`watchlist`, L363 to L366; `size`, L368 to L371; `is_running`, L281 to L282): a copy of the values under the lock; the count under the lock; the `_running` flag.
- P06-S043 FACT (callers at the baseline, search of the whole repository with the four exclusions): the non-test calls of the gate's public methods are `entry_gate.start()` (`main.py` L3975), `entry_gate.stop()` (`main.py` L1748) and `self._entry_gate.clear_all()` (`orders/eod_squareoff.py` L343, section 8). ## 6. The poll loop and `_check_one` (time-out, quote read, quote-failure count, price trigger)

- P06-S048 FACT (`_poll_loop`, L377 to L405): while `_stop_event` is not set: take `t0 = time.monotonic()`; copy the watchlist values under the lock (L385 to L386); if the copy is not empty, submit `self._check_one(entry)` to the executor for each entry, only while `self._executor is not None` (L390 to L392); then wait for each future in turn with `fut.result(timeout=self._poll_interval_sec + 2.0)` inside `try` / `except Exception: pass` (L393 to L397); log DEBUG the count and the elapsed milliseconds (L399 to L402); then wait on `_stop_event` for the rest of the interval, `max(0.0, interval - elapsed)` (L404 to L405). The first cycle starts at once when the thread starts.
- P06-S049 INTERPRETATION (current external context, concurrent.futures page of P06-S005: `result(timeout)` "If the call hasn't completed in timeout seconds, then a TimeoutError will be raised"; a running call "cannot be cancelled"; "If the call raised an exception, this method will raise the same exception"): (a) an exception that escapes `_check_one`, and a `TimeoutError` of the wait, are both discarded at L396 to L397 with no log; (b) a check that is still running after its 7 s wait (5.0 + 2.0) keeps running on its worker; the loop's waits are sequential, so one cycle can last up to about 7 s for each pending check; (c) the next cycle copies the watchlist again and can submit a second check of an entry whose earlier check is still running, so two checks of one entry can run at the same time on the two workers.
- P06-S050 FACT (`_check_one`, L411 to L468; docstring L412 to L415 "Never raises -- all exceptions caught and logged (EG12)"): (1) under the lock, return if the `signal_id` is no longer in the watchlist (L418 to L421); (2) time-out: `now = now_ist()`; `added_aware` is `added_at` with the IST zone attached when naive (L424 to L429); `elapsed_sec = (now - added_aware).total_seconds()`; if `elapsed_sec >= entry.timeout_sec`, call `self._release(entry, "TIMEOUT")` and return (L430 to L433); (3) quote read inside a `try` (L436 to L444): `quotes = self._quote_fn([entry.symbol])`, `quote = quotes.get(entry.symbol)`, `KeyError` if `None`, `ltp = float(quote.last_price)`, and on success the entry's failure count is removed under the lock; (4) on any exception (L445 to L460): under the lock the count becomes `previous + 1`; at `count >= _MAX_QUOTE_FAILURES` an ERROR log and `self._release(entry, "QUOTE_UNAVAILABLE")`, otherwise a WARNING "quote failure (n/3)"; then return; (5) price trigger (L463 to L468): `tolerance = entry.entry_price * entry.tolerance_pct`, `lower = entry_price - tolerance`, `upper = entry_price + tolerance`; `if lower <= ltp <= upper: self._release(entry, "PRICE_HIT", release_ltp=ltp)`; otherwise nothing happens and the entry waits for the next cycle.
- P06-S051 FACT (boundaries and units): the time-out test is inclusive (`>=`, L431) and is evaluated before the quote read, so an entry whose time-out has passed is released `TIMEOUT` without a quote read; the price window is inclusive at both ends (`<=`, L467); the window is symmetric and the same for `LONG` and `SHORT` (no direction is read in `_check_one`; the gate reads `direction` nowhere, search of L377 to L537); `tolerance_pct` is used as a fraction of the entry price (L463), so a stored 0.005 gives a window of plus or minus 0.5 % of `entry_price`. The strategy schema validates `pullback_wait_tolerance_pct` to `0 < v < 1` with default 0.005 and `pullback_wait_timeout_sec` to `>= 1` with default 180 (`strategies/schema.py` L112 to L113, L236 to L241, L272 to L277, A02's); the gate does not apply these validations to a rehydrated row (P06-S030).
- P06-S052 FACT (elapsed time source): the elapsed time is wall-clock time from `now_ist()` (`datetime.now(tz=_IST)`, `core/time_authority.py` L94 to L99) against the stored `added_at`; it does not use a monotonic clock. INTERPRETATION: a host clock change moves the elapsed time; an `added_at` later than the current time gives a negative elapsed time and no time-out until the clock passes it.
- P06-S053 INTERPRETATION (time-out and rehydration; from P06-S030, P06-S050, P06-S051): a rehydrated row whose `added_at` plus `timeout_sec` is already past when the first check runs is released `TIMEOUT` in that check, before any quote read. Only a row whose time-out has not yet passed, that is a restart within `timeout_sec` of the row's `added_at` (180 s at the schema default and at the value of all sixteen strategy files, A02 AUDIT T-14 L1162; the row's own value governs), can reach the quote read and so a `PRICE_HIT`.
- P06-S054 FACT (the quote read, interface with A04): `quote_fn` is the adapter's `get_quote` (`main.py` L3840), called with a one-symbol list for each entry in each cycle (L437); in live mode it takes a `quote` token from the rate limiter (`broker/zerodha_adapter.py` L1757) and returns a dict keyed by bare symbol, omitting a symbol absent from the broker's answer (L1773 to L1774), with `last_price` defaulting to 0.0 when absent (L1787) (A04 AUDIT RD-12). The gate reads only `last_price`; it does not read the quote's `ts` or any other field (L437 to L441).
- P06-S055 FACT (rate-limiter exceptions; interface, A04's limiter): the limiter's `acquire` raises `BrokerRateLimitError` after its maximum wait (`broker/rate_limiter.py` L213 to L223) and `RateLimitAbortedError` when the shutdown event is set during a wait (L236 to L244); a token available at once is taken without waiting (L205 to L211). `_check_one` catches every exception from the quote read at L445, so these exceptions, like broker errors and a missing symbol (`KeyError`, L440), count as quote failures (A04 evidence P05-S176).
- P06-S056 INTERPRETATION (quote-failure count): the count is per `signal_id`, in memory only (L132), reset by any successful read (L443 to L444) and by `remove`, `_release` and `clear_all`; it is not persisted, so a restart starts each rehydrated entry at zero. A quote with `last_price` 0.0 counts as a success (it is a number) and resets the count; for an entry with `entry_price > 0` and `tolerance_pct < 1` the window's lower bound is above 0, so a 0.0 never fires `PRICE_HIT` and such an entry ends by `TIMEOUT` (A04 RD-12's statement that the gate's test "simply does not fire on 0.0" holds under these two conditions). For a row with `tolerance_pct >= 1`, or with `entry_price` equal to 0, the window contains 0.0 and a 0.0 price would fire `PRICE_HIT`; the gate does not exclude such rows (P06-S030). A NaN `entry_price`, `tolerance_pct` or `ltp` makes both comparisons false, so the entry can only time out.
- P06-S057 INTERPRETATION (the "Never raises" docstring against the code): the time-out arithmetic (L424 to L433) and the price arithmetic (L463 to L468) are outside the `try` of L436, and so are the calls to `_release`; an exception raised there would escape `_check_one` and be discarded by the poll loop without a log (P06-S049 (a)). For entries built by the rehydration the numeric fields are already converted (P06-S029), so the escape route found is inside `_release` (section 7).
- P06-S058 INTERPRETATION (time-out against a slow quote read): the time-out is tested once, before the quote read (L431); a read that blocks (in the limiter up to its maximum wait, or in the broker call) and then returns a price inside the window releases `PRICE_HIT` even if the entry's time-out passed during the read.
- P06-S059 FACT (stated expectations only, A19's file `tests/unit/test_entry_gate.py`): tests expect a hit inside the window and at both boundaries (L346 to L458), an exact-price-only window when `tolerance_pct` is 0 (L471), a `TIMEOUT` release (L496), no release after one or two quote failures and a `QUOTE_UNAVAILABLE` release after three (L577 to L634), a reset on success (L635) and independence between symbols (L662).
