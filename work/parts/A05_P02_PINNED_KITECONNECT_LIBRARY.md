### 3.5 Subscriptions and the library's own token record

P02-S028. FACT (published kiteconnect 5.1.0 source, `ticker.py` L567 to L628): `subscribe(tokens)` sends `json.dumps({"a": "subscribe", "v": tokens})`, `unsubscribe(tokens)` sends `{"a": "unsubscribe", "v": tokens}`, and `set_mode(mode, tokens)` sends `{"a": "mode", "v": [mode, tokens]}`, each passed through `six.b(...)` to `self.ws.sendMessage(...)` with no `isBinary` argument. After the send, `subscribe` records each token in `self.subscribed_tokens` with the value `MODE_QUOTE` (`"quote"`), whatever its earlier recorded mode; `unsubscribe` deletes each token (absent tokens are ignored); `set_mode` records each token with the given mode, adding tokens that were never subscribed. If the send raises, each method calls `_close(reason="Error while ...: <error>")` and re-raises the exception. The library does not split token lists into batches, limit their size, or check the mode string or the token types. Whether the frame is sent as text or binary, and what `sendMessage` raises when the connection is not open, are autobahn's behaviour: UNKNOWN / NOT ESTABLISHED.

P02-S029. INTERPRETATION (Python semantics; published kiteconnect 5.1.0 source, `ticker.py` L454, L574, L582 to L584): before the first connection `self.ws` is `None`, so `subscribe`, `unsubscribe` and `set_mode` raise `AttributeError`; the `except` branch calls `_close`, which does nothing while `ws` is `None`, and re-raises; no token is recorded, because the record is updated only after the send.

P02-S030. FACT (published kiteconnect 5.1.0 source, `ticker.py` L630 to L647, L681 to L690): the library itself resubscribes after a reconnect. `_on_open` calls `resubscribe()` when `_is_first_connect` is false, then sets `self._is_first_connect = False`, then calls the user's `on_open`. `resubscribe()` groups `subscribed_tokens` by recorded mode and, for each mode, calls `subscribe(tokens)` and then `set_mode(mode, tokens)`. So on every open after the first, each token in the library's record is subscribed again in its recorded mode, before the user's `on_open` runs; on the first open nothing is resubscribed.

### 3.7 Reconnect algorithm

P02-S035. FACT (published kiteconnect 5.1.0 source, `ticker.py` L52 to L53, L168 to L201, L490 to L491): the library's own part of reconnection is: (a) the factory's `maxDelay` and `maxRetries` are set from `reconnect_max_delay` and `reconnect_max_tries`; (b) after a failed connection attempt (`clientConnectionFailed`) or a lost connection (`clientConnectionLost`) it calls `on_reconnect(retries)` when `retries > 0`, then `self.retry(connector)` (Twisted's `ReconnectingClientFactory.retry`), then `send_noreconnect()`; (c) each successful handshake calls `factory.resetDelay()` from `onConnect`. The delay arithmetic (initial delay, growth, jitter, the cap at `maxDelay`), how `retries` is counted and reset, and what `retry()` does once `maxRetries` is passed are inside Twisted's `ReconnectingClientFactory`, which was not read: UNKNOWN / NOT ESTABLISHED. HISTORICAL (published kiteconnect 5.1.0 source, `ticker.py` L346 to L353, L419 to L420): the docstrings describe an exponential backoff that starts from a "minimum interval which is 2 seconds", grows up to `reconnect_max_delay` and stops after `reconnect_max_tries` attempts.

P02-S036. FACT (published kiteconnect 5.1.0 source, `ticker.py` L192 to L201): when `maxRetries` is not `None` and `retries > maxRetries`, `send_noreconnect` logs "Maximum retries (...) exhausted." at DEBUG and calls `self.stop()` only inside `if self.debug:` (both lines are indented under that check, L195 to L198); then, whatever `debug` is, it calls `on_noreconnect()` if set. With `debug=False` (the default) the library therefore neither stops the reactor nor ends its thread when attempts run out: it only calls `on_noreconnect`. Whether the factory (through its autobahn or Twisted bases) has a `stop` method at all, for the `debug=True` case, is UNKNOWN / NOT ESTABLISHED; `ticker.py` defines none on the factory.

P02-S037. INTERPRETATION (basis P02-S031, P02-S035, P02-S036): `send_noreconnect` runs after every `retry()` call and fires whenever `retries > maxRetries` holds at that moment, so the library does not itself ensure that `on_noreconnect` fires only once; how `retries` behaves after the limit is Twisted's: UNKNOWN / NOT ESTABLISHED. Nothing in the library starts a new connection cycle after `on_noreconnect`: a later connection needs a new `connect()` call by the caller (P02-S023).

### 3.8 Liveness: ping, pong, heartbeat and timeouts

P02-S038. P02-S040. ### 3.9 Text messages

P02-S042. FACT (published kiteconnect 5.1.0 source, `ticker.py` L700 to L717): a text payload is decoded from bytes as UTF-8 (Python 3) and parsed with `json.loads`; a `ValueError` from `json.loads` makes the method return silently. Then a message with `"type": "order"` and a truthy `"data"` calls `on_order_update(ticker, data["data"])` (only if that callback is set), and a message with `"type": "error"` calls `_on_error(self, 0, data.get("data"))`, which logs at ERROR and calls the user's `on_error` with code `0`. No other text message type is handled; only the raw `on_message` callback sees them.

P02-S043. INTERPRETATION (Python semantics; published kiteconnect 5.1.0 source, `ticker.py` L703 to L717): the UTF-8 decode is outside the `try`, so undecodable text raises `UnicodeDecodeError` out of the parser, and a JSON value that is not an object (for example a list) makes `data.get` raise `AttributeError`. The library catches neither (P02-S032 applies).

### 3.10 The binary parser

P02-S044. FACT (published kiteconnect 5.1.0 source, `ticker.py` L844 to L863): framing: the first 2 bytes (big-endian unsigned short) give the number of packets; each packet is preceded by its own 2-byte big-endian length, and its bytes are sliced without any check against the bytes that remain. `_unpack_int` reads big-endian unsigned integers with `struct.unpack(">" + byte_format, bin[start:end])`, format `I` (4 bytes) by default or `H` (2 bytes). INTERPRETATION (Python `struct` and slicing semantics): a frame shorter than its declared lengths yields short slices; a slice shorter than 4 bytes makes the token read at L725 raise `struct.error`, and a missing length header makes L859 raise `struct.error`; neither is caught inside `_parse_binary` (P02-S032 applies). A frame that declares 0 packets, or whose packets all have unhandled lengths (P02-S046), gives an empty list, which is still passed to `on_ticks` when the payload is longer than 4 bytes.

P02-S045. FACT (published kiteconnect 5.1.0 source, `ticker.py` L724 to L737): for each packet, `instrument_token` is the first 4 bytes (unsigned) and `segment = instrument_token & 0xff` (the token's low byte). The price divisor is 10000000.0 when the segment is `cds` (3), 10000.0 when it is `bcd` (6), and 100.0 otherwise, so NSE (1), NFO (2), BSE (4), MCX (7) and indices (9) all use 100.0. `tradable` is `False` only when the segment is `indices` (9).

P02-S046. FACT (published kiteconnect 5.1.0 source, `ticker.py` L739 to L842): the packet's length alone decides how it is parsed and which `mode` value is written; the mode the caller subscribed is not consulted. The lengths handled are 8, 28, 32, 44 and 184; a packet of any other length is skipped silently (the `if`/`elif` chain has no `else`).

| Packet length | `mode` written | Dictionary keys produced (exact) |
|---|---|---|
| 8 | `"ltp"` | `tradable`, `mode`, `instrument_token`, `last_price` |
| 28 (index) | `"quote"` | `tradable`, `mode`, `instrument_token`, `last_price`, `ohlc` (`high`, `low`, `open`, `close`), `change` |
| 32 (index) | `"full"` | the 28-byte keys plus `exchange_timestamp` |
| 44 | `"quote"` | `tradable`, `mode`, `instrument_token`, `last_price`, `last_traded_quantity`, `average_traded_price`, `volume_traded`, `total_buy_quantity`, `total_sell_quantity`, `ohlc` (`open`, `high`, `low`, `close`), `change` |
| 184 | `"full"` | the 44-byte keys plus `last_trade_time`, `oi`, `oi_day_high`, `oi_day_low`, `exchange_timestamp`, `depth` (`buy`: 5 entries, `sell`: 5 entries; each entry `quantity`, `price`, `orders`) |

P02-S047. FACT (published kiteconnect 5.1.0 source, `ticker.py` L740 to L838; byte offsets as read by the code): 28-byte and 32-byte index packets: last price bytes 4 to 8, high 8 to 12, low 12 to 16, open 16 to 20, close 20 to 24; bytes 24 to 28 are not read; the 32-byte packet adds the exchange timestamp at 28 to 32. 44-byte and 184-byte packets: last price 4 to 8, last traded quantity 8 to 12, average traded price 12 to 16, volume traded 16 to 20, total buy quantity 20 to 24, total sell quantity 24 to 28, open 28 to 32, high 32 to 36, low 36 to 40, close 40 to 44; the 184-byte packet adds last trade time 44 to 48, OI 48 to 52, OI day high 52 to 56, OI day low 56 to 60, exchange timestamp 60 to 64, and ten 12-byte depth entries from byte 64 (the first five go to `buy`, the next five to `sell`; per entry, quantity 4 bytes, price 4 bytes, orders 2 bytes read as `H`; the entry's last 2 bytes are not read).

P02-S048. FACT (published kiteconnect 5.1.0 source, `ticker.py` L745 to L838): the divisor is applied to `last_price`, `average_traded_price`, every `ohlc` value and every depth `price`, which therefore come out as Python floats; it is not applied to the quantities, `volume_traded`, `oi`, `oi_day_high`, `oi_day_low` or the depth `orders`, which stay raw integers. `change` is not read from the packet: it is computed as `(last_price - close) * 100 / close`, or `0` when `close` is 0 (L764 to L767, L801 to L804).

P02-S049. FACT (published kiteconnect 5.1.0 source, `ticker.py` L769 to L776, L806 to L822): time stamps are produced only for full-mode packets: `exchange_timestamp` (32-byte and 184-byte packets) and `last_trade_time` (184-byte packets only), each by the exact call `datetime.fromtimestamp(self._unpack_int(packet, a, b))` with no time zone argument; any exception gives `None`. No tick of any mode has a key named `timestamp`. INTERPRETATION (Python semantics of `datetime.fromtimestamp(t)` without `tz`): the result is a naive `datetime` showing the local wall-clock time, on the machine that runs the code, of that epoch second (whole seconds, from a 4-byte unsigned value); the same packet gives different wall-clock values on hosts with different local time zones, and the value carries no offset. The legacy machine's local time zone setting is not established by this part.

### 3.11 The LTP-mode packet (the provisional checkpoint point)

P02-S050. FACT (published kiteconnect 5.1.0 source, `ticker.py` L739 to L746): an 8-byte (LTP) packet yields exactly four keys: `tradable`, `mode` (`"ltp"`), `instrument_token` and `last_price` (divided by the segment divisor). It yields no `exchange_timestamp`, `last_trade_time` or `timestamp`, no `volume_traded`, `last_traded_quantity` or `average_traded_price`, no buy or sell totals, no `ohlc`, no `change`, no `oi` keys and no `depth`. This settles the provisional point on the library side: in the published 5.1.0 parser, an LTP tick carries no time stamp of any kind and no volume. Whether the broker's server sent 8-byte packets for LTP-mode subscriptions in the legacy period is UNKNOWN / NOT ESTABLISHED (the current documentation is in section 5).

P02-S051. INTERPRETATION (basis P02-S046, P02-S050): because the parser chooses the keys by packet length, a token subscribed in LTP mode yields the four-key dictionary only when the server sends an 8-byte packet for it; a 44-byte or 184-byte packet would be parsed as `quote` or `full` whatever the subscription. An index token in LTP mode yields the same four keys, with `tradable` set to `False`.

### 4.3 `_request`: one attempt, response handling and errors

P02-S058. FACT (published kiteconnect 5.1.0 source, `connect.py` L870 to L927): every client method goes through `_get`/`_post`/`_put`/`_delete` to `_request`, which: builds the path from the route table (with `str.format(**url_args)` when there are URL arguments, no URL encoding by the library); joins it to `root` with `urljoin`; sets the headers `X-Kite-Version: 3` and `User-Agent: Kiteconnect-python/5.1.0`; adds `Authorization: token <api_key>:<access_token>` only when both `api_key` and `access_token` are truthy (L902 to L905), so a missing or empty token sends the request without that header and raises nothing on the client side; for GET and DELETE sends `params` as the query string (L911 to L912); and calls `self.reqsession.request(method, url, ..., verify=not self.disable_ssl, allow_redirects=True, timeout=self.timeout, proxies=self.proxies)` exactly once (L915 to L924).

### 4.4 `historical_data`

P02-S063. FACT (published kiteconnect 5.1.0 source, `connect.py` L151, L624 to L653): `historical_data(instrument_token, from_date, to_date, interval, continuous=False, oi=False)` sends one GET to `/instruments/historical/{instrument_token}/{interval}` (route `market.historical`) with the query parameters `from`, `to`, `interval` (the interval appears both in the path and in the query), `continuous` (`1` or `0`) and `oi` (`1` or `0`). P02-S064. FACT (published kiteconnect 5.1.0 source, `connect.py` L639 to L641): a date is formatted with `strftime("%Y-%m-%d %H:%M:%S")` only when `type(value) == datetime.datetime`; any other value is passed unchanged to requests as the query value. INTERPRETATION (Python semantics): (a) the exact-type test is false for a `datetime.date` and for subclasses of `datetime`, which are then passed unchanged and rendered by requests (requests' rendering not read); (b) for an aware `datetime` the format has no `%z`, so the offset is dropped and the wall-clock digits held in the object are sent as they are, with no conversion to another zone; (c) the format has no fraction of a second, so microseconds are dropped. HISTORICAL (published kiteconnect 5.1.0 source, `connect.py` L633 to L634): the docstring describes the dates as "datetime object or string in format of yyyy-mm-dd HH:MM:SS".

P02-S065. FACT (published kiteconnect 5.1.0 source, `connect.py` L655 to L670): `_format_historical` builds one dictionary per element `d` of `data["candles"]`, in the order received: `date` = `dateutil.parser.parse(d[0])`, `open` = `d[1]`, `high` = `d[2]`, `low` = `d[3]`, `close` = `d[4]`, `volume` = `d[5]`, and `oi` = `d[6]` only when `d` has exactly 7 elements. The prices and the volume are not converted: they stay as the JSON decoder gave them. The client does not sort, de-duplicate, fill gaps in, or validate the rows.

P02-S066. INTERPRETATION (basis: python-dateutil's documented parser behaviour; dateutil's source was not read): `dateutil.parser.parse` returns an offset-aware `datetime` when the string carries an explicit UTC offset (for a `+0530` suffix, a fixed offset of +05:30) and a naive `datetime` when it carries none. So whether a caller receives aware or naive candle times depends only on the string the server sends; the client adds no zone of its own. Which form the server sent in the legacy period is UNKNOWN / NOT ESTABLISHED (current documentation: section 5). INTERPRETATION (Python semantics): a candle row with fewer than 6 elements raises `IndexError`, a body without `candles` raises `KeyError`, and a time string that dateutil cannot parse raises dateutil's parser error; any of these ends the whole call, so the caller gets either the full list or an exception, never a partial list.

### 4.5 `instruments`

P02-S067. FACT (published kiteconnect 5.1.0 source, `connect.py` L148 to L149, L567 to L579, L951 to L952): `instruments(exchange=None)` sends one GET to `/instruments/{exchange}` (route `market.instruments`) when an exchange is given, or to `/instruments` (route `market.instruments.all`) otherwise; a CSV response comes back from `_request` as the raw body bytes and is passed to `_parse_instruments`. The whole body is held in memory; nothing is streamed.

P02-S068. FACT (published kiteconnect 5.1.0 source, `connect.py` L815 to L838): `_parse_instruments` decodes the bytes as UTF-8 and strips leading and trailing white space (Python 3), reads them with `csv.DictReader` (the first line gives the column names), and for every row converts exactly these columns: `instrument_token` with `int`, `last_price` with `float`, `strike` with `float`, `tick_size` with `float`, `lot_size` with `int`, and `expiry` with `dateutil.parser.parse(...).date()` only when its text is exactly 10 characters long (otherwise it is left as the original text, for example an empty string). Every other column stays a string exactly as in the CSV: in particular `exchange_token`, `tradingsymbol`, `name`, `instrument_type`, `segment` and `exchange` are not converted (`exchange_token` is not turned into an integer). Rows are returned in file order, with no filtering, de-duplication or validation of values.

P02-S069. INTERPRETATION (Python semantics; basis P02-S068): a dump without one of the six columns the parser reads raises `KeyError`, and an empty or non-numeric value in a converted column raises `ValueError` (for example `int("")`); the parser has no per-row `try`, so one bad row ends the whole call and the caller receives an exception, not a partial list.
