### 2.4 Calculations

- P07-S019 FACT (the window): both metric functions take `start_date = as_of_date − lookback_days` calendar days (L84 to L87, L130 to L133) and select `SUBSTR(updated_at, 1, 10) >= start_date AND <= as_of_date` (L97 to L98, L142 to L143); both ends are inclusive, so the default window spans 31 calendar dates. The trade's date is the first ten characters of `updated_at`, not `exit_time` (schema L142) or `entry_time` (L141). INTERPRETATION: the date assigned to a closed trade is the date of its last row update; any later update of a closed row (by a reconciliation or back-fill writer, A03's and others') moves it to a later date bucket. Whether such updates occurred is UNKNOWN / NOT ESTABLISHED. The text comparison assumes that `updated_at` begins with `YYYY-MM-DD` (A03 owns the value format).
- P07-S020 FACT (the Sharpe ratio, `compute_sharpe`, L70 to L116): the query sums `net_pnl` per date over the strategy's closed trades in the window (`GROUP BY trade_date ORDER BY trade_date`, L89 to L103), so each observation is one date's total net P&L, and dates with no closed trade are absent (not zero). With fewer than two dates the result is `None` (L105 to L106). Otherwise: `mean = sum / n` (L109); `variance = Σ(x − mean)² / (n − 1)` (L110); `std = sqrt(variance)` if the variance is above zero, else 0.0 (L111); when `std` is 0.0 the result is 0.0 (L113 to L114); otherwise the result is `(mean / std) × sqrt(252)` (L116). The docstring states the same: "Sharpe = mean(daily_pnl) / std(daily_pnl) * sqrt(252)"; "Returns None if fewer than 2 trading days of data" (L79 to L82). No risk-free rate or benchmark is subtracted.
- P07-S021 FACT (current external context, read 2026-11-21; not evidence of what production did): Sharpe's own article defines the ex post Sharpe ratio on the "differential return" and states that "Originally, the benchmark for the Sharpe Ratio was taken to be a riskless security", so that "the differential return is equal to the excess return of the fund over a one-period riskless rate of interest" (https://web.stanford.edu/~wfsharpe/art/sr/sr.htm, sections "The Ex Post Sharpe Ratio" and "Scale Independence"); on time aggregation it states that the simple-summing case assumes one-period differential returns that "have zero serial correlation" and that "It is common practice to 'annualize' data that apply to periods other than one year" (section "Time Dependence"). Lo's abstract states that "monthly Sharpe ratios cannot be annualized by multiplying by √12 except under very special circumstances", because of serial correlation (https://rpc.cfainstitute.org/research/financial-analysts-journal/2002/the-statistics-of-sharpe-ratios). The sample (n − 1) denominator of L110 is the form of Excel's `STDEV`, which Sharpe's spreadsheet example uses ("AVERAGE(C1:C60)/STDEV(C1:C60)"); his endnote on the denominator is worded ambiguously, so this part draws no conclusion from it.
- P07-S022 INTERPRETATION (comparison of P07-S020 with P07-S021): the script's ratio differs from the article's definition in three recorded ways: (a) its observations are daily rupee P&L totals, not returns on a capital base, so the ratio changes when position sizes change even at the same return; (b) no riskless rate or benchmark is subtracted; (c) its observations are only the dates with at least one closed trade, while the factor √252 corresponds to one observation per trading day of a year; the √n scaling also rests on the zero-serial-correlation assumption that the article and Lo's abstract name. Whether the script's figure was meant as the textbook ratio or as an internal score is not stated by any source found (Question for Rama, section 10, P07-R2).
- P07-S023 FACT (win rate and average P&L, `compute_win_rate`, L119 to L156): over the same window and filters, without grouping (L135 to L146), `total` is the number of closed trades with non-null `net_pnl`; with none the result is `(None, None, 0)` (L148 to L150); otherwise `win_rate = (number with net_pnl > 0) / total` and `avg_pnl = Σ net_pnl / total` (L152 to L156). A trade with `net_pnl` exactly 0 counts as not a win. The DDL comments define `win_rate` as "fraction of winning trades (0-1)" and `avg_pnl` as "average net P&L per trade" (schema L938 to L939); no currency unit is stated in the DDL (L149, L939).
- P07-S024 FACT (rounding): the stored values are `round(sharpe, 4)`, `round(win_rate, 4)` and `round(avg_pnl, 2)`, each kept as `None` when the computed value is `None` (L258 to L265); `total_trades` is the unrounded count from `compute_win_rate` (L264). The demotion check reads the stored, rounded `sharpe` (L187 to L195, section 2.6).
- P07-S025 FACT (stated expectations, A19; never run): `tests/unit/test_fix134_strategy_metrics.py` expects `None` with no data and with one day (L65 to L72), 0.0 when every day has the same P&L ("All same P&L -> std = 0 -> sharpe = 0", L74 to L81), a negative value for mostly negative days (L92 to L99), and a value equal to `(mean / sqrt(sample variance)) × _ANNUALIZATION_FACTOR` within 0.01 (L101 to L111); win rates 1.0 and 0.5 and `(None, None, 0)` with no trades (L117 to L140); a stored row after a run and no row after a dry run (L146 to L176). INTERPRETATION: the test of L74 to L81 states, as expected behaviour, that identical daily P&L gives 0.0; by the same branch (L113 to L114) identical negative daily totals also give 0.0, which is not below the demotion threshold.

### 2.6 The demotion rule (Q18)

- P07-S030 FACT (`_check_demotion`, L176 to L230): it reads `SELECT sharpe FROM strategy_metrics WHERE strategy = ? ORDER BY date DESC LIMIT 3` (L187 to L195, with `_CONSECUTIVE_BAD_DAYS` as the limit); with fewer than three rows it returns False (L196 to L197); it returns False unless every one of the three rows has a non-null `sharpe` strictly below `-0.3` (L199 to L204); otherwise it logs CRITICAL `strategy_metrics.demotion_triggered` with the strategy, threshold, day count and recent Sharpe values as `extra` fields (L206 to L214), sends a notification only `if notifier is not None` (L215 to L229), and returns True (L230).
- P07-S031 FACT (the trigger's inputs): the three rows are the strategy's three most recent stored dates, not three consecutive calendar or trading days and not tied to the date being computed (the query has no date condition, L189 to L192). The check runs inside the loop right after the strategy's own insert (L289), so on a normal run the newest row is the one just written; it does not run in a dry run (L273, L289). ### 4.4 The reconcile rules (`reconcile`, L98 to L167; pure, no I/O)

- P07-S058 FACT (NEW): the "actual" set is the union of the direction map's names and the signal names (L120 to L121). For each name of that set, in sorted order, that has no registry row (L123 to L125): the direction is the direction map's value (L129); if there is none, the strategy's realized directions are used only when there is exactly one (L130 to L132); if still none, a WARNING "seen but direction unresolvable (no YAML, no single realized side) — not registered" is logged and the name is skipped (L133 to L136). Otherwise a row is added with `direction`, `registration_status: "PENDING"`, `health: "OK"`, `first_seen: <today>` and `evidence: {source_yaml: "config/strategies/<name>.yaml" or "signals (no YAML)", scanner: <name>}` (L137 to L147), and the name is listed as newly registered (L148).
- P07-S059 FACT (CONFIRM): over every row of the registry after the NEW step, a row whose `registration_status` is `"PENDING"` and whose name is in the filled set becomes `"CONFIRMED"` and is listed as newly confirmed (L151 to L154). No rule moves a row back from CONFIRMED to PENDING.
- P07-S060 FACT (CONFLICT): for every row, with `declared = row.get("direction")` and `rz` the realized set, `conflict = bool(declared) and any(d != declared for d in rz)` (L156 to L158); a conflict sets `health = "DIRECTION_CONFLICT"` and lists the name as newly conflicted only when the previous `health` (default `"OK"`) was not already `"DIRECTION_CONFLICT"` (L159 to L163); no conflict sets `health = "OK"` (L164 to L165). The declared `direction` of an existing row is never changed (the only assignment of `direction` is in the NEW step, L137 to L138).
- P07-S061 FACT (what the rules never do): no row is removed (the function only adds rows and updates `registration_status` and `health`, L115 to L167), and the direction of an existing row is not refreshed from the strategy file. The status and health values are written as string literals; the module constants `VALID_STATUSES` and `VALID_HEALTH` are read nowhere (P02-S100).
- P07-S062 INTERPRETATION: (a) the realized set is taken over every filled trade ever stored (P07-S056), so once one filled trade's direction differs from a row's direction, that row stays `DIRECTION_CONFLICT` on every later run unless the trade rows change; the "self-heal" branch (L164 to L165) applies only when no differing trade remains in the rows read, which also happens on a run whose trade query failed (P07-S057; qualified in the check); (b) since the trading path takes a trade's direction from the strategy object (P02-S108), for trade rows written through that path (other writers of `trades` rows are not traced here; qualified in the check) a conflict for a strategy with a file arises when the file's `direction` differs from the direction stored in its registry row (for example after the file's direction was edited) or for a signal-only name; (c) a row for a strategy whose file was removed stays in the registry indefinitely.
