## 3. The adapter's own HTTP 429 handling (`_is_429`, `_compute_429_backoff_delay`, `_reset_429_attempts`, L2006 to L2033; the 429 branch of `_translate_broker_exception`, L2052 to L2077)

- **P02-S028** HISTORICAL: the stated intent is the module docstring's BL-6 paragraph (L70 to L88, "locked 2026-04-19, Phase D.1"): detect a broker HTTP 429 by `getattr(exc, "code", None) == 429`; translate it to `BrokerRateLimit429Error`, distinct from the client-side `BrokerRateLimitError`; before raising, call `rate_limiter.penalize(category, delay)` with an exponential delay from a per-category attempt counter (initial 0.2 s, multiplier 2, maximum 5.0 s, plus or minus 0.05 s jitter); reset the counter after any successful call in the same category; never retry or sleep (ZA11, L28: "Adapter does NOT retry. Single attempt, raise and exit."); the caller (OrderPlacer, BL-19) owns the retry.
- **P02-S029** FACT: `_is_429` returns `getattr(exc, "code", None) == 429` (L2008). The class is not examined, and the test runs before the class tests (L2052), so any exception carrying code 429, whatever its class (a `TokenException` included), becomes `BrokerRateLimit429Error`.
- **P02-S343** HISTORICAL: the BL-6 block says "Empirically the SDK wraps 429 into either kex.NetworkException (transport-shaped) or kex.GeneralException (API-shaped)" (L1994 to L1996), and the module docstring says a 429 "can surface via kex.NetworkException, kex.GeneralException, or any other exception carrying .code == 429" (L84 to L86); both date from 2026-04-19 (`dfc4779`). FACT: in the actions that use `_translate_broker_exception`, an exception of either class that carries code 429 becomes `BrokerRateLimit429Error`, because the 429 test runs before the class tests (P02-S029), and not the `BrokerTimeoutError` or `BrokerError` of its class row (P02-S013, P02-S017). What the SDK raises for a 429 is UNKNOWN / NOT ESTABLISHED (P02-S318).
- **P02-S030** FACT: on a 429 (L2052 to L2077): the category is `_CATEGORY_MAP.get(operation, "order")` (L2053); `_compute_429_backoff_delay(category)` gives the delay and attempt number (L2054); `self._rl.penalize(category, delay)` is called (L2056), and a `ValueError` from it is logged at ERROR as "zerodha_adapter.penalize_unknown_category" and swallowed (L2057 to L2064); a WARNING "zerodha_adapter.broker_429" is logged with operation, category, attempt, delay and the caller's context (L2065 to L2070); the method returns `BrokerRateLimit429Error("broker 429 on <operation>", operation=..., category=..., delay_sec=..., attempt=...)` (L2071 to L2077).
- **P02-S031** FACT: in the 429 branch the original exception is not passed to `log_exception`, and the returned error's context holds only operation, category, delay_sec and attempt; the caller's context (for example the symbol) appears in the warning but not on the exception (L2065 to L2077).
- **P02-S032** FACT: `_compute_429_backoff_delay` (L2010 to L2028) reads the category's prior count (0 if absent) and stores prior + 1 under `self._429_lock` (L2018 to L2020); outside the lock it computes `initial_delay_sec * multiplier ** prior`, caps it at `max_delay_sec`, adds `random.uniform(-jitter_sec, jitter_sec)` when `jitter_sec > 0`, floors the result at 0.0 and returns (delay, prior + 1) (L2021 to L2028).
- **P02-S033** FACT (arithmetic on the configured values, `config/broker_limits.yaml` L35 to L40, which equal the model defaults, `core/config_loader.py` L2203 to L2207): successive 429s in one category with no success between them give nominal freezes of 0.2, 0.4, 0.8, 1.6 and 3.2 s, then 5.0 s for every later one, each plus or minus up to 0.05 s.
- **P02-S034** FACT: `_reset_429_attempts(category)` removes the category's counter under the lock (L2030 to L2033). The order actions call it after a successful SDK call: `place_order` (L664), `place_gtt` (L749), `modify_gtt` (L797), `get_gtt` (L929), `get_gtts` (L944), `delete_gtt` (L962); the read methods of other parts call it too (L991, L1200, L1274, L1516, L1614, L1724, L1769, L1825, L1849, L1906, L1962).
- **P02-S035** FACT: the categories used by each order action are as in the table below.

- **P02-S036** FACT: `_CATEGORY_MAP` (L254 to L269) has no "place_gtt" or "modify_gtt" key; both methods use the "place_order" key and pass the operation name "place_order", so a 429 on a GTT placement or modification is logged and raised as operation "place_order".
- **P02-S037** FACT: `cancel_order` and `modify_order` catch every exception from the SDK call and return a result object (L1068 to L1074, L1141 to L1147) without calling `_translate_broker_exception`. A broker 429 on a cancel or a modify therefore neither freezes the bucket nor advances the counter and is reported only as `success=False` with `reason=str(exc)`; and a successful cancel or modify does not reset the "order" counter. HISTORICAL: the legacy note `docs/audit/batch_classification_16jul2026.md` L140 records "429 backoff bypassed on `cancel_order`/`modify_order`".
- **P02-S038** FACT: an operation name that is not a key of `_CATEGORY_MAP` defaults to "order" (L2053). At the baseline two methods outside this part pass such names: "order_margins" (L1610, after acquiring "order" at L1593) and "get_quote_raw" (L1823, after acquiring "quote" at L1818). INTERPRETATION: a 429 on `get_quote_raw` freezes and counts against the "order" bucket, not the "quote" bucket it took its token from, while its success resets the "quote" counter (L1825). (The method is P03's; it is recorded here because the default is at L2053.)
- **P02-S039** INTERPRETATION (comparison of two literal sets): the map's categories ("order", "margins", "quote") and the default "order" are all among the limiter's four categories (`broker/rate_limiter.py` L45, L157 to L162), so the `ValueError` branch at L2057 to L2064 cannot be reached with the baseline map.
- **P02-S040** FACT (limiter side, P05's subject, recorded for the adapter's contract): `penalize` freezes the category's bucket for the given time and logs a WARNING (`broker/rate_limiter.py` L258 to L272; `_Bucket.freeze` L101 to L105); while frozen, `acquire` keeps waiting up to `max_wait_sec` (constructor default 30 s, L152) and then raises `BrokerRateLimitError` (L214 to L223); a set shutdown event ends the wait with `RateLimitAbortedError` (L236 to L244).
- **P02-S041** FACT: no order action's own code sleeps or loops; each Live invocation makes exactly one SDK call (L639, L742, L790, L926, L941, L959, L1061, L1131). The waiting is in the limiter: `acquire`, which each action calls before its SDK call, polls and sleeps until a token is free, its deadline passes or shutdown is signalled (`broker/rate_limiter.py` L204 to L246), so the pacing after a 429 comes only from the next `acquire` on the frozen bucket.
- **P02-S042** INTERPRETATION: the counter is per category and shared by every thread using the adapter instance; a success of any method in the same category resets it (for example `get_order_history`, category "order", L1200), so while one thread keeps receiving 429s another thread's success can restart the sequence of P02-S033 at 0.2 s.
- **P02-S043** FACT: the adapter contains no soft-kill or kill-switch call for 429s; the word "kill" occurs in it only in comments and a docstring (L1237, L1422, L2361; text search). The configured ladder `broker_limits.backoff_sequence_sec` (1, 5 and 30 s, then a soft kill; `config/broker_limits.yaml` L25 to L29) is read by no non-test Python code; only `core/config_loader.py` declares it (L2251) (A02 K-32, A04 side; the whole-system question is P05's).

### 4.2 The flow, step by step

- **P02-S047** FACT: step 1 (L547 to L553): an INFO log "place_order call_start" with method, symbol, side, qty, order_type and intent (price and tag are not logged).
- **P02-S048** FACT: step 2 (L560 to L562): `_validate_place_order` runs first, before the tick snap, the product resolution, the state machine and the paper branch. Its checks, each raising `ValueError` with a descriptive message, are in the table below.

|---|---|---|

| P02-S050 | `side` is "BUY" or "SELL" (`_VALID_SIDES`, L229) | L2093 to L2096 |
| P02-S051 | `qty` is an `int` and greater than 0 | L2097 to L2100 |
| P02-S052 | `order_type` is one of "MARKET", "LIMIT", "SL", "SL-M" (`_VALID_ORDER_TYPES`, L230) | L2101 to L2105 |
| P02-S053 | `price` greater than 0 for "LIMIT" and "SL" | L2106 to L2109 |
| P02-S054 | `trigger_price` greater than 0 for "SL" and "SL-M" | L2110 to L2115 |

- **P02-S056** FACT: not validated: `variety` (any string reaches the SDK), `intent` (only the resolver checks it, step 5), `tag`, `price` for "MARKET" and "SL-M", `trigger_price` for "LIMIT" and "MARKET" (a positive trigger is sent whatever the order type, L648), and the pairing of `market_protection` with an order type (a band is accepted and sent with any order type). ## 5. Tick resolution and snapping (`_resolve_tick`, L1383 to L1407; `_snap_order_to_tick`, L1409 to L1463)

- **P02-S099** HISTORICAL: the stated intent: `_resolve_tick`'s docstring (L1384 to L1390, 2026-06-23, `478673f`) says the tick is resolved "FAIL-SAFE", falling back to `DEFAULT_TICK` (0.05) when the cache is unwired, the symbol is unknown or the tick is not positive, with a throttled warning; it "NEVER signals 'do not round'", because "a 0.05-multiple is also a valid 0.01-multiple"; the "Residual edge (unknown symbol whose true tick > 0.05) is now ALERTED, not silent". `_snap_order_to_tick`'s docstring (L1417 to L1435, 2026-06-16, `7f93c2f`, updated by `478673f`) says Zerodha rejects any price or trigger that is not a tick multiple and calls the method the "Authoritative net for ALL placements (entry, SL, TGT, emergency and kill exits)".
- **P02-S100** FACT: `_resolve_tick(symbol)`: when `self._instrument_cache` is set it calls `tick_size(symbol)`, and any exception gives `None` (L1391 to L1396). When the result is `None` or not positive, the first time for each symbol (the set `_missing_tick_warned`, L425) it logs a WARNING "snap_to_tick.missing_tick_size" with the symbol and the fallback tick, and it returns `DEFAULT_TICK` (L1397 to L1406), which is 0.05 (`orders/price_math.py` L27). - **P02-S101** FACT: the constructor's cache default is `None` (L387); `main.py` binds the cache later with `broker_adapter.set_instrument_cache(instrument_cache)` (L2522; setter L1370 to L1381). Until then, and in any construction that never binds a cache, every symbol resolves to 0.05.
- **P02-S102** FACT: `_snap_order_to_tick` takes the tick from `_resolve_tick` (L1436). For "SL", a positive price is rounded down for "SELL" and up otherwise (L1438 to L1445), and a positive trigger is rounded to the nearest tick (L1446 to L1447). For every other type ("LIMIT", "MARKET", "SL-M"), a positive price and a positive trigger are both rounded to the nearest tick (L1448 to L1452). A change is logged at DEBUG "adapter.snap_to_tick" (L1454 to L1462); the method returns the pair (L1463).
- **P02-S103** FACT: the three rounding helpers (`broker/slippage_engine.py` L147 to L186) convert the value and the tick with `Decimal(str(...))`, divide, quantize to an integer with `ROUND_CEILING` (up), `ROUND_FLOOR` (down) or `ROUND_HALF_UP` (nearest), multiply by the tick and return a `float`.
- **P02-S104** INTERPRETATION (from the code and the blame dates): the comments at L566 ("No-op when no cache is wired") and L384 to L386 ("None = no-op"), both of 2026-06-16, predate the fail-safe of 2026-06-23; at the baseline an unwired cache gives the tick 0.05 and the price is still rounded (L1397 to L1406), so these two comments no longer describe the code.
- **P02-S105** FACT: the docstring's rule "MARKET / SL-M: price is 0; nothing to snap" (L1430) is a statement about the callers, not a branch: a positive price passed with "MARKET" is rounded to the nearest tick (L1449 to L1450) and is then not sent (L647); an "SL-M" trigger is rounded to the nearest tick.
- **P02-S106** INTERPRETATION (arithmetic): with the fallback tick of 0.05, the price of an instrument whose true tick is 0.01 moves by up to 0.025 (nearest) or by just under 0.05 (the directional rounding of an "SL" limit); for an instrument whose true tick is larger than 0.05, a multiple of 0.05 can still be off-tick, which is the docstring's residual edge.
- **P02-S107** INTERPRETATION (arithmetic): because validation precedes snapping (P02-S057), a positive price below half a tick (nearest rounding) or below one tick (an "SL" "SELL" limit, rounded down) would become 0.0 after validation and be sent as 0.0 for "LIMIT" or "SL".
- **P02-S108** FACT: the adapter has no public tick method; `_resolve_tick` and `_snap_order_to_tick` are its only tick methods (L1383, L1409). Besides `place_order` and `modify_order` (L1110, section 7), `_resolve_tick` is used through the private name by `main.py` L3034 (`tick_fn=broker_adapter._resolve_tick`, given to `CncGttPlacer`, which rounds the GTT triggers and limits itself, `orders/cnc_gtt.py` L114 to L118 and L229 to L234) and by `scripts/t2_cnc_gtt_realtest.py` L274 and L589 (A19). A01 C36d hands A04 the stability of `_resolve_tick` as a private attribute used across owners; the A04 side is this contract: a positive tick always, 0.05 when nothing better is known, one warning per symbol.

### 10.2 What a repeat sends, and what the adapter tells the caller

- **P02-S175** FACT: `place_order` and `place_gtt` create a new broker object on every call and send no client order id or idempotency key (P02-S081, P02-S141); the only caller-chosen identifier sent with an order is the tag, cut to 16 characters (P02-S066), and `place_gtt` sends no tag at all. INTERPRETATION: a repeated call is a new request; whether the broker would recognise a duplicate is UNKNOWN / NOT ESTABLISHED.
- **P02-S176** FACT: the outcomes that mean "not sent" are the ones raised before the SDK call: validation, product, CNC-lock and conversion errors, and the limiter's `BrokerRateLimitError` and `RateLimitAbortedError` (P02-S089 to P02-S092, P02-S157, P02-S159), because `acquire` and the checks precede the call in every method. ### 11.2 Question 11 (adapter side): rate limits, 429s, throttling, transient errors and timeouts

- **P02-S193** FACT: every Live order action takes one limiter token before its SDK call, in the category of P02-S035; for `place_order` this is after validation, product resolution and the state-machine registration (L560 to L622). Client-side exhaustion surfaces as `BrokerRateLimitError` after the limiter's wait, and a shutdown as `RateLimitAbortedError`, both unchanged and both before the request is sent (P02-S064, P02-S176). The limiter's sharing between threads is P05's.
- **P02-S194** FACT: a broker 429 on `place_order`, a GTT action or a read freezes the category's bucket for an exponentially growing delay and raises `BrokerRateLimit429Error` (section 3); on `cancel_order` and `modify_order` it is reported only as `success=False` (P02-S037). The adapter does not retry, sleep or call a kill switch (P02-S041, P02-S043).
- **P02-S195** FACT: timeouts: the adapter passes no per-call timeout (P02-S083); a `kex.NetworkException`, built-in `TimeoutError` or `socket.timeout` becomes `BrokerTimeoutError`, and any other transient error becomes `BrokerError` (P02-S013, P02-S016 to P02-S018), with the uncertainty of P02-S022 about library exceptions.

### 11.3 Question 13 (adapter side)

- **P02-S196** FACT and INTERPRETATION, as established in section 10: the adapter never repeats an action (P02-S171); repeats come only from the callers (P02-S173); `place_order` and `place_gtt` send no idempotency key, so each repeat is a new request (P02-S175); the adapter separates "not sent" outcomes clearly (P02-S176), but after an SDK exception the broker outcome is unknown, and the adapter reports that uncertainty as `BrokerTimeoutError` only for the timeout classes it recognises (P02-S178), as `success=False` for cancels and modifications (P02-S180), and for `place_order` records FAILED in every case (P02-S177).
