## 3. The storage system in brief

From STUDY 2, with the AUDIT's refinements applied.

The legacy system stores its state in two SQLite files, reached through Python's `sqlite3` (the only database engine in non-test code): the trading database `data_store/trading_system.db` and the analytics database `analytics.db`, which always sits beside whatever main path is opened and is attached to main connections as schema `analytics`. No configuration key names either file for the trading application: the trading process opens the store with the relative literal `data_store/trading_system.db`, so the file it reaches depends on its working directory, while most scripts anchor the path to the project root.

`core/state_store.py::StateStore` keeps one connection per thread, opened in autocommit mode with a 30-second lock wait and the PRAGMAs `journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`, `temp_store = MEMORY` and `busy_timeout = 30000`; `transaction()` is `BEGIN IMMEDIATE` with `COMMIT` or `ROLLBACK`, without nesting or retry. There are 26 non-test `StateStore` constructions in 26 files, of which only `main.py` may migrate; 21 files outside `core/` open SQLite otherwise, 12 of them with a raw `sqlite3.connect` without the store's PRAGMAs; every heartbeat write constructs a full `StateStore`.

`core/schema.sql` declares 45 tables (577 columns), 73 named indexes and one trigger, every CREATE with `IF NOT EXISTS`, and stamps `schema_version` to `'45'`; `core/analytics_schema.sql` declares 3 tables and 4 indexes, with no version marker. Every `StateStore` construction initialises the analytics schema, reads the stored version, refuses a newer database, refuses a pending migration unless the opener may migrate and the market is closed, and then re-runs the whole `schema.sql`. Migrations rebuild whole tables to the current definition, one transaction per table, with no backup first. The store has about 120 query and write helpers; many writes bypass them through `transaction()` or `execute` with SQL held in the calling module.

Files under `data_store/` and `logs/` (daily JSON-lines logs, sentinels, evidence and V3 JSONL, state files, locks, pre-flight and security files, reports) use three write disciplines: temporary file plus rename, append, or in-place overwrite, with `fsync` in three writers only. Declared cron jobs back up both databases nightly with the `sqlite3` command-line `.backup` into `data_store/backups/`, and the six A03 scripts copy the evidence JSONL, drill-restore the newest main backup into a temporary copy, prune backups by count, delete old rows from six tables, prune report and log files, and run a PASSIVE WAL checkpoint. Every backup lands under the project's own `data_store/`; no code copies any artefact to another machine.

The most important facts:

- FACT: the trading process's database path is a working-directory-relative literal (`main.py` L2233 to L2237), shared by 13 other opener rows and the heartbeat helper, with no configuration key (STUDY 3.1, 9.1; D-02).
- FACT: every `StateStore` open that passes the version gates re-applies `schema.sql`, re-runs its three `DROP ... IF EXISTS` statements and re-writes the version row, in every process that opens the store, reports and dry runs included; the analytics DDL is applied by every opener before the gates (STUDY 5.1, 5.2, 8; H-19, Y-02). [refined: AUDIT, Appendix A; section 6, row 7: the re-stamp needs the write lock, so an open can wait 30 s and fail while another process writes.]
- FACT: a write-capable opener without an existence check creates a missing database: `StateStore` builds the full schema, the others an empty file (STUDY 3.5, 11; D-03, Z-05). [refined: section 6, row 1: the pre-flight WAL auto-fix also creates the file and reports AUTOFIXED.]
- FACT: only `main.py` passes `allow_migrate=True`; the boot path can migrate only off-market inside the service start window, and `--status` and `--dry-run` reach the same constructor (STUDY 5.3). [refined: section 6, row 6: the single-instance lock refuses both diagnostics beside a running service, so their database writes apply only while it is down.]
- FACT and INTERPRETATION: the migration runner's "idempotent" skip compares a target text ending with `;` with the stored text without it, so every listed table in range is rebuilt on every migration run; a multi-table run commits table by table (STUDY 5.5; N-01, N-02).
- FACT: storage failures reach callers as raw `sqlite3` errors; `TransactionError` is never raised; `_best_effort_insert` and the heartbeat helper swallow every exception without a log (STUDY 3.3, 6.5; D-10, Q-04, Q-20).
- FACT: the restore drill tests only the newest main backup, into a temporary copy, checks 26 of the 45 tables and records heartbeat SUCCESS whatever its verdict; no restore program exists (STUDY 10.4, 10.9; J-11, J-14, J-19).
- FACT: `fm_ledger` rows older than 365 days are deleted by `scripts/db_retention.py`, while the schema says its rows are never deleted (STUDY 10.6; Z-01).

### 4.3 Migrations and schema versioning (STUDY 5)

- FACT: migration happens inside the `StateStore` constructor: the analytics schema is initialised and the connection opened before the stored version is read; a version above 45 raises `SchemaVersionMismatch`; a version below 45 is refused (CRITICAL log, attempted sentinel, `MigrationNotPermitted`) unless `allow_migrate and not market_open`, otherwise `run_migrations` and the analytics relocation run; then `executescript(schema.sql)`; then a post-check. No `PRAGMA user_version`; the target exists as two literals (`EXPECTED_SCHEMA_VERSION`, L102; the text at `schema.sql` L1610), compared only after the stamp is written (STUDY 5.1).
- FACT: outcome by state: a new or empty file is built and stamped 45 by any opener at any time; an existing file with a missing or non-integer version row is treated like a new one (INTERPRETATION: a statement needing a newer column then raises before the stamp); a current file has the script re-run and 45 re-stamped by every opener on every open; an older file is refused or migrated; a newer one is refused. Before either gate, the analytics initialisation, the PRAGMAs and the ATTACH have already run (STUDY 5.2).
- FACT: only `main.py` `_main_locked` passes `allow_migrate=True`, with `market_open` from a weekday-and-hours test without holidays; INTERPRETATION: without a bypass flag the boot can migrate only in [08:00, 09:15) or (15:30, 18:15) IST on a day the holiday guard lets through. `migrate_to_latest()` is an uncalled stub; four readers check the version without migrating (STUDY 5.3).
- FACT: `MIGRATION_TABLES` rebuilds whole tables to the current definition at versions 25, 26, 27, 29, 30, 32, 34, 35, 38 and 45; each rebuild runs inside one `BEGIN IMMEDIATE` with `foreign_keys` off, copies the common columns, drops, renames, re-creates the table's indexes (not the trigger) and runs a whole-database `foreign_key_check`; the v28 relocation moves the three analytics tables out of `main` one transaction per table, on every migration run (STUDY 5.4).
- FACT and INTERPRETATION: each rebuild is one transaction and the run has none around it; a failure leaves earlier tables rebuilt and the version unchanged; a restart re-runs the range; under the declared unit (`Restart=on-failure`, `RestartSec=10`) a deterministic failure restarts every 10 seconds while the window allows, and the first restart after 15:30 would migrate a database refused in market hours; no backup is taken before migrating (HISTORICAL: deploy notes describe operator backups) (STUDY 5.5). [refined: section 6, row 12: every route that returns a store re-creates the trigger (N-30).]
- FACT: exception classes and exit codes: `StateStoreError`, `SchemaVersionMismatch` and `MigrationNotPermitted` (exit 1); `TransactionError` (never raised); `MigrationError` on `Exception` only, and raw `sqlite3` or OS errors (exit 2); relocation errors are not wrapped (STUDY 5.6).

### 4.4 The state-store API and persistence contracts (STUDY 6)

- FACT: L618 to L1901 define 46 methods (31 read-only, 15 writing); L1902 to L3355 define 74 methods; the records check counts 137 methods in the class, about 120 of them query or write helpers. Reads run outside a transaction, except four that take the write lock (STUDY 6.1).
- FACT: each write method runs one `transaction()`; only `release_gate_state` and `release_retest_state` combine two writes atomically; no method retries, and outside `_best_effort_insert` none catches database errors. Callers combine separately committed calls (for example the reconciler's manual-close sequence, the recovery adoption, the EOD write-ahead log, the GTT exit and recreate sequences); INTERPRETATION: a stop between them leaves partial state (STUDY 6.2).
- FACT: the state transitions written by store UPDATEs are tabled in STUDY 6.3; the six status-writing `trades` UPDATEs of the store restrict the from-status to non-terminal values; raw SQL outside the store writes the same transitions, some without a from-state condition. `INSERT OR REPLACE` is used by nine methods and `INSERT OR IGNORE` by two; INTERPRETATION: `INSERT OR REPLACE` deletes and re-inserts the row with a new id (STUDY 6.3).

### 18.2 The treatment groups of the 206 ISSUEs

Rama's choices (11-Nov-2026), each adopting ChatGPT's suggested choice; the Audit Findings Register quotes each recommendation, accepted principle and qualification in full, and governs. "A" is accept; "B" is accept with qualification. Every group's status is AGREED (11-Nov-2026), and every ISSUE row in the register names its group with status AGREED.

- **TG1 — Database access, paths and opening (20 findings; B).** Accepted principle: one governed database-access contract; fixed, explicit paths; read-only access for read-only work; a missing production database fails clearly rather than being silently created; ordinary opens do not run schema migrations; analytics is not an unconditional trading dependency; reads take no write lock; writer and concurrency rules are explicit. Qualification: "one database access layer" is a required consistency and control boundary, not a decision that every operation sits in one class or module; Phase 2 chooses the structure; A03-09, A03-10, A03-11 and A01-05 are preserved.
- **TG2 — Transactions, atomicity, failure propagation and connections (21 findings; B).** Accepted principle: atomicity for each business operation that must be all-or-nothing; named and observable storage failures; clear connection ownership and closure; no success indication after a failed write; reconciliation when a broker action succeeds but persistence fails. Qualification: a broker action cannot be made atomic with a local transaction, so such workflows need durable intermediate states, idempotency and reconciliation; no single giant transaction for long or cross-system workflows; Phase 2 sets the transaction boundaries and resumable state model; A03-13, A03-14 and the A01 group A input are preserved.
- **TG3 — WAL checkpoint maintenance (7 findings; A).** Accepted principle: truthful outcomes (done, busy, skipped with reason, failed); separate scheduled and manual behaviour with no silent skip; accurate schedule descriptions; each database maintenance target reported; a listed auto-fix must correspond to a real, implemented and tested check. A03-44, A03-45 and A03-02 are preserved.
- **TG4 — Schema constraints and data model (10 findings; B).** Accepted principle: explicit key, nullability and relationship rules; declared mutation policies enforced; history kept where required; constraint failures not treated as duplicates; cardinality and uniqueness defined where consumers depend on them. Qualification: no specific keys, indexes, table structures, cardinalities or history models are chosen in this round unless an agreed input already settles them; business meaning and data ownership come first, and schema design belongs to Phase 2; A03-03, A03-16 and A03-20 are preserved.
- **TG5 — Status vocabularies and state transitions (26 findings; B).** Accepted principle: authoritative status vocabularies and transition rules; guarded from-state transitions; detection of missing or stale target rows; shared definitions of the active, open and terminal sets; confirmed broker facts preserved; explicit ownership and clearing rules for latches. Qualification: "one place" means one authoritative definition and enforcement contract, not necessarily one runtime component; state machines are defined per business entity and workflow, without merging distinct order, trade, EOD or job states for uniformity; A03-17, A03-22, A03-28, A03-30 to A03-34 and related inputs are preserved.
- **TG6 — Time stamps and dates (11 findings; B).** Accepted principle: one authoritative time source consistent with the A01 decision; explicit time-zone semantics; consistent parsing, comparison and ordering; no accidental dependence on host-local time or database defaults; date filters that respect the stored semantics. Qualification: the storage representation (UTC, IST-offset ISO-8601 or another explicit form) is not decided in Phase 1; purpose and semantics first, representation chosen and validated in Phase 2; A03-43 and the A01 group D input are preserved.
- **TG7 — Unused tables, methods and code (10 findings; B).** Accepted principle: every retained table, method, file and job has a declared purpose, owner, producer and consumer relationship and life cycle; dashboards do not portray unwritten data as live. Qualification: the absence of a caller or writer is evidence, not by itself authority to delete or retire; whether an item is obsolete, planned, dormant, externally consumed or unused is determined first, and any retirement is an explicit Phase 2 decision after dependency and impact checks; A03-36 and A03-37 are preserved.
- **TG8 — Migrations and schema versioning (12 findings; B).** Accepted principle: controlled, versioned migrations for each database; one version authority per database; safe handling of missing or unreadable version markers; validated steps; data and counters preserved; truthful failure and stop behaviour; dry-run and status operations that do not mutate operational state. Qualification: changes spanning separate SQLite files cannot be one atomic transaction, so per-database atomic steps and a resumable or reconciliation contract for cross-database changes are defined; supported starting versions and mechanics are decided in Phase 2; A03-15, A03-23 to A03-27 and A01-05 are preserved.
- **TG9 — Failure visibility: logging, heartbeats, exit codes and dry runs (24 findings; B).** Accepted principle: attributable failure records; configured logging in every process; truthful exit codes and completion signals; success, partial completion, failure and missed execution distinguished; dry-run previews that represent the action accurately; the agreed end-of-day operational execution report. Qualification: a dry run must not change operational state or trigger the simulated action, while harmless preview output is permitted and defined; alerting once is done by bounded, deduplicated reporting, not by making alert delivery a precondition for recording the failure; A03-38, A03-45, A03-48, A03-50 and A02 V-13 are preserved.
- **TG10 — File persistence: atomic writes, locks and sentinels (25 findings; B).** Accepted principle: safe atomic replacement for state files; complete append records; ownership-aware locks and release; one authoritative configured path per state family; no silent fallback from unreadable state; sentinel recording independent of whether the notification channel is enabled. Qualification: the concrete atomic-write, durability and locking mechanisms are chosen in Phase 2 for the filesystem, process model and deployment; files are distinguished by persistence class (replaceable state, append-only evidence, logs, locks, markers, credentials); no separate credential or security investigation or disclosure is authorised; A03-48 and the relevant A01 and A02 inputs are preserved.
- **TG11 — Retention (13 findings; B).** Accepted principle: retention inputs validated before deletion; an explicit preservation rule per data family; capital-ledger records protected while dependencies remain; a database and its required sidecars treated as one retention unit. Qualification: no universal age rule and no requirement that every family rotate by trading date; each family needs its own purpose-based rule, stable selection key, dependency check and safe deletion rule; "never delete the newest copy" is a safety guard, not a complete policy; A03-07, A03-08, A03-46, A03-47 and A03-48 are preserved.
- **TG12 — Backups and restore (14 findings; B).** Accepted principle: a documented and tested restore procedure; verified independent off-machine protection for everything needed to restore; truthful backup and drill outcomes; coverage checks based on the actual schema and dependencies; declared and implemented cadence and retention consistent. Qualification: backup scope, destinations, cadence, retention, verification, recovery-point and recovery-time objectives are Phase 2 requirements; no provider, technology or cadence is assumed; a backup is not proven usable because a file exists, so restore verification tests the actual recovery path; A03-49, A03-50 and A03-51 are preserved.
- **TG13 — Descriptions and documents against code (6 findings; B).** Accepted principle: comments, docstrings, banners, labels and operational documents describe established behaviour accurately. Qualification: where a document states an intended behaviour that the code does not implement, the document is not changed automatically to match the defect; intended requirement and stale description are told apart first, the owner decides, and documentation and implementation inputs then agree; the A01 group J input is preserved.
- **TG14 — Queries and scripts against the schema (7 findings; B).** Accepted principle: schema-aware validation of queries, including automated tests against the schema versions they are expected to use; schema and query mismatches surface as failures, not as empty results; the agreed operator-recovery boundary is preserved (no unguarded bulk changes; recovery a distinct, authorised, confirmable and audited workflow); A03-12, A03-19, A03-41 and A03-42 are preserved. Qualification: the test coverage and supported schema-version matrix are defined in Phase 2; a static text search alone does not prove runtime compatibility.
