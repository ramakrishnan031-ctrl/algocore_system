## 2. Executive summary

- **Inventory.** At the baseline `config/` holds 51 tracked files, all YAML or CSV; 50 are A02's (30 YAML: 14 top-level files and 16 strategy files; 20 CSV), and with the eight modules and scripts the A02 set is 58 paths, all present. No discrepancy with the index was found (section 3).
- **One central loader for eight files.** `core/config_loader.py::load_all` (L2457 to L2516) reads exactly eight registered files: `system_config.yaml`, `broker_costs.yaml`, `broker_limits.yaml`, `slippage_model.yaml`, `scoring_weights.yaml`, `scan_webhook_map.yaml`, `chartink_scanners.yaml` and `nse_holidays_<year>.yaml`, the year taken once, at module import, from the host-local date (L2449). All eight are required; the load is atomic and returns one `AppConfig` with a SHA-256 of each file's raw bytes (`file_hashes`). There is no cache and no reload: each of the 26 non-test call sites in 21 files re-reads the files (sections 4 and 5).
- **The other 42 files are read by their own modules or not at all.** The 16 strategy files go through `strategies/loader.py` and `strategies/schema.py`; six other YAML files and the 20 CSV files are read directly by their consumers, without a central schema, or have no reader (sections 3 and 6).
- **Schema.** 65 pydantic models, all `extra="forbid"`; 458 fields, of which 289 have a code default; 97 validators. Pydantic runs in its default lax (coercing) mode; mapping-typed fields accept any keys; there is no cross-file validation; NaN and infinity pass most float fields; duplicate YAML keys are accepted, the last value winning. At the baseline the eight files conform by key and type; 38 key occurrences (24 distinct keys) are absent and take the code default (section 4).
- **The configuration auditor runs inside every load.** `SystemConfig`'s model validator runs `core/config_auditor.py` (groups A, C and G); a BLOCK finding fails the load, which `main.py` turns into exit 5, and WARN findings are logged by every process that loads (sections 4.2 and 7.3).
- **The key-usage validator is wired but inert.** `main.py` registers the leaf values of five of the eight sections (L2205; `core/config_validator.py` L179 to L183) and calls `validate_all(strict=False)` (L4164), but no non-test code calls the tracking method `get()`; INTERPRETATION: every registered key is reported as unaccessed and drift is never detected (section 7.4).
- **Change detection and snapshots cover the eight registry files only.** The boot compares the per-file hashes with the previous session's; a removed registry key is not reported (A01 C7d). The W0 snapshot stores the whole validated configuration as JSON with a key-substring redaction, de-duplicated per IST date and hash, with no unique constraint; it stores e-mail addresses, an IP literal and scanner URLs unredacted and logs the broker account identifier at INFO (section 7).
- **Strategy configuration.** 16 files, all conforming to the 41-field `StrategyConfig` (13 required); each omits 5 or 6 keys; 15 enabled, 1 disabled. The boot loads them twice; the cross-check against `scan_webhook_map.yaml` (S10) is never requested; a duplicate `name` would silently replace an earlier file (section 6).
- **Configured against code-effective values.** Of the 327 leaf keys of `system_config.yaml` (the items of its two lists of mappings counted by their keys; section 10.1), most reach a functional consumer, but several configured values do not reach the code that they describe: the entry-gate liquidity settings, the three `live_feed` keys, `smart_tgt.enabled`, `eod_squareoff.auto_resume_kill_switch` and `broker.primary`; two exit buffers are bypassed by constants on some paths; and the 33 Telegram notifier call sites in 31 files use only the on/off switch, read directly from the file (sections 5.4 to 5.6 and 10).
- **Environment.** `.env.example` declares 20 key names; the code makes 57 environment reads, 3 writes, 22 `load_dotenv` calls and 2 child-process pass-throughs; 20 names that the code reads (and 4 supplied by the operating system) are absent from `.env.example`, and one declared name is never read (section 9).
- **The TEMP-revert script** is not declared or invoked anywhere in the code, cron or deployment files; a deployment guide tells the operator to run it. INTERPRETATION (from a re-implementation of its regular expressions, the script not run): at the baseline it would treat the word "ATTEMPT" as a TEMP marker and, with `--apply --confirm`, would change `risk.daily_loss_limit_pct` from the file value 0.03 to 0.05 and replace the inline comments of all six matched lines (five of them keeping their values), writing in place without a backup (section 8).
- **Existing records.** Of 234 configuration claims in the five records, 181 match the baseline code, 17 match partly and 8 differ; the rest are outside A02 or not checkable from code (Appendix A).
- **Runtime.** Which configuration, values and environment were in force, and whether any of these paths ran, is UNKNOWN / NOT ESTABLISHED (section 13.3).

## 15. Questions for Rama about intent

The code shows what is implemented; these questions concern what was intended, where the admitted intent sources conflict or are silent. They are not decisions, and none is answered by this STUDY.

1. The daily loss limit: the file value of `risk.daily_loss_limit_pct` is 0.03, while the revert script's table holds 0.05 as the "prod" value and the deployment guide tells the operator to run the script when switching to Live. Which value was intended for Live, and was the script meant to be run?
2. The entry-gate liquidity check: the file says `liquidity_check_enabled: true` with spread and depth limits, but the values are not passed and the check is off in the code. Was the check meant to be active?
3. `smart_tgt.enabled` and `eod_squareoff.auto_resume_kill_switch`: both are described as switches; the code never reads `auto_resume_kill_switch`, and uses `smart_tgt.enabled` only for an alert text. Were they meant to control the behaviour?
4. Webhook authentication: the comment at `system_config.yaml` L332 to L334 says the all-interfaces bind "relies on require_hmac=true", while the value's own comment (L336) sets it false because Chartink cannot sign payloads and uses a query token instead. Which was intended?
5. The Telegram settings in `system_config.yaml` (retries, rate limit, channels, e-mail fallback): were they meant to apply to the notifiers built through `from_env` or `from_config` (scripts, cron jobs, the control tower, the daily report and the boot's invalid-strategy alert, `main.py` L331), which use their own defaults?
6. The strategy files and the locked decisions S5, S6 and S13 (every field declared; ATR methods and a 14:30 end for the positional strategies; R:R 2.0 for most intraday strategies): which governs, the files or the decisions?
7. `broker.primary`, `broker.fallback`, `broker.fallback_enabled` and `broker.multi_account_mode`: were broker selection, a fallback broker or multi-account operation intended for Live?
8. The holiday calendar: A01 R9(a) (open, narrowed) and R10 already cover the year-end behaviour and the IST clock (the IST intent is documented). A02 asks only: was `load_all`'s requirement of the current year's file, with no other year read (exit 5 when it is missing), the intended year-end behaviour, and was the loader's host-local year meant to differ from the documented IST clock?
9. Sensitive data in tracked configuration (account identifiers and names, e-mail addresses, an IP literal, an SSH fingerprint, home paths): was keeping these in the repository and in the snapshot intended?
10. The key-usage validator: was it meant to be fed by every consumer (so that unused keys and drift are found), or was the non-strict warning the intended end state?
