### 2.2 The single authentication decision, `_authenticate`

P02-S015. FACT (`signals/webhook_receiver.py` L298 to L354; every line from commit `e8ec604`, 25-Jul-2026, "refactor(webhook): C6 -- one auth decision, one call site per route", HISTORICAL): `_authenticate(hmac_payload)` returns `(True, "")` or `(False, reason)` in this order:
- (a) L330 to L331: if `self._secret` is empty or `None`, the request is authenticated with no check. The comment (L326 to L329, HISTORICAL) calls this a test-only path because the secret is a required start-up secret.
- (b) L333 to L334: it reads the request header `X-Webhook-Signature` (default empty) and the URL query parameter `token` (default empty).
- (c) L336 to L342: if the header starts with the exact, case-sensitive text `sha256=`, it computes HMAC-SHA256 keyed with `self._secret.encode()` over `hmac_payload` (L337 to L339), takes `hexdigest()`, and compares it with the header text after the 7-character prefix (`sig_header[7:]`) using `hmac.compare_digest` (L340). Mismatch: `(False, "HMAC signature mismatch")`; match: authenticated. The token is not consulted in this branch.
- (d) L343 to L349: otherwise, if `require_hmac` is true: `(False, "HMAC signature required (require_hmac=True); token param is not accepted")`.
- (e) L350 to L353: otherwise, if a `token` value is present, it is compared with the secret by `hmac.compare_digest(token_param, self._secret)` (L351). Mismatch: `(False, "Invalid token")`; match: authenticated.
- (f) L354: otherwise `(False, "Missing auth: provide X-Webhook-Signature header or ?token= param")`.

P02-S016. FACT (P02-S015; `config/system_config.yaml` L336): at the file values (`require_hmac: false`) a request authenticates either with a correct `sha256=` signature over the signed payload or with a `token` query parameter equal to the secret. A signature header that does not begin with exactly `sha256=` is treated as absent, and the request falls through to the token branch.

P02-S017. FACT (L336 to L342 return before L350): a request that carries a `sha256=` header which does not match is rejected even when it also carries a correct token. The comment at L346 to L347 (HISTORICAL) states this as intended ("A bad signature is NOT rescued by a valid token either").

P02-S018. FACT (L340, L351): both comparisons of secret-derived material use `hmac.compare_digest`; no `==` comparison of the secret, the token or the signature exists in the file. Current external context (read 17-Nov-2026; Python 3.11 `hmac` documentation): `compare_digest(a, b)` returns "a == b" using "an approach designed to prevent timing analysis by avoiding content-based short circuiting behaviour"; "a and b must both be of the same type: either str (ASCII only, as e.g. returned by HMAC.hexdigest()), or a bytes-like object"; and "If a and b are of different lengths, or if an error occurs, a timing attack could theoretically reveal information about the types and lengths of a and b—but not their values." INTERPRETATION: both calls pass two `str` values, and the receiver does not check that the incoming token or signature text is ASCII; incoming text with a non-ASCII character is outside the documented contract. Current external context (read 17-Nov-2026, in the check; CPython 3.11 published source): `Lib/hmac.py` binds `compare_digest` to `_hashlib.compare_digest` when the `_hashlib` module imports, otherwise to `_operator._compare_digest`; both C implementations (`Modules/_hashopenssl.c`, `Modules/_operator.c`) raise `TypeError` with the message "comparing strings with non-ASCII characters is not supported" when either `str` argument is not ASCII. INTERPRETATION: on a 3.11 interpreter, a `token` value or a signature text after `sha256=` that holds a non-ASCII character raises `TypeError` instead of returning false. On `/webhook` the call runs inside the `try` of L510, so the request ends in the generic 500 of L525 to L528 with a `webhook_audit` row (section 5, row 29); on `/health` it reaches the Flask 500 handler of L410 to L413 (row 8; see P02-S073). The Python version installed on the legacy machines is UNKNOWN / NOT ESTABLISHED (P02-S008), so this holds only for an interpreter that behaves as the 3.11 source read.

P02-S019. FACT (L480, L511, L547): on `/webhook` the signed payload is the raw request body exactly as read by `request.get_data()` (L480), passed unchanged to `_process_request` (L511) and to `_authenticate(raw_body)` (L547). No timestamp, nonce, expiry or request identifier is part of the signed material or checked by `_authenticate`. The token is a fixed value carried in the URL. INTERPRETATION: a copy of an accepted request (signed or token-bearing) authenticates again if re-sent; repeats are then subject only to the later controls (deduplication and in-flight claims, P03; expiry, section 4).

P02-S020. Current external context (read 17-Nov-2026; Python 3.11 `hmac` documentation): `hexdigest()` returns "a string twice the length containing only hexadecimal digits"; the letter case is not stated on the page read. INTERPRETATION: because the comparison is exact equality, a signature whose hexadecimal letters differ in case from `hexdigest()`'s output would not match.

P02-S021. Current external context (read 17-Nov-2026; Werkzeug 3.1.x): `Request.args` is "The parsed URL parameters (the part in the URL after the question mark)", an `ImmutableMultiDict` by default, and for a `MultiDict` "the standard dict access methods will only return the first value for a key". INTERPRETATION: when a URL carries several `token` parameters, only the first is compared (L334 uses `request.args.get`).

P02-S022. FACT (L333 to L334 are the only authentication reads): the secret is accepted only as the `token` URL query parameter or as the HMAC key behind the `X-Webhook-Signature` header. No body field, cookie, `Authorization` header or client certificate is consulted. INTERPRETATION (with A02 STUDY section 9.4, whose INTERPRETATION, made with `.env.example` L49, is that the token is held in the Chartink-side webhook URL, which is not in the repository; A02 RECONCILED TOPIC RECORD section 4.7 records only that the webhook-secret name is declared in the template and that `core/config_loader.py` has no webhook-secret field): for Chartink requests the token travels in the configured webhook URL.

### 4.3 JSON body: malformed, empty, non-object, duplicate keys, unexpected fields

P02-S047. FACT (L586 to L596): the raw bytes are parsed with `json.loads(raw_body)`; `json.JSONDecodeError` or `ValueError` gives 400 with `{"error": "Malformed JSON: <exception text>"}` and a WARNING log of the first 500 bytes (P02-S034); a parsed value that is not a JSON object gives 400 with `{"error": "Request body must be a JSON object"}`. INTERPRETATION: an empty body (not a valid JSON document) and a body in an unsupported encoding both end in the 400 of L593; neither reaches the field checks.

P02-S048. ### 4.6 Timestamps: `triggered_at`, `received_at` and the expiry check

P02-S055. FACT (L635 to L662; commits `31a03c7`, 28-Apr-2026, "parse Chartink triggered_at format (HH:MM am/pm)", and `0a734e4`, 13-May-2026, "FIX-022 timezone-aware triggered_at parsing", HISTORICAL): `triggered_at` is converted with `str(...)` and stripped (L637), so any JSON type is accepted as text (`null` becomes the text `None` and fails the parse). Three formats are tried in order: `%Y-%m-%d %H:%M:%S`, `%I:%M %p`, `%H:%M` (L640). For the two time-only formats the date is the IST date of `now`, taken by `now_ist()` at L581 before the parse, with seconds set to 0 (L643 to L647). A parsed value without a time zone is given the IST zone by `replace(tzinfo=ist_timezone())` (L652 to L653): the text is taken to be IST, with no conversion. No format carrying a zone or offset, an ISO `T` separator or fractional seconds is accepted. A value matching no format gives 400 with `{"error": "Invalid triggered_at; expected HH:MM am/pm or YYYY-MM-DD HH:MM:SS"}`.

P02-S056. FACT (`core/time_authority.py` L58 to L59, L94 to L104; A01's file, interface only): `now_ist()` returns `datetime.now(tz=_IST)` and `ist_timezone()` returns `_IST`, a fixed `timezone` of UTC+05:30 named "IST"; both values are therefore time-zone aware.

P02-S057. Current external context (read 17-Nov-2026; Python 3.12 `datetime` documentation): `strptime` raises `ValueError` "if the date_string and format can't be parsed"; `%p` is the "Locale's equivalent of either AM or PM" (examples "AM, PM (en_US)"), depends on the current locale, and "only affects the output hour field if the `%I` directive is used to parse the hour"; "the leading zero is optional for formats `%d`, `%m`, `%H`, `%I`, `%M`, `%S`". The page does not say whether `%p` matches case-insensitively. Current external context (read 17-Nov-2026, in the check; CPython 3.12 published source `Lib/_strptime.py`): the AM and PM texts are taken from `time.strftime("%p", ...)` in the current locale, lower-cased and stripped (`LocaleTime.__calc_am_pm`), and every `strptime` pattern is compiled with `IGNORECASE` (`TimeRE.compile`). INTERPRETATION: a one-digit hour such as Chartink's sample "2:34 pm" (Chartink page, read 17-Nov-2026) is within the documented `%I` behaviour, and, on an interpreter that behaves as the 3.12 source read, letter case does not prevent a match; whether "pm" matches still depends on the AM and PM texts of the process's locale, and both the locale of the legacy process and the installed Python version are UNKNOWN / NOT ESTABLISHED (corrected in the check: the draft left the case question open). HISTORICAL: the unit tests post lower-case times such as "10:30 am" (`tests/unit/test_webhook_receiver.py` L1594, L1652, L1699), evidence of the expectation only; not run.

P02-S058. FACT (L677 to L679, L916 to L926): `received_at` is `now_ist()` at L677, after the parse; per symbol, `_process_signal` takes `now_ist()` again (L919) and computes `age_sec = (now - triggered_at).total_seconds()` (L924); only `age_sec > expiry_sec` gives the per-symbol status `EXPIRED` (L925 to L926), with `expiry_sec` from `signal_queue.expiry_sec` (L679; 600 in `config/system_config.yaml` L127). A timestamp later than now gives a negative age and is not rejected; there is no future-time check and no check that a full-format date is today. INTERPRETATION: a time-only value later in the day than the moment of receipt is accepted as not expired; a full-format value from a past day is caught only by the age check. The expiry rules as a whole are P04's (direction question 17); the deduplication bucket that also uses `triggered_at` (L952) is P03's.

P02-S075. (added in the check) FACT (L957 to L961, L976): the `expires_at` stored with each inserted signal is `received_at + expiry_sec`, while the receiver's own age check measures from `triggered_at` (L924; P02-S058). `triggered_at`, `received_at` and `expires_at` are stored as the `isoformat()` texts of the IST-aware values (L958 to L961). ### 4.8 Body size

P02-S063. FACT (L251, commit `39110d8`, 16-May-2026, "Phase 17 audit fixes batch"; L250 from the initial commit `bcf03b5`): the Flask app sets `MAX_CONTENT_LENGTH` to 1,048,576 bytes ("1MB hard limit prevents OOM", HISTORICAL comment), and `TESTING` to false (L250). Current external context (read 17-Nov-2026; Flask 3.1.x configuration): `MAX_CONTENT_LENGTH` is "The maximum number of bytes that will be read during this request. If this limit is exceeded, a 413 RequestEntityTooLarge error is raised"; `TESTING`, when enabled, makes exceptions propagate "rather than handled by the app's error handlers". Werkzeug 3.1.x: `get_data()` "loads the full request data into memory" and "This is only safe to do if the max_content_length is set"; a 413 returned before the whole request is read may reach the client as a connection reset.

P02-S064. INTERPRETATION (basis: P02-S063; L479 to L510): `request.get_data()` (L480) runs before the shutting-down check, before the per-IP limiter and outside the `try` of L510. A 413 raised there leaves `_handle_webhook` before any `_write_audit` call, so an oversized request writes no `webhook_audit` row, takes no limiter token, and is answered by Flask's default 413 response (Flask 3.1.x error handling, read 17-Nov-2026: "the default HTTP exceptions return simple exception pages"); the receiver's 500 handler does not apply to it. Because waitress has already received the whole body before Flask runs (P02-S065), the Werkzeug note on a connection reset before the request is fully read (P02-S063) is not expected to apply under the pinned waitress (INTERPRETATION).

P02-S065. FACT (`main.py` L3991 to L3996) and current external context (read 17-Nov-2026; waitress 3.0.2 arguments): `main.py` sets no waitress size limit, so waitress's defaults apply: `max_request_body_size` 1,073,741,824 bytes ("Maximum number of bytes in request body"), `max_request_header_size` 262,144 bytes ("Maximum number of bytes of all request headers combined"), and a temporary file for pending input larger than `inbuf_overflow` (524,288 bytes). INTERPRETATION: for request bodies the Flask limit of 1 MiB is the lower limit; header size is bounded only by waitress's default. Current external context (read 17-Nov-2026, in the check; waitress 3.0.2 design page and tagged source): a task is scheduled "When a channel determines the client has sent at least one full valid HTTP request" (design page); in the source, `HTTPChannel.received` queues the request and calls `server.add_task` only once `request.completed` is true (`channel.py`), and `HTTPRequestParser.received` sets `completed` for a request with a body only when the body receiver has completed, the body being held in an `OverflowableBuffer(self.adj.inbuf_overflow)` (`parser.py`). INTERPRETATION (corrected in the check: the draft left this UNKNOWN): at the pinned waitress version, the whole body, up to waitress's own 1 GiB limit, is received and buffered (in memory, or in a temporary file above 512 KiB) before Flask runs; the Flask 1 MiB limit then stops the application from reading the buffered body into memory (`get_data()`, L480), but it does not stop the upload or waitress's buffering. Whether the installed waitress is the pinned 3.0.2 is UNKNOWN / NOT ESTABLISHED (P02-S008). Threads and connection limits are P01's.

## 6. Points the AUDIT may examine (neutral)

1. At the file values, authentication rests on one shared secret, accepted as a URL query token; the signed alternative covers the raw body only, with no timestamp or nonce; `/health` accepts the same token and a signature that is constant for a given secret (P02-S015 to P02-S019, P02-S025).
2. The A06 side of A02-13 and X-01: the code facts behind the bind comment's premise, with the history OPEN as recorded (P02-S036 to P02-S042).
3. No source-address control exists in the code, and `remote_addr` is the immediate peer when waitress has no trusted proxy (P02-S029, P02-S030).
4. The token and signature comparisons pass incoming text that may fall outside `compare_digest`'s documented ASCII-only contract; in the CPython 3.11 source such text raises `TypeError`, so the request ends in a 500 rather than a 401 (P02-S018).
5. Raw body text is logged on every 400 path without the storage sanitiser; a UTF-16 or UTF-32 body would defeat the sanitiser's matches in the stored copy (P02-S034, P02-S050).
6. `/webhook` returns granular authentication reasons, `/health` a uniform one (P02-S035).
7. Kill-switch, backpressure and entry-window refusals come before payload validation (P02-S043).
8. The strategy written for a signal is the scanner name; the map's `strategy` value is not read (P02-S045).
9. The FIX-074 cast acts on six keys that the receiver never uses; an `OverflowError` in any of five of them, or a non-string `scan_name`, ends the request in a 500 rather than a 400 (P02-S046, P02-S051, P02-S052).
10. Repeated JSON keys and `NaN` or `Infinity` literals are accepted without notice (P02-S048).
11. Unexpected fields are accepted, and the whole sanitised body is stored in each `signals` row that the request inserts (P02-S049).
12. `triggered_at` text is taken as IST; time-only values take the IST date of receipt; future times are not refused; `am`/`pm` parsing depends on the AM and PM texts of the process locale (letter case is ignored in the CPython 3.12 source, not in the documentation) (P02-S055 to P02-S058).
13. Price items "nan" and "inf" pass the positive-price check; there is no bound or tick check (P02-S061, P02-S062).
14. No instrument check on symbols at the receiver; symbols keep their case on an alias miss (P02-S059).
15. The oversize path (413) is answered before the shutting-down and limiter checks and writes no audit row; at the pinned waitress the whole body, up to 1 GiB, is received and buffered before the 1 MiB Flask limit applies; header size is bounded only by waitress's default (P02-S064, P02-S065, P02-S074).
16. The `webhook_audit` counts are 0 and 0 for any non-200 answer, including mixed 503 batches; the end-of-day 200 counts all symbols as accepted (P02-S067; P03).
17. The docstring's response-code and status lists differ from the code (P02-S071).
18. The 503 retry contract assumes a sender retry that the Chartink page does not describe (P02-S072).
19. The post-start self-check counts a 401 as reachable (P02-S026).
20. `OPTIONS` requests are answered by Flask without the limiter, authentication or audit (P02-S027).
21. `excluded_symbols` applies only to the intraday path, not to the end-of-day route (P02-S060).
22. The receiver's 500 handler answers only while Flask debug mode is off; nothing in the repository sets or checks `FLASK_DEBUG` (P02-S073; added in the check).
23. The stored `expires_at` counts from receipt, while the receiver's age check counts from `triggered_at` (P02-S075; added in the check).
