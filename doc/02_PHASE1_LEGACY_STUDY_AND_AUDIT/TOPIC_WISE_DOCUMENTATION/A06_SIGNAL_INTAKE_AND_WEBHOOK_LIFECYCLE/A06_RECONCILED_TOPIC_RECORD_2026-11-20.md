## Part A — Study findings (reconciled)

## 3. Signal intake in brief

From STUDY 2, with the AUDIT's refinements applied.

One Flask app with two routes, `POST /webhook/<scanner_name>` and an authenticated `GET /health`, is served by waitress in the daemon thread `webhook-server`, with a fixed pool of eight worker threads and a connection limit of 100, on all interfaces, port 5000 (repository values). The receiver is built at boot before the processor, starts its in-flight sweeper inside its constructor and is reachable only once the server starts, last; its `stop()` only sets two events, and the server is never stopped. At the repository value `require_hmac: false` a request passes with a correct `sha256=` signature over the raw body or with a `token` query parameter equal to `WEBHOOK_SECRET`, which start-up requires; nothing else in the code restricts who may connect. The scanner name is the URL path segment, which must be a key of the scanner map; the body must be JSON with `stocks`, `trigger_prices` and `triggered_at` (taken as IST); the kill switch, back-pressure and the entry window are checked before the body is parsed; end-of-day alerts go to the PB-01 capture worker (A18's) and skip those gates (STUDY 2, 3, 4).

Three duplicate layers with different keys and windows (a per-symbol in-flight claim, a 300-second TTL cache, a stored fingerprint per five-minute slot and day) apply per symbol, and one per-IP token bucket (60, then 5 per second) per request; a request-level 503 fires at a depth of 240 and a per-symbol `QUEUE_FULL` at 300. The signal event is one `signals` row (status `QUEUED`, the scanner name also written as the strategy), committed before a 5-tuple is put on an in-memory FIFO queue of 300 that only the processor drains; the dispatcher moves each item at once into an unbounded executor queue for five workers. Each worker writes `PROCESSING`, re-checks the kill switch and the window, rejects signals older than 600 s from `triggered_at`, applies the shadow guard, resolves the strategy from the scanner map, runs the strategy-level gates and calls A07's screening; where A06 ends and A07 begins (at the dequeue, or at the screening call) is OPEN FOR RAMA. After the handoff, at the interface: price, sizing, risk and reservation (A09), the `INTRADAY SIGNAL` alert (A14), the entry throttle (A06's module: at most one admit per 20 s, three per 60 s and one per symbol per 300 s at the repository values, counted at the admit before `place()`), placement (A10) and the S&R, V3 and allocator hooks (A08, A18); A04's limiter is never called by A06 code under `main.py` (STUDY 2, 5, 6, 8, 9, 13).

Sixteen scanner keys, each equal to its strategy name, carry screener URLs of one name-derived pattern [refined: section 6, row 5: the repository's form is also a form real Chartink addresses take; the files' own "placeholders" note stands], used only by an outbound reachability check (a GET with 2xx success, a warning only at boot and exit code 1 in the operator script), which shows nothing about whether alerts reach the receiver. A06 writes `signals`, `webhook_audit` and the `pb01_capture` heartbeat; the audit counts and the stored rows do not reconcile on several routes; rows left `QUEUED`, `QUEUE_FULL`, `PASSED` or `RESERVED` are never reaped; `/metrics` reports the queue as 0, so A20's back-pressure check always passes. Nothing here says what ran in production: every runtime fact is UNKNOWN / NOT ESTABLISHED (STUDY 1.6, 2, 10, 14).

The most important facts:

- FACT and INTERPRETATION: at the repository values authentication rests on one shared secret, as a URL token or as the HMAC key over the raw body, with nothing that binds a request to a time, so a copy of an accepted request authenticates again; the code has no source-address control; the documented network path (a loopback bind behind a TLS proxy) conflicts with the configured all-interfaces bind and with the receiver's address handling, and which path production had is UNKNOWN / NOT ESTABLISHED; A02-13's history stays OPEN (STUDY 4, 17 point 4; WA-01, WA-13, WI-09). [refined: section 6, row 1: `require_hmac` is false in the repository history from `a1704df`, 28-Apr-2026, not from 02-Jul-2026 (WA-02, a records observation).]
- FACT and INTERPRETATION: the in-flight heartbeat is never connected (`main.py` passes no `in_flight_heartbeat_fn`), so the sweeper evicts every claim older than 60 s, whether or not a worker still holds it, and logs it as a stalled worker; a second signal for the symbol can then pass the claim, and because a release is keyed by symbol, not signal, a late release can free a newer signal's claim (STUDY 3, 5; WI-01, WD-08).
- FACT and INTERPRETATION: an exception raised inside the fingerprint-conflict (`IntegrityError`) handler (the read at L987, or a re-queue `put_nowait` raising other than `queue.Full`), or between the claim and the INSERT's `try`, leaves the in-flight claim and the cache key held, skips the batch's later symbols and answers 500; whether it occurred is UNKNOWN / NOT ESTABLISHED (STUDY 5; WD-01, WD-02). [refined: section 6, row 2: the STUDY's provisional KNOWN DEFECT P03-S034 is not confirmed: WD-01 is ISSUE, KNOWN DEFECT considered and not given, condition (a) not established.]
- INTERPRETATION: the receiver's back-pressure (the 503 at 240 and `QUEUE_FULL` at 300) measures only the dispatcher's hand-off buffer; while the dispatcher runs, a backlog builds in the executor's unbounded work queue that back-pressure never sees, its only limit the age check; no A06 code supplies the live depth to the port-8080 `/metrics`, whose queue fields stay 0 (STUDY 5, 6, 14; WD-10, WD-13).
- FACT and INTERPRETATION: a `QUEUE_FULL` row recovers only through a sender's retry, which Chartink's pages do not describe; a failed `QUEUE_FULL` mark and a stop leave `QUEUED` rows with no queue item, whose retries are refused and which nothing re-reads; a stop also leaves rows `PROCESSING`, `PASSED`, `RESERVED` or parked (STUDY 5, 6, 8; WD-05, WA-09, EV-08).
- FACT: `pipeline_timeout_sec: 30`, stated as a "hard per-signal processing deadline", is read by nothing, so a worker blocked in a call holds one of the five slots without limit; the processor's `stop()` waits without limit for every submitted signal, each of which runs intake, screening, sizing, risk and reservation before the pre-placement `SHUTDOWN` reject (STUDY 6; PQ-01, PQ-02; A01 C18's A06 side).
- FACT and INTERPRETATION: every processor status write replaces the stored status and reason, with no check of the current status and no time stored; a failing status write can leave a status that misdescribes the signal, and a reservation release that follows a failing write is skipped (STUDY 8; EV-01, EV-02, EV-03).
- FACT: the receiver writes the URL path segment into both `signals.scanner` and `signals.strategy`; the strategy is first resolved from the scanner map inside the processor and is never written to the row; the two coincide in the repository map, where every key equals its strategy (STUDY 3, 7; WI-17).
- FACT and INTERPRETATION: the entry throttle records an entry at the admit, before `place()`, and is never told the outcome; the reservation, `RESERVED` and the `INTRADAY SIGNAL` alert precede the admit on all three paths, so a throttled signal has been announced; a FIX-069 rate-limit retry meets the throttle measured from its own first admit (STUDY 9; ET-01, ET-02, ET-03).
- KNOWN DEFECT (provisional; A06's classification of its own side of A05 IN-08): `_sector_for` asks the instrument cache for `sector_for` and `get_sector`, which the cache does not define, so it returns "UNKNOWN" for every symbol; A05's record of IN-08 is unchanged (STUDY 7; PQ-07). [refined: section 6, row 3: the STUDY left conditions (c) and (d) open; PQ-07 establishes both.]
