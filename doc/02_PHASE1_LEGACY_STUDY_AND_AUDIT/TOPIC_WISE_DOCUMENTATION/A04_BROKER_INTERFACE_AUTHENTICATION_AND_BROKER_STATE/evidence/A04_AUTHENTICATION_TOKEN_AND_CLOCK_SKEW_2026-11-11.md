### 2.2 The token file: path, fields, reader and validity rule

- P07-S013. FACT: `load_token(token_path)` opens the file as UTF-8 and returns `json.load(fh)`; it returns `None` on `OSError` or `json.JSONDecodeError` (L53 to L57). It does not check the type or the fields of the parsed value.
- P07-S014. INTERPRETATION (Python semantics): a missing file (`FileNotFoundError`), a directory or an unreadable file (other `OSError` subclasses) and a non-JSON file all give `None`; a file that is not valid UTF-8 raises `UnicodeDecodeError` (a `ValueError`, not caught by L56) out of `load_token`; a file that holds valid JSON that is not an object (a list, a string, a number, `null`) is returned as that value (or `None` for `null`), and the caller's next field access fails with `TypeError` or `AttributeError`.
- P07-S015. FACT: `is_token_valid(account_id, token_path)` returns True only if `load_token` returned a value, the value's `account_id` equals the argument, its `date` equals today's IST date in ISO form, computed as `datetime.now(ist_timezone()).date().isoformat()`, and its `access_token` is non-empty after `strip()` (L69 to L77). It reads no other field: `broker`, `api_key`, `saved_at` and `expires_at` are not checked.
- P07-S016. INTERPRETATION (Python semantics): the three conditions are joined by `and` and short-circuit; if the file's `account_id` and `date` match but `access_token` is present with a non-string JSON value (for example `null`, a number or a list), `token.get("access_token", "")` returns that value and `.strip()` raises `AttributeError` out of `is_token_valid` (L76); a parsed value that is a list, string, number or boolean raises `AttributeError` at L74; a top-level JSON `null` gives `None` from `load_token` and `is_token_valid` returns False at L70 to L71.
- P07-S017. FACT: the validity rule is a calendar-date rule: a token saved on an IST date is "valid" for the whole of that IST date and invalid from 00:00 IST of the next date, whatever the broker says. Nothing in `is_token_valid` asks the broker.
- P07-S018. FACT: `save_token(account_id, broker, api_key, access_token, token_path=_DEFAULT_TOKEN_PATH)` (L132 to L176) creates the parent directories (L144), sets the parent directory's mode to 0o700 and ignores an `OSError` (L148 to L151), computes `expires_at` as 05:00 IST today, moved to 05:00 IST tomorrow when that time is not later than the current time (L152 to L155), and writes one JSON object with the fields `account_id`, `broker`, `access_token`, `api_key`, `date` (IST date), `saved_at` and `expires_at` (both ISO) (L157 to L165) through `os.open(token_path, O_WRONLY | O_CREAT | O_TRUNC, 0o600)` and `json.dump(..., indent=2)` (L170 to L172), then sets the file mode to 0o600 and ignores an `OSError` (L173 to L176). HISTORICAL: the permission lines are the C-4 change of `dd4f3f4` (2026-07-08; comments L145 to L147, L166 to L169).
- P07-S019. FACT: the write is in place: there is no temporary file, rename, lock or `fsync`. A03 records this as G-11 (ISSUE; FACT; INTERPRETATION; KNOWN DEFECT not given; owners A03 for the write discipline and A04 for the token life cycle). A04's side: the readers of the same path in a live trading process are `main.py` L2362, L2547 and L2553 at start (section 3) and, after start, the health endpoint's `_check_token` (`scripts/healthcheck_server.py` L36 to L46, A15), which runs inside the trading process in the health-server thread that `main.py` starts at L4074 to L4082 (module docstring HC2, L10) and reads the file through `load_token` and `is_token_valid` on every GET /health (L93; P07-S224); the paper-only reads (`main.py` L413, L499) and the interactive reads (L1881 to L1891, unreachable, A01 C1) are not live readers; outside the process, the scripts listed in section 10. INTERPRETATION (as G-11): a reader that opens the file between the truncate and the end of the write sees an empty or partial file, and `load_token` returns `None` for it (L56 to L57).
- P07-S020. FACT: no code in the trading process uses `expires_at` for a decision; the only non-test reader of the token file's `expires_at` found by `git grep` is `scripts/healthcheck_server.py` `_check_token` L44 (A15), which runs inside the trading process (health-server thread started by `main.py` L4074 to L4082) and only copies the value into the /health payload (P07-S224); the other `expires_at` hits in non-test code concern other records (for example the copy-token records of `scripts/copy_gate.py` L124 to L140 and `scripts/security_monitor.py` L600 to L604). `saved_at` is read only by `main.py` L1887, inside the interactive helper (unreachable, A01 C1), for a printed message.

### 2.3 Token creation: the exchange and the login flow

- P07-S022. FACT: `exchange_request_token(api_key, api_secret, request_token, timeout_sec=10.0)` computes the SHA-256 hex digest of the concatenation of the API key, the request token and the API secret (L100 to L102), and POSTs the form fields `api_key`, `request_token` and `checksum` to the session-exchange URL with a 10-second timeout (L104 to L112). A non-200 status raises `RuntimeError` with the HTTP status and the first 200 characters of the response body (L114 to L117). The access token is taken from `payload["data"]["access_token"]` or, failing that, `payload["access_token"]` (L119 to L120); if neither is present it raises `RuntimeError` (L121 to L124). Network failures propagate from `requests.post` (docstring L96 to L98).
- P07-S023. INTERPRETATION (Python and requests semantics): a 200 response whose body is not JSON makes `resp.json()` raise (L119); a 200 response whose `data` member is JSON `null` makes `payload.get("data", {}).get(...)` raise `AttributeError` (L120). Neither is caught inside the function.
- P07-S024. FACT: `run_login_flow(account_id, broker, api_key, api_secret, token_path=_DEFAULT_TOKEN_PATH, input_fn=input, open_browser=True)` (L183 to L232) opens the login URL, built with the API key, in a web browser (L211 to L214), prints instructions to log in with user id, password and TOTP from the Kite app and to copy the `request_token` from the redirect URL (L216 to L221), reads the request token from `input_fn` (L222), exchanges it (L224 to L225), and on any exception from the exchange prints "Login failed: <exception>" and calls `sys.exit(1)` (L226 to L228). It then calls `save_token` outside the `try` (L230), prints a success line naming the account (L231) and returns the access token (L232).
- P07-S025. INTERPRETATION: token creation in this file needs a person at a browser and a keyboard (L211 to L222); it is not a headless path. An `OSError` from `save_token` (L230) is not caught and propagates to the caller.

FACT: `_cli_main(argv=None)` (L239 to L284) takes `--account` (required) and `--token-path` (default the token path) (L244 to L252), puts the repository root on `sys.path` (L255), loads `config/accounts.csv` (relative path) through `AccountRegistry.load` and selects the row with `registry.get(args.account)` (L256 to L259); a `KeyError` prints "Account ... not found in accounts.csv" and returns 5 (L260 to L262); any other exception prints "Error loading accounts.csv" and returns 5 (L263 to L265). ## 7. Clock skew: `get_server_time`, the Date-header hook and `broker/clock_skew_probe.py`

### 7.1 The broker clock reading: `_install_date_header_hook` and `get_server_time`

- P07-S108. FACT: `ZerodhaAdapter.__init__` sets `self._last_response_date = None` and calls `_install_date_header_hook()` (L450 to L454). - P07-S109. INTERPRETATION (requests semantics; library outside the admitted repository): the hook runs for every response on the client's session, from whichever thread made the request: adapter calls, the token monitor's direct `profile()` calls and any other direct use of the same client (A01 C38a: one client shared by several threads). `_last_response_date` is one attribute with no lock.
- P07-S110. FACT: `get_server_time()` (L1688 to L1728) returns `now_ist()` in paper mode (L1709 to L1710). HISTORICAL: `53e61e2` (2026-04-26, D.3) moved the call from `kite.margins()` to the quote bucket (docstring L1698 to L1703).
- P07-S111. FACT: the docstring's live-mode description, "then returns now_ist() after the round-trip ... - P07-S112. INTERPRETATION: (a) the returned value is a bare `datetime`, so a caller cannot tell a broker Date-header reading from the local-clock fallback; with the fallback the measured skew is about zero and the call only confirms that the broker answered; (b) the HTTP Date header has a resolution of one second, so a reading carries an error of up to about one second, plus any asymmetry of the round trip; (c) a response to another thread's request on the same session, arriving between L1715 and L1726, can supply the value (still a broker Date header, from a slightly different moment).

### 8.2 Which code detects each token fault, what follows and what is observed

- P07-S130. FACT: an expired token (calendar date) is detected locally, in the trading path, only by the start gate (`main.py` L2547, through `scripts/zerodha_login.py` L72 to L77), and only if the broker accepted the token at the first broker call; the result is exit 6 with CRITICAL "Token missing or expired for <account>". The health endpoint's `_check_token` also applies the date rule on each GET /health, but only reports the result (/health 503; P07-S224). A token the broker rejects at start is detected by the startup clock check and ends with exit 3 under the label `clock_skew` (A01 C8).
- P07-S131. FACT: a token the broker rejects during the session is detected by the token monitor (SOFT_KILL "token_expired", CRITICAL notification), by the order monitor while it watches orders (HARD_KILL after three consecutive failures; the order monitor stops), by the order reconciler (RC12: a SOFT_KILL "order_reconciler: 3 consecutive BrokerAuthError cycles" after three consecutive cycles with an authentication error, `orders/order_reconciler.py` L45 to L47, L709 to L736; P07-S228), by the probe (an ERROR line per minute), by the kill switch's `record_api_failure` when a signal-processor broker call fails with `BrokerAuthError` (a CRITICAL line; an IP-allowlist alert only for IP-classed messages) and, for the WebSocket, by the live feed as a reconnect failure (SOFT_KILL through the critical callback) (table 6.5).
- P07-S132. FACT: a missing token file is detected at start by `load_token` returning `None`, which the pre-load does not handle, so the start ends with exit 2 (A01 C2); during the session only the health endpoint reads the file again (each GET /health; P07-S224): a removal is reported as `checks.token.ok` false with HTTP 503, and a replacement is reported according to `is_token_valid` with the new file's own `account_id`; the trading path does not notice either and keeps the token it loaded.
- P07-S133. FACT: a malformed token file is detected at start in the same place, with exit 2, or exit 6 for an object without `access_token` (section 3.5); during the session only the health endpoint reads it (P07-S224): a non-JSON, empty or partial file gives `None` from `load_token`, hence `ok` false; a JSON value that is not an object gives `ok` false, with `error` "token_check_failed" when the value is truthy (its `.get` raises, `scripts/healthcheck_server.py` L41 to L46) and without it when it is falsy (`load_token(...) or {}`, L41); a file that is not valid UTF-8 gives the same `error` (the `UnicodeDecodeError` is caught at L45); in every case /health answers 503 (L120 to L130); the trading path does not read it.
- P07-S134. FACT: a wrong-account token is detected only by the start gate's `account_id` comparison (L2547; `scripts/zerodha_login.py` L74), and only if the broker accepted the token first; nothing compares the token file's `api_key` with the client's key. During the session nothing checks the account: the adapter has no account identity (`account_id=None`, P07-S040) and the token monitor discards `profile()`'s return value (`broker/token_monitor.py` L132), so the profile's user identity is never compared with the configured account.
- P07-S135. INTERPRETATION: no detecting site in the trading process recovers from a token fault by itself; the next step after every detection is a kill, an exit, or a log line, and a working token returns only through a new token file and a new start (outside this part).

## 9. Facts bearing on A01's agreed Phase 2 inputs (question 9)

The inputs are A01's agreed treatments (Phase 2 input, not V2 design decisions): A01-01 (one start path, headless), A01-08 (token and configuration checked locally before the first broker call; an authentication failure reported as such, not as clock skew; clock errors kept separate), A01-03 and A01-24 (one configured Zerodha client; no `accounts.csv` or account selection; the client validated before any order call; never switch account). Open Issues Register A01-04 and A01-15 bear on the restart limit and the NTP thresholds. The facts below record where the legacy code stands against each input; they make no Phase 2 decision.

- P07-S136. FACT (one headless start path): the code has one non-interactive start path, which is headless, and an interactive branch that is unreachable at the baseline (A01 C1). The headless path cannot create a token: it needs a token file made outside the process, and the only token creator in the files of this part, `run_login_flow`, needs a browser and an operator (P07-S025); the other creator, `scripts/auto_refresh_token.py`, is part P08's.
- P07-S137. FACT (configuration checked locally before the first broker call): before the first broker call the start checks, locally, the presence of the configuration files and of the required secret names (`ZERODHA_API_KEY_<ACCOUNT_ID>`, `ZERODHA_API_SECRET_<ACCOUNT_ID>`, `TELEGRAM_BOT_TOKEN`, `WEBHOOK_SECRET`; `utils/startup_checks.py` L1550 to L1558), and the pre-load needs the API-key variable (L2361; a missing one ends the start with exit 6 before the call, L2371 to L2374). But the configuration-file and secret checks do not stop the start before that call: the runner records their failures and still runs the clock check, and the start stops only after the whole aggregate (`utils/startup_checks.py` L1543 to L1575; `main.py` L2484 to L2502). `ZERODHA_API_SECRET_<ACCOUNT_ID>` is checked for presence although nothing in the trading process's start reads its value (the secret is read only by the login and refresh scripts, `scripts/zerodha_login.py` L268 and `main.py` L1895 in the unreachable interactive helper); A01 hands this question to A04 under C12 ("whether the API secret is needed at start").
- P07-S138. FACT (token checked locally before the first broker call): the token file is read before the first broker call (L2362) but not checked: the local checks of account, IST date and non-empty token run only at the gate, after it (P07-S036, P07-S050). As A01 C8 records, the legacy order is the reverse of A01-08's input.
- P07-S139. FACT (authentication failure reported as such, not as clock skew): at start, no: a broker authentication failure is reported as the blocking failure `clock_skew` with exit 3, its text visible only in ERROR log records (the adapter's record of the original exception, `broker/zerodha_adapter.py` L299, and the check's line) (P07-S044, P07-S045). - P07-S140. FACT (clock errors kept separate): the startup check uses one label for a measured skew and for any broker error (P07-S115); the probe separates them by exception type (P07-S120). The NTP check is A01's and A20's (A01-15) and is not traced here.
- P07-S141. FACT (one configured client): the trading process builds one live `KiteConnect` client, once (L2375), from the primary row of `accounts.csv` (exactly one primary is enforced, `core/account_registry.py` L179 to L191) and the API key in the variable that row names; the adapter, the token monitor and the probe use that client (P07-S040, P07-S069, P07-S110); the live feed opens its own WebSocket with the same key and the token from the third read (P07-S047, A05).
