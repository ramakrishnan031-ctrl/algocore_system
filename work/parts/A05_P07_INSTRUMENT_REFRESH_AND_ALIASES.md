## 3. The four sources and their loaders (what is read, from where, and what happens when a source is missing or malformed)

P07-S012. FACT (L92 to L109, `_load_security_master(path)`): an absent file prints "ERROR: security master not found: <path>" to stderr and calls `sys.exit(1)` (L94 to L96). A present file is opened with `newline=""` and `encoding="utf-8"` and read with `csv.DictReader` (L98 to L99). For each row: the symbol is the `symbol` cell, stripped (L101); the series is the ` series` cell (with a leading space) or, when that column is absent, the `series` cell, stripped and lower-cased (L103; comment L102: "Header has ' series' with leading space due to CSV formatting"); a row with an empty symbol is skipped (L104 to L105); a row whose series is not empty and not in `_EQ_SERIES` is skipped (L106 to L107); every other symbol is appended, in file order (L108). No other column is read: not `fno_stock`, `market_lot` or `isin_number`.

P07-S013. INTERPRETATION (Python and `csv` semantics; points (a), (d) and the blank-line rule were confirmed with an own standard-library snippet that runs no legacy code): (a) a row whose series cell is empty is kept, so the filter admits every row without a series; (b) the list is not de-duplicated: a symbol on two rows is returned twice; (c) the symbol text keeps its case and inner characters; (d) a row with fewer fields than the header gets `None` for the missing cells, so `.strip()` raises `AttributeError` at L103 (or at L101), which nothing catches; (e) bytes that are not UTF-8 raise `UnicodeDecodeError`, and an unreadable path raises `OSError`, neither caught; (f) a header without a `symbol` column, or with a byte-order mark before it (the first name then is not `symbol`), makes every symbol empty, so no symbol is returned, and the run then fails validation on the row count (section 5) without writing; (g) a header with neither ` series` nor `series` makes every series empty, so every row with a symbol is kept; (h) completely blank lines are skipped by `csv.DictReader`.

## 4. The join (`_build_rows`): which symbols are kept, which source wins for each column, unmatched symbols, duplicates

P07-S022. FACT (L159 to L204, `_build_rows(symbols, sector_map, fno_set, kite_lookup, verbose)`): it walks the security master's symbol list in order (L175). For each symbol it looks up the Kite entry by the same text (L176). With no entry, it appends the symbol to `missing` and sets token 0, lot size 1 and tick size 0.05 (L177 to L181). With an entry, it sets `int(kite.get("instrument_token", 0))`, `int(kite.get("lot_size", 1))` and `float(kite.get("tick_size", 0.05))` (L183 to L185). For every symbol, `is_fno = sym in fno_set` (L187) and `sector = sector_map.get(sym, "")` (L188), and one row is appended with the keys `symbol` (the security master's text), `instrument_token`, `exchange` (the literal "NSE", L197), `lot_size`, `tick_size`, `is_fno` (the text "true" or "false", L200) and `sector` (L194 to L202). It returns the rows and the `missing` list (L204). With `--verbose` it prints one line per symbol (L190 to L192). No row is ever dropped: the output has exactly one row per element of the security master's list.

P07-S023. FACT (D2, the source of each output column; no column has two sources that are compared, and there is no conflict rule between sources other than the sector files' order, P07-S016):

| Output column | Source | Lines | Value when the source has nothing |
|---|---|---|---|
| `symbol` | security master `symbol`, stripped | L101, L195 | (row not built when empty, L104) |
| `instrument_token` | dump row with the same `tradingsymbol`, segment "NSE" or "NSE-EQ" | L176, L183 | 0 (L179) |
| `exchange` | the literal "NSE" | L197 | (always "NSE"; the dump's `exchange` is not read) |
| `lot_size` | the same dump row | L184 | 1 (L180) |

| `sector` | the 12 sector files, the latest in priority order winning | L188 | "" (blank) |

The `.get` defaults at L183 to L185 apply only to a dump element that lacks the key; the published library always sets those keys for every row it returns (P02-S068).

P07-S026. INTERPRETATION (I1, instrument identity; basis L152 to L155, L176, L195): matching is exact and case-sensitive on the stripped text, with no alias, suffix or series mapping; the security master's series is used only to filter (L106), never to build the broker's symbol. So, for every row with a non-zero token, the written `symbol` is exactly a `tradingsymbol` of the NSE dump at the time of the run (the lookup key is that text), and its token is that dump row's token; for a token-0 row the symbol had no such counterpart. This settles, on the writer side, the question that part P05 left open (P05-S089, P05-S118): the cache's `symbol` equals the broker's NSE `tradingsymbol` for every row the writer matched, at the time of the refresh. HISTORICAL: a commit message of 2026-05-07 (`435b3a2`, which adds an alias) says "Chartink sends base, Kite has -BE series"; if the dump lists a BE-series stock with such a suffix, the security master's plain symbol for it would not match and would get token 0 (INTERPRETATION, conditional; the dump's form in the legacy period is UNKNOWN / NOT ESTABLISHED).

P07-S027. INTERPRETATION (D3, duplicates; dictionary and list semantics): the writer does not de-duplicate. A symbol listed twice in the security master gives two identical rows (the same token, P07-S013 (b)); two different symbols can share a non-zero token only if the dump gives one token to two `tradingsymbol` texts; every unmatched symbol shares the token 0. Nothing is reported. The loader then keeps the later row for a repeated symbol and one `_by_token` entry for all token-0 rows (part P05, P05-S017, P05-S080). HISTORICAL (own count-only check): the past tracked file has no repeated symbol and no repeated non-zero token.

P07-S028. FACT and INTERPRETATION (A04 CG-27, the writer side of the tick size): the tick is the dump's value converted again with `float` (L185), or the literal 0.05 for an unmatched symbol (L181). The script checks no tick and no lot size anywhere (L159 to L271: no positivity, `nan`, range or tick-grid test). INTERPRETATION (P02-S068: the library converts `tick_size` with `float` and `lot_size` with `int`; P05-S028, P05-S029): a dump row with a tick of 0 or below, or a lot size below 1, would be written, and at the next start of the trading process the loader would refuse the whole file with `ConfigSchemaError` (the path of part P05, P05-S053, and A01 C9); a `nan` or `inf` tick would be written as `nan` or `inf` and accepted by the loader. Whether the dump ever held such a value is UNKNOWN / NOT ESTABLISHED. The cache's refusal of a non-positive tick, which A04 CG-27 names as the base of the tick helpers' safety, therefore applies to a file this writer can produce, one load later and for the whole file.

P07-S029. FACT (the lot size): the lot size is the dump's equity-row value (`int`, L184) or 1 for an unmatched symbol (L180); the security master's `market_lot` column is not read (P07-S012). HISTORICAL: every row of the past tracked file has lot size 1 (P05-S079).

## 5. The output checks (`validate_instrument_rows`) and the refresh alert (`_send_refresh_alert`)

P07-S034. ## 6. The write (`_write_csv`) and the post-write check (`_check_fresh_write`): the CSV handoff (E1)

P07-S037. FACT (L207 to L218, `_write_csv(csv_path, rows)`): the temporary path is `csv_path.with_suffix(".csv.tmp")` (L209), which for the default target is `config/instruments.csv.tmp`, in the same directory (checked with an own standard-library call: `Path("config/instruments.csv").with_suffix(".csv.tmp")`); it is opened for writing with `newline=""` and `encoding="utf-8"`, and a `csv.DictWriter` with `fieldnames=_CSV_COLUMNS` writes the header and all rows (L211 to L214); after the file is closed, `tmp_path.replace(csv_path)` moves it over the target (L215); on any exception the temporary file is removed (`unlink(missing_ok=True)`) and the exception is raised again (L216 to L218). There is no `flush` or `os.fsync`, no lock, no copy of the previous file and no creation of a missing directory.

P07-S038. INTERPRETATION (Python, `csv` and POSIX semantics; points (c) and (d) checked with an own standard-library snippet): (a) `Path.replace` is `os.replace`; with the temporary file in the target's directory, on POSIX the target is replaced in one rename, so a reader that opens the path sees the old file or the new one, never a partly written file (RI6's intent, L18); (b) without an `fsync`, whether the new content survives a power loss just after the rename is the file system's behaviour (UNKNOWN / NOT ESTABLISHED); (c) the `csv` module's default dialect ends every line with CRLF, so the file is written with CRLF line ends, which the loader (`csv` module), the alias tool (text mode with universal newlines) and `_check_fresh_write` (`splitlines`) all accept; (d) cells are written with `str()`: the token and lot size as integer text, the tick as Python's float text (for example `0.05`, `1.0`, `5.0`), `is_fno` as the lowercase word set at L200, and a blank sector as an empty cell; (e) a process killed during the write (for example by the pre-flight's subprocess timeout, section 10) skips the `except` block, so `config/instruments.csv.tmp` can remain while the target is untouched (unless the rename had already happened); the next run's open with mode "w" overwrites it. HISTORICAL: the past tracked copies have LF line ends, but the repository stores text files with LF (`.gitattributes` L2, `* text=auto eol=lf`, present at `9f58848` and at `970aabf`), so they cannot show the line ends the writer produced on disk.

P07-S039. FACT (L221 to L245 and L420 to L424, `_check_fresh_write(csv_path, max_age_sec=600, min_bytes=1000)`): after the write it fails when the target is absent, when its modification time is more than 600 seconds old, when it is smaller than 1000 bytes, when its text cannot be read as UTF-8 or has no first line (the `except Exception` at L241 also catches the `IndexError` of an empty file), or when the first line does not contain "symbol" in any case; `main` then prints "ERROR: post-write assertion failed: <reason>" and returns 1 (L421 to L424). HISTORICAL (docstring L223 to L228): "Post-write assertion (instruments staleness incident 21-Jun-2026)", to catch "a silent no-write -- the worst kind of failure (the bug that froze instruments 7 weeks)".

P07-S040. INTERPRETATION (when the post-write check can fail; basis P07-S037, P07-S039): it runs only after `_write_csv` has returned, that is after the rename succeeded, so when it fails the new file is already in place and is not rolled back. With at least 1000 validated rows the file is far above 1000 bytes, its first line is the header with `symbol`, and the rename keeps the fresh modification time of the temporary file; in a normal run it therefore passes, and it can fail only if writing took more than 600 seconds, the clock moved, or another process changed the file in between. It cannot see what happens after the script exits, such as the deploy hook's `git checkout -f` restoring a committed copy, which the untracking commit names as the incident's cause (`2b4d976`, 2026-06-21: "the deploy hook's `git checkout -f` silently reverts the VM's fresh copy back to the committed version"); that is visible only to the pre-flight's date grading (part P05, P05-S074; A20).

P07-S041. FACT (E1 and E2, what the script writes, reads, updates and deletes): it reads the four sources of section 3; it writes two paths, the temporary file and the target (default `config/instruments.csv`, or the `--csv` path); it deletes only its temporary file, on a write exception; it updates nothing in place; it writes no database row and no log file of its own (all messages go to stdout and stderr; the declared cron line appends both to `logs/cron-refresh-instruments.log`, section 10). The handoff to the instrument cache is the file: seven named columns in the order of `_CSV_COLUMNS`, UTF-8 text, a header line, one row per security-master symbol, values as in P07-S023 and P07-S038 (d); it carries no timestamp, as-of date, source identity, version or row count of its own (its only date is the file's modification time, which the pre-flight grades). The loader's side of the same contract is part P05's (P05-S076 to P05-S078). The heartbeat row that the cron wrapper writes is A16's (`utils/cron_heartbeat.py` L55 to L95; the table is A03's).
