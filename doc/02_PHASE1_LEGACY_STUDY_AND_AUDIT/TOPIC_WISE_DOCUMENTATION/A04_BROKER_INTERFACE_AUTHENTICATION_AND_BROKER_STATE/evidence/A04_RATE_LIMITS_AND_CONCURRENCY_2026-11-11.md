## 2. The rate limiter module: purpose, structure, categories, algorithm and limits

- P05-S009. HISTORICAL (`broker/rate_limiter.py` module docstring L4 to L7): "Client-side token bucket rate limiter for Zerodha API endpoint categories. Every broker call must go through acquire() before hitting the network. Enforces burst + sustained-rate limits independently per category."
- P05-S010. HISTORICAL (L9 to L23, locked decisions RL1 to RL10): a token bucket, one independent bucket per category (RL1); four categories, `order`, `quote`, `historical`, `margins`, an unknown category raising `ValueError` (RL2); `acquire(category, n=1)` blocks until `n` tokens are available or a timeout, raising `BrokerRateLimitError` if `n` exceeds the capacity or `max_wait_sec` is exceeded (RL3); `max_wait_sec` global, default 30 s, passed at construction (RL4); `try_acquire` non-blocking (RL5); backoff is the adapter's responsibility, and `penalize(category, sleep_sec)` freezes a bucket (RL6); one `threading.Lock` per bucket, no global lock (RL7); `time.monotonic()` for refill arithmetic (RL8); `BrokerRateLimitError` with severity WARN on timeout (RL9); a layer-2 module importing only `threading`, `time`, `core.exceptions`, `core.config_loader` and `core.logger` (RL10).
- P05-S011. HISTORICAL (L25 to L29, "What This Module Does NOT Do"): it makes no HTTP call and catches no 429 (the adapter's job, RL6); it implements no retry or backoff sequence; it reads no configuration file (the caller injects `BrokerLimitsConfig`); it does not use wall-clock time (time_authority) for refill arithmetic (L29: "Does not use wall-clock time (time_authority) for refill math (RL8)").
- P05-S012. FACT (L31 to L42): the imports are `threading`, `time`, `BrokerRateLimitError` and `RateLimitAbortedError` from `core.exceptions`, `get_logger` from `core.logger`, and `BrokerLimitsConfig` from `core.config_loader` (comment L39: "Import only for type annotation; caller constructs and injects the config"); the module logger is `_log = get_logger(__name__)` (L42). The module has no `os`, environment, file or socket access.
- P05-S013. FACT (L44 to L45): `_VALID_CATEGORIES` is a frozenset of the four names, commented "used for validation and for iterating at construction". FACT (reading the file): the name is referenced nowhere else in the module; validation uses the keys of `self._buckets` (L166 to L173) and construction names the four categories literally (L157 to L162).
- P05-S014. FACT: the module defines two classes, `_Bucket` (L52 to L121, internal) and `RateLimiter` (L128 to L272, public), and no module-level function, singleton or registry.
- P05-S015. FACT (`_Bucket.__init__` L58 to L65): each bucket holds `_capacity` (int), `_rate_per_sec` (float), `_tokens` (float, initialised to the capacity: "start full", L61), `_last_refill` (the `time.monotonic()` reading at construction), `_frozen_until` (0.0 meaning not frozen), `_was_frozen` (False) and `_lock` (`threading.Lock()`).
- P05-S016. FACT (`_Bucket._refill` L69 to L74): refill is continuous: `_tokens = min(capacity, _tokens + elapsed * rate_per_sec)`, with the elapsed time from `time.monotonic()`, and `_last_refill` is set to the current reading. There is no discrete window or periodic reset.
- P05-S017. INTERPRETATION (L58 to L74, L90 to L99): the algorithm is a token bucket with continuous refill; a category allows up to `burst` calls at once from a full bucket and `rate_per_sec` calls per second sustained. Because a bucket starts full (L61), the first `burst` calls in a category after construction pass without waiting.
- P05-S018. FACT (`RateLimiter.__init__` L148 to L162): the constructor takes `limits: BrokerLimitsConfig` and the keyword-only `max_wait_sec: float = 30.0` and `shutdown_event: threading.Event | None = None` (FIX-060); it builds four buckets from `limits.order`, `limits.quote`, `limits.historical` and `limits.margins`, each with `.burst` as capacity and `.rate_per_sec` as rate.
- P05-S019. FACT (`RateLimiter._get_bucket` L166 to L173): an unknown category raises `ValueError` ("Unknown rate-limit category: ... Valid categories: [...]"); each public method calls it first (L186, L256, L267).
- P05-S020. FACT (`config/broker_limits.yaml` L9 to L23, consumed at L157 to L162): the committed limits are `order` burst 8 and 8 per second; `quote` 3 and 3 per second (L14 comment: "H-24 / F.1: bumped from 1 to relax quote serialization under burst"); `historical` 2 and 2 per second; `margins` 8 and 8 per second. Whether these values were in force on the production VM is UNKNOWN / NOT ESTABLISHED (section 21).
- P05-S021. FACT (L157 to L162): there is one bucket per category per `RateLimiter` instance; nothing in the module keys a bucket by thread, endpoint, client, account or process. INTERPRETATION: within one process, every caller that holds the same instance shares each category's limit (a global limit per category, not per thread); a category groups several adapter methods, so the limit is not per endpoint (section 8); separate instances, for example in other processes, have separate buckets (section 7).
- P05-S175. FACT (`signals/entry_throttle.py` module docstring L1 to L19, `EntryThrottle` L37 onwards, lock L55, `admit` L65 onwards; built by `SignalProcessor` at `signals/signal_processor.py` L262 to L263 and consulted at L1410, L2225 and L2530; `config/system_config.yaml` L349 to L353; wired at `main.py` L3595 to L3599): besides the broker limiter, the signal processor applies an application-level entry-rate limiter (FIX-190, Bug G): at the file values at least 20 s between any two placed entries (`min_gap_between_entries_sec`), at most 3 placed entries in a rolling 60 s (`entry_burst_max`, `entry_burst_window_sec`) and a 300 s cooldown per symbol (`per_symbol_cooldown_sec`), checked and recorded atomically under one `threading.Lock` (docstring L13 to L17). It limits how often entries are placed, not broker requests as such, and does not use the broker limiter (its imports, L21 to L27, are `__future__`, `threading`, `time`, `collections`, `dataclasses` and `typing`); its logic is A06's.

## 3. `acquire`: blocking, waits, the timeout and the shutdown abort

- P05-S022. FACT (`RateLimiter.acquire` L177 to L199): `acquire(category, n=1)` returns `None` on success. If `n > bucket._capacity` it raises `BrokerRateLimitError` at once, with context `category`, `requested_tokens=n`, `available_tokens=bucket._capacity` (the capacity, not the current token count), `waited_sec=0.0` and `max_wait_sec`.
- P05-S023. FACT (grep of non-test code; the calls are listed in sections 8 to 10): every non-test call of `acquire` and `try_acquire` passes only the category, so `n` is always 1. INTERPRETATION: the immediate `n > capacity` rejection can then occur only for a bucket whose `burst` is below 1; at the committed values (P05-S020) it is not reached.
- P05-S024. FACT (L201 to L223): otherwise `acquire` loops. It calls `bucket.try_acquire(n)`; on success it calls `bucket.pop_thaw_notice()` and, if that returns True, logs INFO "Rate limiter: bucket '%s' thawed (freeze expired)" (L206 to L210), then returns. On failure, once `time.monotonic()` reaches the deadline (start plus `max_wait_sec`, L201 to L202), it raises `BrokerRateLimitError` ("Rate limit timeout after ...") with context `category`, `requested_tokens`, `available_tokens=bucket.available_tokens()`, `waited_sec` (rounded to three places) and `max_wait_sec`.
- P05-S025. FACT (L225 to L233, L145 to L146): before each retry it computes `sleep_for` under the bucket lock from `_seconds_until_ready(n)` (L76 to L86: the larger of the remaining freeze and the time to accrue the missing tokens), caps it at the time left to the deadline and at `_POLL_INTERVAL_SEC` (0.1 s), and floors it at `_MIN_SLEEP_SEC` (0.001 s) (HISTORICAL: the 0.001 s floor dates from `bcf03b5`, 2026-04-17; the 0.1 s cap replaced a 0.05 s cap in FIX-060, `07979fa`, 2026-05-15; FIX-111, `2ad9a31`, 2026-05-18, replaced both literals with the named constants).
- P05-S026. FACT (L235 to L246): when a shutdown event was given, the wait is `self._shutdown_event.wait(timeout=sleep_for)`; if that returns True, `acquire` raises `RateLimitAbortedError` ("Rate limiter acquire aborted by shutdown during wait for ...") with context `category` and `waited_sec`. Without an event it calls `time.sleep(sleep_for)`.
- P05-S027. FACT (L204 to L211, L235 to L244): the shutdown event is consulted only in the waiting branch, after a failed take; a call that finds a token returns normally even when the event is already set. INTERPRETATION (standard library: `threading.Event.wait` returns True at once when the flag is set): once the event is set, every `acquire` that has to wait aborts at its first wait, and every `acquire` that does not have to wait proceeds to its broker call.
- P05-S028. INTERPRETATION (L204 to L246): waiting is polling: each sleep between two takes lasts at most 0.1 s and at least 0.001 s (L232 to L233); there is no queue, condition variable or ticket, so waiters are not served in arrival order: whichever thread's `try_acquire` runs first after tokens accrue takes them. A waiter can therefore reach its 30 s deadline while other threads keep taking tokens in the same category.
- P05-S029. FACT (L152; `main.py` L2348; the construction sites in section 7): `max_wait_sec` is 30.0 for every instance in non-test code: no construction site passes it, and `BrokerLimitsConfig` has no key for it (`core/config_loader.py` L2245 to L2256).
- P05-S030. FACT (`core/exceptions.py` L243 to L258): `BrokerRateLimitError` subclasses `BrokerError` with `SEVERITY = "WARN"`; its docstring reads "Client-side token bucket was exhausted and max_wait_sec elapsed before enough tokens became available" and "WARN (not ERROR): rate limiting is an expected operational condition under heavy load, not a system failure". FACT (L284 to L298): `RateLimitAbortedError` subclasses `TradingSystemError` directly, not `BrokerError`, with `SEVERITY = "INFO"` ("shutdown is an expected operation, not a failure"). FACT (L47 to L49): both take `(message, **context)` and keep the context in `self.context`.
- P05-S031. INTERPRETATION (class hierarchy, `core/exceptions.py` L30, L158, L243, L261, L284): a handler written `except BrokerError` catches `BrokerRateLimitError` and `BrokerRateLimit429Error` but not `RateLimitAbortedError`, which reaches only handlers for `TradingSystemError` or `Exception`.
- P05-S032. FACT (section 8): in every adapter method the `acquire` call precedes the `self._kite` call. INTERPRETATION: when `acquire` raises either exception, no request was sent for that call. HISTORICAL: `docs/design/a2_timeout_retry_design_02jul2026.md` L57 states the same ("raised by `broker/rate_limiter.py:191/:215` inside `acquire()`, before any network I/O").

## 4. `try_acquire`, `penalize` and the freeze

- P05-S033. FACT (`RateLimiter.try_acquire` L248 to L256; `_Bucket.try_acquire` L90 to L99): `try_acquire(category, n=1)` does not block. Under the bucket lock it returns False if the bucket is frozen (`time.monotonic() < _frozen_until`), without refilling; otherwise it refills, and if at least `n` tokens are available it consumes them and returns True, else returns False. It does not consult the shutdown event, does not log and does not call `pop_thaw_notice`.
- P05-S034. FACT (`RateLimiter.penalize` L258 to L272; `_Bucket.freeze` L101 to L105): `penalize(category, sleep_sec)` sets `_frozen_until` to now plus `sleep_sec` and `_was_frozen` to True under the lock, then logs WARNING "Rate limiter: bucket '%s' frozen for %.1fs (broker 429 backoff)". During the freeze `try_acquire` returns False (L93 to L94) and `acquire` waits, its sleep estimate including the remaining freeze (L82, L86).
- P05-S035. FACT (L104): the freeze end is assigned, not extended: a later `penalize` replaces any freeze in force, so a shorter later penalty shortens a longer earlier one. `sleep_sec` is not validated: a zero or negative value sets an end in the past, which freezes nothing but still sets `_was_frozen`.
- P05-S036. INTERPRETATION (L69 to L74, L93 to L95): a freeze stops consumption but not accrual: `_refill` works from elapsed time, so when a freeze ends the bucket holds the tokens accrued during it, up to `burst`, and up to `burst` waiting callers can proceed at once.
- P05-S037. FACT (`_Bucket.pop_thaw_notice` L107 to L115; L206 to L210): `pop_thaw_notice` returns True once after a freeze has expired and clears `_was_frozen`; only `acquire` calls it, after a successful take. INTERPRETATION: if the first take after a freeze is made by `try_acquire`, the INFO "thawed" line is written later, at the next successful `acquire` in that category.
- P05-S038. FACT (`_Bucket.available_tokens` L117 to L121; L220): `available_tokens()` refills and returns the token count under the lock; it is used only for the context of the timeout error.
- P05-S039. FACT (grep of non-test code): the only caller of `penalize` is `ZerodhaAdapter._translate_broker_exception` (`broker/zerodha_adapter.py` L2056, section 9); the only caller of `try_acquire` is `SignalProcessor` (`signals/signal_processor.py` L418 to L419), which receives no limiter from `main.py` (section 10).

## 5. Thread safety inside the limiter

- P05-S040. FACT (L65; RL7 at L19): each `_Bucket` has its own `threading.Lock`; `RateLimiter` has no lock of its own.
- P05-S041. FACT: the bucket lock is held in `_Bucket.try_acquire` (L92 to L99), `freeze` (L103 to L105), `pop_thaw_notice` (L111 to L115) and `available_tokens` (L119 to L121), and by `RateLimiter.acquire` around `_seconds_until_ready` (L226 to L227). `_refill` and `_seconds_until_ready`, documented as to be called with the lock held (L67, L79), are called only inside those locked blocks (L83, L95, L120, L227).
- P05-S042. FACT: each lock protects its bucket's `_tokens`, `_last_refill`, `_frozen_until` and `_was_frozen`. `bucket._capacity` is read without the lock (L190 to L196; comment L189: "_capacity is read-only; safe to access without lock") and is assigned only in `_Bucket.__init__` (L59). `RateLimiter._buckets`, `_max_wait_sec` and `_shutdown_event` are assigned only in `__init__` (L155 to L162) and are not changed afterwards (reading the file).
- P05-S043. FACT: no lock is held while logging (L207 to L210, L269 to L272) or while sleeping or waiting (L236 to L246); each locked block is arithmetic only. No path takes a bucket lock while already holding it (the `with` blocks in `acquire` are sequential, and `_seconds_until_ready` and `_refill` take no lock). INTERPRETATION (`threading.Lock` is not re-entrant): the module has no self-deadlock path, and locks are held briefly.
- P05-S044. INTERPRETATION (P05-S040 to P05-S043): at code level one instance can be shared by the threads of a process: each take and each freeze is atomic per bucket, and different categories never contend for one lock. Atomicity covers each take, not the wait: between a failed take (L205) and the sleep estimate (L226 to L227) other threads may take tokens; the estimate only bounds the next sleep (P05-S028).
- P05-S045. FACT (L33 to L40): the limiter's state is held in process memory only (no file, socket, shared memory or database). INTERPRETATION: instances in different processes neither share nor see each other's buckets.
- P05-S046. FACT (`main.py` L116, L1525, L1570 to L1578, L1628 to L1629, L2348, L4141): the shutdown event given to the trading process's limiter is the module-level `_shutdown_event = threading.Event()`; it is set by the SIGINT and SIGTERM handler (L1573), by the end-of-day self-exit thread through its `shutdown_event` parameter (L1525; passed at L4141), and at the start of `_shutdown` (L1629; comment L1628: "FIX-060: Set shutdown event FIRST so rate limiter aborts immediately"). The ordering of these is A01's (A01 AUDIT C17).

## 9. Interaction with the adapter's HTTP 429 backoff

The detection, delay formula, counter and jitter are part P02's (`broker/zerodha_adapter.py` L2006 to L2079); this section records only where they meet the limiter.

- P05-S078. FACT (`broker/zerodha_adapter.py` L2035 to L2077): on an exception whose `code` attribute equals 429 (`_is_429`, L2006 to L2008), `_translate_broker_exception` takes the category `_CATEGORY_MAP.get(operation, "order")` (L2053), obtains a delay and an attempt number from `_compute_429_backoff_delay` (L2054), calls `self._rl.penalize(category, delay)` (L2056), logs WARNING "zerodha_adapter.broker_429" (L2065 to L2070) and returns a `BrokerRateLimit429Error` carrying `operation`, `category`, `delay_sec` and `attempt` (L2071 to L2077), which the calling method raises.
- P05-S079. FACT (L2055 to L2064): the `penalize` call is wrapped in `except ValueError`, which logs ERROR "zerodha_adapter.penalize_unknown_category" and still returns the 429 error. INTERPRETATION: every value of the map is a valid category (L254 to L269) and the fallback is `"order"` (L2053), so this branch cannot be reached from the committed map; it is defensive.
- P05-S080. FACT (module docstring L70 to L81; comment L2000 to L2004; ZA11 at L28): the adapter neither sleeps nor retries after a 429; "On the next attempt, rate_limiter.acquire() blocks until the bucket thaws, which is the backoff pacing." INTERPRETATION (with `broker/rate_limiter.py` L101 to L105, L204 to L246): the pause is delivered only through the bucket freeze, to whichever call next acquires in that category, from any thread; with the committed values the freeze is capped at `max_delay_sec` 5.0 s plus up to 0.05 s of jitter (`config/broker_limits.yaml` L37, L40; the computation is P02's), well inside the 30 s `max_wait_sec`.
- P05-S081. INTERPRETATION (P05-S021, P05-S070): a freeze applies to every user of that bucket in the process, not only to the caller that met the 429. A 429 on an `order`-category call pauses all order-category calls, including the target manager's modifies, which take their own `order` token (section 10); a 429 on a `margins`-category call pauses positions, margins, trades, holdings, GTT reads and order-list reads.

### 15.5 Answers to direction questions 11 and 12

- P05-S135. Question 11 (what limits; their scope; 429s, throttling, transient errors and timeouts), from the statements above: FACT: the only implemented broker request-rate limits are four client-side token buckets with continuous per-second refill and a burst capacity (`order` 8 and 8, `quote` 3 and 3, `historical` 2 and 2, `margins` 8 and 8 at the committed file; P05-S016 to P05-S020); separately, `signals/entry_throttle.py` throttles entry placements (A06's FIX-190 rule: at least 20 s between placed entries, at most 3 within 60 s and a 300 s per-symbol cooldown at the file values; P05-S175), and `scripts/fetch_daily_candles.py` sleeps 0.35 s between historical calls (P05-S065); the module keeps no per-minute or per-day count (`broker/rate_limiter.py` L52 to L272), and a legacy audit proposed adding such budgets (HISTORICAL: `docs/audit/audit_05jul2026.md` L694, "Add per-minute/daily order budgets to RateLimiter"). Throttling: a blocking wait of up to 30 s, with sleeps of at most 0.1 s between checks, with no fairness, raising `BrokerRateLimitError` (WARN) on timeout and `RateLimitAbortedError` (INFO) on shutdown; the non-blocking `try_acquire` is unused at the baseline wiring (P05-S022 to P05-S039, P05-S091). 429s: the adapter freezes the method's bucket and raises `BrokerRateLimit429Error` without retrying; the order placer retries entries up to three times; `cancel_order` and `modify_order` never penalize, `get_quote_raw` penalizes the `order` bucket instead of the `quote` bucket it takes its token from, and the historical closure and the token monitor have no 429 handling (P05-S071, P05-S072, P05-S078 to P05-S086, P05-S094, P05-S098). Transient errors and timeouts: the adapter does not retry (ZA11); a limiter timeout is counted by the kill switch's breaker only when it arrives as `BrokerRateLimitError` (not from the four methods whose acquire is inside the `try`, nor from the `quote` leg of `get_live_margin_pct`), and by the order monitor's breaker in any form (P05-S057, P05-S058, P05-S074); HTTP timeouts use `read_sec` on the main live client only, and `connect_sec` is unused (P05-S051, P05-S123). G7's 1 s / 5 s / 30 s / soft-kill sequence is not implemented (P05-S057).
- P05-S136. Question 12 (can concurrent workers share a client or a limiter; locking): FACT: yes at code level: the trading process's threads share one limiter instance and one adapter, and in live mode one REST client (P05-S061, P05-S104 to P05-S107). The limiter's per-bucket locks make each take and freeze atomic, hold no lock while waiting, and give no fairness (P05-S040 to P05-S044, P05-S028). The adapter's five locks protect its 429 counter, its margin cache and its paper stores; none is held across a broker call, and `_last_response_date` is written after every response that carries a `Date` header, without a lock (P05-S109 to P05-S115). INTERPRETATION and UNKNOWN / NOT ESTABLISHED: the client's own thread safety at the pinned versions and any actual runtime overlap (P05-S121, P05-S122, P05-S132).
