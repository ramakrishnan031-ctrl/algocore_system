## 3. `scripts/auto_refresh_token.py`: headless login, request token, exchange, save and retries

- **P08-S025** FACT: `run_refresh` (L248 to L273) makes up to `_NETWORK_RETRIES = 3` attempts (L71, L258), each a call of `_refresh_once` (L260). `_AuthError` is re-raised at once (L261 to L262). A `requests.RequestException` is logged at WARNING as `auto_refresh_token.network_retry attempt=<n>/3 error=<exception>` and followed by a sleep of 2 seconds before the second attempt and 4 seconds before the third (L256, L263 to L271); after the third failure the last exception is re-raised (L272 to L273). INTERPRETATION (Python semantics): any other exception type, for example `RuntimeError`, `KeyError`, `TypeError` or `OSError`, has no `except` clause in `run_refresh` and leaves it at once, without a retry.
- **P08-S026** FACT: `_refresh_once` (L220 to L245) imports `requests` and, from `scripts.zerodha_login`, `exchange_request_token` and `save_token` (L222, L226); opens a new `requests.Session` with a browser-like `User-Agent` header (L228 to L229; the string at L66 to L69, with the comment that "a default python-requests User-Agent can be 403'd by upstream WAFs", L64 to L65); calls `login_and_get_request_token` (L231 to L234), then `exchange_request_token` (L235 to L237), then `save_token` (L238 to L244); and returns the access token, which `main` does not use (L376).
- **P08-S027** FACT: Each attempt starts again from the password step on a new session (L228, L258 to L260); nothing from a failed attempt (request identifier, cookies, request token) is carried over. INTERPRETATION: one run can submit the password up to three times and the 2FA form up to six times.
- **P08-S028** FACT: Step 1, password login (L169 to L179): `POST https://kite.zerodha.com/api/login` (L58) with the form fields `user_id` and `password` and a 10-second timeout (`_REQUEST_TIMEOUT = 10.0`, L72; L170 to L174); then `resp.raise_for_status()` (L175) and `resp.json()` (L176); a JSON `status` other than `success` raises `_AuthError("Login failed: <message>")` (L177 to L178); otherwise the request identifier is read as `data["data"]["request_id"]` (L179).
- **P08-S029** INTERPRETATION (library semantics; `requests==2.33.1` is pinned, `requirements.txt` L9): an HTTP error status at the password step raises `requests.HTTPError` from `raise_for_status`, which is a `RequestException`, so it is retried as a network error and not raised as `_AuthError`; a body that is not JSON makes `resp.json()` raise an exception that in this `requests` line derives from both `RequestException` and `ValueError`, so it is retried too; a `success` reply without `data.request_id` raises `KeyError` or `TypeError` at L179, which is not retried. HISTORICAL: the `_AuthError` docstring names "wrong password" as a definitive failure not to be retried (L75 to L77); the code raises `_AuthError` for it only when the endpoint answers with a success HTTP status and a non-success JSON status, the shape the unit test uses (`tests/unit/test_fix135_auto_token.py` L159 to L164: HTTP 200 with `status: error`). Which HTTP status the live endpoint gave for a rejected password: UNKNOWN / NOT ESTABLISHED.
- **P08-S030** FACT: Step 2, TOTP 2FA (L181 to L210): up to two `POST https://kite.zerodha.com/api/twofa` (L59) with `user_id`, `request_id`, `twofa_value` (a code generated at that moment, L189) and `twofa_type: "totp"`, each with a 10-second timeout (L183 to L193). An attempt succeeds on HTTP 200 with JSON `status == "success"` (L194 to L199); a 200 body that is not JSON, or any other status, makes it fail with a message of up to 200 characters of the response text (L200 to L203). After the first failure the script logs `auto_refresh_token.twofa_retry: <message>` at WARNING, sleeps 1 second and tries again (L206 to L209); after the second it raises `_AuthError("2FA failed: <message>")` (L210). A network exception from `session.post` is not caught here; it reaches `run_refresh`, which restarts the whole sequence (L263).
- **P08-S031** INTERPRETATION: the comment says that the second 2FA attempt "allows the next 30s window / a small clock skew to pass" (L181 to L182) and the docstring that the step is retried "once on a rejected TOTP (clock skew)" (L162 to L163), but the wait is 1 second (L208); `generate_totp` uses the library's default 30-second period (L90), so the second attempt usually submits the same code as the first unless a 30-second boundary falls between them.
- **P08-S032** FACT: Step 3, request token (L212 to L213; `_fetch_request_token` L123 to L146): `GET https://kite.zerodha.com/connect/login?v=3&api_key=<api key>` (L60, L132) on the authenticated session with `allow_redirects=False` and a 10-second timeout (L134); the request token is taken from the `request_token` query parameter of the `Location` header, or else of the response URL (L135 to L136; `_request_token_from_url` L115 to L120); a redirect without it is followed by joining its `Location` to the current URL (L139 to L141), for at most `max_hops=6` requests (L123, L133); an answer that is not a redirect and has no token raises `_AuthError("request_token not found from connect/login (HTTP <status>, hop <n>)")` (L142 to L145), and six hops without one raise `_AuthError("request_token not found: connect/login redirect chain too long")` (L146). HISTORICAL: the docstring says the token is taken from the `Location` header before the app's registered redirect address, "possibly unreachable", would be fetched (L124 to L131).
- **P08-S033** FACT: Step 4, exchange (`scripts/zerodha_login.py` `exchange_request_token` L84 to L125; part P07's file): the SHA-256 checksum of API key, request token and API secret (L100 to L102) is posted with the API key and the request token to `https://api.kite.trade/session/token` (L41, L104 to L112) with a 10-second default timeout (L88); the call uses `requests.post`, not the refresh's session, so it carries the library's default `User-Agent`. A status other than 200 raises `RuntimeError("Kite session exchange failed: HTTP <status> -- <up to 200 characters of the body>")` (L114 to L117); a reply without `data.access_token` or a top-level `access_token` raises `RuntimeError` with up to 200 characters of the parsed reply (L119 to L124). INTERPRETATION: both `RuntimeError` cases leave `run_refresh` without a retry (S025); a network error, or a 200 reply that is not JSON (L119), is a `RequestException` and is retried.
- **P08-S034** FACT: Step 5, save (`save_token`, `scripts/zerodha_login.py` L132 to L176): creates the parent folder (L144) and sets it to mode 0700, ignoring `OSError` (L148 to L151); builds the record `account_id`, `broker`, `access_token`, `api_key`, `date` (the IST date of the save), `saved_at` (the IST time of the save) and `expires_at` (the next 05:00 IST: today's 05:00 if it is still ahead, otherwise tomorrow's) (L152 to L165); opens the final path with `os.open(path, O_WRONLY | O_CREAT | O_TRUNC, 0o600)` and writes the record with `json.dump(..., indent=2)` (L170 to L172); then sets mode 0600, ignoring `OSError` (L173 to L176). The refresh passes `account.account_id`, `account.broker`, the resolved API key, the new access token and the token path (L238 to L244).
