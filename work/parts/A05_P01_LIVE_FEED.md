## 5. Tick intake, normalisation, queue, consumer and dispatch

P01-S040. P01-S041. FACT (L278 to L301): for each raw tick the feed sets `bid` and `ask` to 0.0 and, when `raw.get("depth")` is truthy, takes the first `buy` and `sell` entries' `price` with `or 0.0` fallbacks (L283 to L292). It then builds a new dict with six keys (L293 to L300): `instrument_token = raw.get("instrument_token")` (None when absent); `last_price = float(raw.get("last_price", 0.0))` (0.0 when absent); `bid`; `ask`; `timestamp = raw.get("exchange_timestamp") or raw.get("timestamp")` (None when both are absent or falsy); `volume = raw.get("volume_traded")` (None when absent). P01-S042. FACT (L293 to L300; grep of `MODE_FULL|MODE_QUOTE|MODE_LTP` outside tests and documents: L175, L191, L280, L353 only) (A3): the feed adds no receipt timestamp to the tick and does not convert, localise, round or validate `timestamp`, `last_price` or `volume`; `volume` is the library's `volume_traded` value passed through under another name, with no delta computed in the feed. Which keys the library supplies in MODE_LTP (for example `exchange_timestamp`, `volume_traded`, `depth`) and their types and time zone: library behaviour: see P02. INTERPRETATION: without depth data `bid` and `ask` stay 0.0.

P01-S043. INTERPRETATION (Python semantics): `float(raw.get("last_price", 0.0))` raises when the key is present with `None` or a non-numeric value, and `buys[0].get(...)` raises when a depth entry is not a dict. `_on_ticks` has no try around its loop, so such an exception leaves `_on_ticks` on the library's thread after the earlier ticks of the batch were queued and before the later ones. Whether the library can supply such values, and what it does with the exception: library behaviour: see P02.

P01-S044. FACT (L302 to L322): when the queue is not full the tick is queued with `put_nowait` (L303 to L304). When it is full the feed logs CRITICAL with the tag "LIVEFEED_QUEUE_FULL" (L306 to L310); calls `self._kill_switch.soft_kill("LIVEFEED_QUEUE_FULL")` if a kill switch was injected (L311 to L312), otherwise logs a second CRITICAL line, "no kill_switch configured - cannot trigger soft_kill" (L313 to L316); then tries `put_nowait` once more and swallows `queue.Full` (L318 to L322), so the new tick is lost when the queue is still full. These steps repeat for every tick of a batch that meets a full queue; there is no once-per-episode guard. `_on_ticks` never waits on the queue.

P01-S045. HISTORICAL against FACT: the docstring (L265) says "Drop oldest if full"; LF5 (`docs/locked_decisions.yaml` L2451 to L2460, 2026-04-17) says "Queue full: drop oldest tick (get_nowait to evict), log WARNING, add new tick"; the FIX-029 comment (L302) says "queue.Full triggers soft_kill instead of dropping ticks"; the comment at L317 says the second put "may block briefly or raise". FACT (L303 to L322): nothing is evicted; when the queue is still full the newest tick is dropped. INTERPRETATION (Python `queue` semantics): `put_nowait` does not block.

P01-S046. FACT (`main.py` L2927 to L2938): `main.py` passes no `kill_switch`. INTERPRETATION: in the wired system a full queue therefore produces two CRITICAL log lines for each affected tick and the loss of that tick when the second put fails; no kill-switch action and no notification come from this path.

P01-S047. FACT (L526 to L570): `_consume_ticks` records the consumer thread's own identity in `_ticker_thread_id` (L543 to L545; the name and the FIX-088 comment say "ticker thread"), and loops while `_stop_event` is clear (L547): it first services the force-reconnect flag (L548 to L562; section 7), then waits up to 0.1 s for one tick (L564) and drains every further queued tick without waiting into the same batch (L565 to L570). INTERPRETATION (Python `queue` semantics): the batch size is not capped; with a FIFO queue and one consumer at a time, ticks are dispatched in the order `_on_ticks` queued them, and ticks from several library batches can be merged into one dispatch.

P01-S048. FACT (L572 to L590): before dispatch a tick is discarded, with a DEBUG log only, when `instrument_token` is None or `last_price` is None or equal to 0.0 (L576 to L586); a batch left empty is skipped (L589 to L590). INTERPRETATION: `last_price` cannot be None here because it was converted with `float()` at L295, so the check that acts is the 0.0 test, which also catches ticks for which the library supplied no `last_price` (the 0.0 default at L295).

P01-S049. FACT (L264 to L322, L526 to L620) (A4): the feed has no handling of duplicate, out-of-order, delayed or late ticks: it compares no timestamps, keeps no per-token last value, does not check volume or price sign, and does not drop ticks for tokens it did not subscribe. Missing ticks are detected only as the whole feed's tick age, by the watchdog (section 7).

P01-S050. FACT (L592 to L620): for dispatch the feed copies the callback list under `_lock` and drops dead weak references (L593 to L596), dereferences the rest (L599 to L600), and calls each live callback with the whole validated batch (L602 to L606). Each call sits in its own `try/except Exception`, which logs `log_exception` and a CRITICAL line naming the callback and the error (L607 to L618) and goes on to the next callback; nothing is re-raised (HISTORICAL comment L603 to L604: "consumer thread must be immortal"). `queue.Empty` leads to the next loop (L619 to L620).

P01-S051. INTERPRETATION (Python semantics): an exception raised inside the loop but outside the per-callback `try` (for example from a logging call inside an `except` block) is not caught by `except queue.Empty` (L619) and ends the consumer thread; `_check_consumer_health` later restarts it (section 7). Callbacks run on the consumer thread, so a slow callback delays every later dispatch and lets the queue fill.

P01-S052. FACT (L211 to L244, L232, L602): `register_callback(fn)` stores `weakref.WeakMethod(fn)` when `fn` has `__self__` and `weakref.ref(fn)` otherwise (L224 to L230), after a duplicate check `weak_cb() is fn` (L219 to L222); `unregister_callback` removes the first entry whose dereference `is fn` (L240 to L244). P01-S053. INTERPRETATION (Python semantics): each access to a bound method creates a new bound-method object, and calling a `WeakMethod` returns a new one, so the `is` tests at L221 and L242 never match a bound method: registering one bound method twice would store two entries, and a bound method could not be unregistered. In non-test code the only bound-method registration is the placer's, which guards itself with a flag (`orders/order_placer.py` L3407 to L3409), and there is no `unregister_callback` caller (P01-S032).

P01-S054. INTERPRETATION (Python semantics): its only strong reference is the local name in `_main_locked`'s frame, which stays alive until `_main_locked` returns after `_shutdown`, so the weak reference stays alive for the session.

P01-S055.
