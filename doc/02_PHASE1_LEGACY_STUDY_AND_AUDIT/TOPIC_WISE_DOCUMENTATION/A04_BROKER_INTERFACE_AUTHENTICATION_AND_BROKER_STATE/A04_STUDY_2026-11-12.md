## 2. The broker interface in brief

A summary for orientation; each point is established in the section named, with its evidence.

- **One client, one adapter.** A live start builds one `KiteConnect` client from the primary row of `config/accounts.csv` and the shared token file, and one `ZerodhaAdapter` around it; the adapter, its bound methods or the raw client reach every consumer in the trading process. There is no broker abstraction: the AngelOne adapter is a dormant stub, and the `broker` configuration section has no reader (section 3).
- **The adapter.** It sends the order actions (`place_order`, cancels, modifications and the GTT actions) and the reads (holdings, positions, margins, order history, the order book, trades and quotes) through the SDK; it takes a limiter token before each call, translates SDK exceptions into the system's broker exceptions (cancels and modifications instead return `success=False`), resolves the product, snaps prices to the tick and registers each new order with the order state machine. It never retries and validates no broker answer; broker statuses are passed through unmapped (sections 6, 7 and 11).
- **Around the adapter, in the trading process.** A four-bucket rate limiter shared by all threads (section 9); the order monitor, which polls each watched order's history and publishes fills and status changes, and the in-memory order state machine (section 10); the token monitor and the clock-skew probe, two daemon threads (section 4); the product resolver, the position helpers, the cost calculator and the tick helpers (sections 11 and 12). The callers that decide what to place, exit, cancel or reconcile are A10's to A13's, mapped in section 8.
- **Authentication.** The repository contains token-writing paths in the external login tool (run by hand or by the PC morning scripts, the token then copied to the VM) and in the headless refresh declared for 08:15 on the VM; a further call path is present in the source of the trading process's interactive start but is unreachable at the baseline (A01 C1), and whether it ran in any earlier build is UNKNOWN / NOT ESTABLISHED. The watcher checks the token file before its declared service start; the trading start reads the token without checks for the client and checks it locally only after the first broker call. There is no refresh, reload or re-login in the process; INTERPRETATION: a rejected token ends in a kill, an exit or a log line, and a new token needs a new start (sections 4 and 5).
- **Outside the trading process.** Eleven scripts, the pre-flight's broker probe among them, build their own clients with their own credential rules and do not share the trading process's limiter (sections 3 and 8).
- **Evidence limit.** All of this is what the code at the baseline does when called; what ran, with which account and what the broker answered is UNKNOWN / NOT ESTABLISHED (sections 1.6 and 17.2).

## 3. Broker client construction, selection, configuration and the adapter contracts (questions 1 to 4 and 21)

Evidence: the client evidence (P01), which covers `broker/zerodha_adapter.py` L1 to L289, L346 to L493 and L1297 to L1382, `broker/angelone_adapter.py`, `broker/__init__.py`, every construction site of an adapter or a Kite client, and the configuration keys and environment-variable names that the A04 paths consume.

**Construction, selection, configuration and sharing (question 1).**

- FACT: in the trading process there is one configured trading client. In live mode it is one `KiteConnect`, built once by `_build_kite_client` (`main.py` L381 to L390, called at L2375) from the primary account's API-key variable (whose name `config/accounts.csv` gives) and the token file's access token, both passed through the process environment (L2361, L2363), with the read timeout from `config/broker_limits.yaml` and a 50-connection pool. It is injected into the one `ZerodhaAdapter` (L2383), and the adapter, its bound methods or the raw client reach 23 consumer sites by reference; the token monitor and the market-data fetch closure use the raw client directly (P01-S084, P01-S097). In paper mode there is no trading client; the separate read-only clients are paper-only (P01-S097). The live feed's `KiteTicker` is a second broker connection, built from environment values (A05) (P01-S085).
- FACT: no alternate or fallback client-selection path is active: the `broker` section of `config/system_config.yaml` (`primary`, `fallback`, `fallback_enabled`, `multi_account_mode`) has no runtime reader (A02 K-01, A02-15); the AngelOne adapter has no importer; the adapter accepts `account_id` and ignores it, so it has no account identity. The only selections are the command-line mode and the primary row of `config/accounts.csv`; the interactive account selector cannot run at the baseline (A01 C1) and would not rebuild the client if it did (P01-S036, P01-S098).
- FACT: the live client is never given a new token after L387 (P01-S076). INTERPRETATION: the environment write at L2576 reaches only later readers of the environment, chiefly the live feed, not the client (P01-S080, P01-S163).
- FACT: outside the trading process, eleven scripts construct `KiteConnect` directly, each in its own process, with its own credential rule (at least six rules: per-account names, generic names, a literal default identifier, the token file's own `api_key`) and no timeout argument; one builds a new client for every sampled symbol (P01-S091, P01-S100, P01-S168; A01 M-39, A02 F-16, A02 K-32). Five of them do not load `.env` themselves (P01-S092). One of the eleven is the pre-flight's broker probe: the pre-flight orchestrator, run by three weekday jobs at 08:30, 09:14 and 09:15 and launched on demand by the trading process's start between 06:00 and 09:20 IST, builds one client per run, with no freshness test of its own; its `TokenFreshCheck` compares the token file's modification date with the run date, and the client is not rebuilt after an auto-fix refreshes the token (P01-S192, P01-S193).

**Configuration keys and environment-variable names, and their precedence (question 2).**

- FACT: the A04 paths read the configuration keys and environment-variable names tabled in the P01 evidence, section 11 (P01-S121, P01-S124); the broker modules themselves read no environment variable (P01-S126). Precedence: (1) a YAML value wins over the schema default (A02's loader), and `main.py` passes each configured value explicitly to the A04 constructors, so the constructors' own defaults apply only to callers that omit an argument (the T2 script; tests); `timeouts.connect_sec`, `backoff_sequence_sec` and the four `broker.*` keys have no effect; for `force_intraday_only` the schema default (`True`) differs from the adapter's default (`False`), which equals the file value (`false`); the file value is the one passed in the trading process. (2) The trading client's API key is the value of the variable named by the primary row, which `main.py` copies into `ZERODHA_API_KEY`, overwriting any earlier value; the token goes into `ZERODHA_ACCESS_TOKEN`; the environment itself is assembled outside the code (the service unit, A17, and `load_dotenv()` at import, which, INTERPRETATION (python-dotenv's default), does not override a variable already set; P01-S122). (3) The scripts take a per-account name first and a generic name second, or the per-account name only with `--account`. (4) `deploy/token_watcher.sh` takes the environment value if set and non-empty, else its literal default. (5) Literals, with no key, win by construction (P01-S125, P01-S126).

**Client and account selection against the settled A01 inputs (question 3; recorded, not classified).**

- FACT: (a) the trading process builds one client once and never rebuilds, re-tokens or switches it at run time; (b) the account is still chosen through `config/accounts.csv`, whose primary row, read twice, supplies the name of the API-key variable, whether or not the row is enabled (A01 M-35); (c) the token is not tested locally before the first broker call; (d) the broker pin tests the selected row only after the client has been built and used (exit 9 for a broker other than "zerodha"); (e) across the system's processes there is no single configured client (the script rules above); (f) nothing compares the token file's `api_key` with the environment key, and its `account_id` is compared with the selected row only by the later gate; (g) an authentication failure at the first broker call is reported as a failed clock check (`clock_skew`, exit 3), not as an authentication failure (A01 C8) (P01-S060, P01-S078, P01-S099, P01-S100, P01-S191). The authentication side is in section 4.

**Adapter interfaces and conformance (question 4).**

- FACT: there is no broker-adapter interface or abstraction: no base class, protocol or abstract class, only two concrete classes. `ZerodhaAdapter` has 25 public members (24 methods and one property) (P01-S033, P01-S111). The adapters do not conform to a common contract: the stub matches the Zerodha adapter neither in method set nor in signatures nor in return types. The callers depend on the concrete Zerodha adapter by type annotation, by its private members (`_kite`, `_resolve_tick`; A01 C36d) and its raw client, by methods only it provides, and in one case by a Kite error code (16388) (P01-S113 to P01-S117). INTERPRETATION: an `AngelOneAdapter` put in the Zerodha adapter's place would fail in the boot wiring itself, before any order could be attempted (P01-S117).

**The AngelOne adapter (question 21).**

- FACT: `broker/angelone_adapter.py` is a dormant stub: it has no non-test importer or constructor, every method raises `NotImplementedError`, the configuration key its docstring names as the switch (`broker.fallback_enabled`) has no runtime reader, the place its docstring says it would be wired (`order_placer`) does not mention it, and `main.py` refuses any account whose broker is not "zerodha" (exit 9). No Angel One use can be inferred from the file's presence; whether such use was intended is OPEN (A02 K-01, A02-15) (P01-S105, P01-S110).
