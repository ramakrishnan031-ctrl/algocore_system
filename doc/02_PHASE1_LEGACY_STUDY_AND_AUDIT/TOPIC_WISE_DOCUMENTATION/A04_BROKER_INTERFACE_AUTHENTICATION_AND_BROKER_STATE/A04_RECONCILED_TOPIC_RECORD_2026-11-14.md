## Part A — Study findings (reconciled)

## 3. The broker interface in brief

From STUDY 2, with the AUDIT's refinements applied.

A live start builds one `KiteConnect` client, from the API-key variable that the primary row of `config/accounts.csv` names and the access token in the shared token file `data_store/session/zerodha_token.json`, and one `ZerodhaAdapter` around it; the adapter, its bound methods or the raw client reach every consumer in the trading process. There is no broker abstraction: the AngelOne adapter is a dormant stub, and the `broker` configuration section has no runtime reader. The adapter sends the order actions (placement, cancel, modification and the GTT actions) and the reads (holdings, positions, margins, order history, the order book, trades and quotes) through the SDK; it takes a limiter token before each call, translates SDK exceptions into the system's broker exceptions (cancels and modifications instead return `success=False`), resolves the product, snaps prices to the tick and registers each new order with the in-memory order state machine. It never retries and validates no broker answer; broker statuses are passed through unmapped.

Around it, in the trading process: a four-bucket client-side rate limiter shared by every thread; the order monitor, which polls each watched order's history and publishes fills and status changes; the token monitor and the clock-skew probe, two daemon threads; and the product resolver, the position helpers, the cost calculator and the tick helpers. Tokens are produced outside the process: by the headless refresh declared for 08:15 on the VM, or by the browser-assisted login run by hand or by the PC morning scripts and copied to the VM; the token watcher starts the trading service when it judges the token fresh. The trading start reads the token without checks, makes its first broker call and only then checks the token locally; there is no refresh, reload or re-login in the process, so a rejected token ends in a kill, an exit or a log line, and a new token needs a new start. Outside the trading process, eleven scripts, the pre-flight's broker probe among them, build their own clients with their own credential rules and do not share the trading process's limiter.

The most important facts:

- FACT: one live client, built once and never re-tokened, from the primary row's key variable, before and regardless of the broker pin and the row's `enabled` flag; nothing at construction checks the client, the mode or the credentials (STUDY 3; CL-05, CL-07, CL-09).
- FACT: the start's first broker call (the clock check's quote) comes before the local token gate, and an authentication failure there is reported as `clock_skew` with exit 3 (STUDY 4; A01 C8, kept).
- FACT: `place_order` marks the internal order FAILED on every SDK exception, timeouts included, while the state machine's UNKNOWN_IN_FLIGHT, added for that case, is never entered; `cancel_order` and `modify_order` report a refusal, a timeout, a rejected token and a 429 alike as `success=False` (STUDY 6; OA-08, OA-20). [refined: section 6, row 5: the order placer writes UNKNOWN_IN_FLIGHT as a trade status through the order manager (A10), a different record.]
- FACT: `main.py` builds the order reconciler without the order placer, so its in-flight recovery, the only reader of `get_all_orders` and of the placer's timeout queue, cannot run under this wiring (STUDY 8; CS-08).
- FACT: the order monitor maps seven broker strings and is silent for every other, transitional statuses included; it reads a `status_message` attribute that the history entry does not have, so no broker rejection text leaves it; at restart, rows stored as OPEN, PARTIAL or TRIGGER_PENDING are brought forward only one step from PENDING (STUDY 10; MO-01, MO-03, MO-09).
- FACT: the only implemented request limits are four per-second token buckets inside one process; no per-minute or per-day order budget, no limit shared across processes, and no escalation of sustained 429s exists (STUDY 9; RL-01, RL-06, RL-14). [refined: section 6, rows 2 and 3: single 429s and client-side limits do reach kills on some paths, and the kill switch's counter is reset only at construction.]
- FACT: `broker_net_qty` nets a symbol across every product (and, with no exchange field, every exchange), while each caller exits under one product (STUDY 11; PR-10).
- FACT: every round trip is costed as a BUY at the entry and a SELL at the exit, costing happens only at a close, and a costing failure books zero charges with no mark (STUDY 12; CG-01, CG-05, CG-07).

### 4.2 Runtime authentication, the token lifecycle and clock skew (STUDY 4)

- FACT: one shared token file holds `account_id`, `broker`, `access_token`, `api_key`, `date`, `saved_at` and `expires_at`; `save_token` writes it in place with best-effort modes 0600 and 0700 (A03 G-11, kept). `is_token_valid` accepts a token whose `account_id` matches, whose `date` is the current IST date and whose token is not empty; `expires_at` (the next 05:00 IST) is used for no decision (AU-04).
- FACT: `save_token` is called by the browser-assisted login CLI, by the headless refresh, and by a call path in the trading process's interactive start that is unreachable at the baseline (A01 C1). INTERPRETATION: token creation occurs only through the external paths.
- FACT: the live start's pre-load reads the token file with no checks and sets that token on the one client; the first broker call precedes the local gate; a missing or unreadable file ends in exit 2 (A01 C2), a token the broker rejects in `clock_skew` and exit 3 (A01 C8), a token object without `access_token` or a token for the wrong account or date in exit 6. Nothing compares the token file's `api_key` with the client's key, and no start step checks the client's identity.
- FACT: the token monitor calls `profile()` every `check_interval_sec` (1,800 s, a literal passed by `main.py`; the first check one interval after its start), within market hours; on an expiry it logs CRITICAL, sends a "TOKEN EXPIRED" notification and soft-kills, latching once per episode; it never hard-kills, logs in or refreshes. `classify_broker_auth_error` classes an error by its message text only, so every "permission denied" is the IP-allowlist case and any text containing "token" is a token expiry (INTERPRETATION).
- FACT: a rejected token is detected by the token monitor (soft kill), the order monitor (hard kill after three consecutive failures, after which it stops), the reconciler (soft kill after three cycles), the probe (an ERROR line per interval), the kill switch's failure recorder and the live feed. INTERPRETATION: no detecting site recovers by itself. The shutdown-time token rename (FIX-062) exists but cannot be armed in the wired code (A01 C3).
- FACT: the adapter installs a response hook, when the SDK's client exposes an HTTP session with hooks (UNKNOWN for the installed SDK), that stores the parsed HTTP `Date` header without a lock; `get_server_time` resets it, makes a quote call and returns the captured header time or, failing that, the local clock. INTERPRETATION: a caller cannot tell a header reading from the local fallback, and another thread's response can supply the value. The probe records broker time minus the round-trip mid-point with the time authority; `main.py` wires only the critical-skew callback (A01 C30).

### 4.3 Token tooling outside the trading process (STUDY 5)

- FACT: `scripts/auto_refresh_token.py` runs a trading-day guard first, with no bypass; it logs in with the account's user identifier, password and second factor read from environment-variable names, exchanges the request token and writes the shared file through `save_token`; up to three attempts on network errors; exit 0 with an INFO alert and a SUCCESS heartbeat, or exit 1 with a CRITICAL alert and a FAILED heartbeat, the alerts only when the notifier is configured.
- FACT: `deploy/token_watcher.sh`, a root bash loop run by its unit (A17), starts `trading-system.service` when the unit is not running, within 08:00 to 16:00 IST, when `token_is_fresh` passes (a parsable object, today's IST date, a non-blank token; no account test) and as its exit-status contract allows; it skips the whole iteration, silently, while `zerodha_token.json.tmp` exists (A03 E-47, kept).
- FACT: the two PC morning scripts test the PC's token file (by its `date` or by the file's last-write date), run the login CLI with a literal account when the test fails, copy the file to the VM's final name with `scp` and check the service; `scripts/copy_token_to_vm.bat` (FIX-040) copies to a temporary name and renames it. FACT (declarations): `token_cleanup` deletes the token file at 05:00 every day and `auto_refresh_token` runs at 08:15 Monday to Friday; the crontab has no `CRON_TZ`, so the times are IST only if the VM's zone was IST (UNKNOWN).
- FACT: two producers write the token record through `save_token`; three routes copy the PC file to the VM, two writing the final name directly; five freshness tests in the tooling use different criteria, account tests and date bases; the refresh's `--account` selects any row and saves to the same file. INTERPRETATION: the refresh can also run through the pre-flight's token fix (A20) and the trading start's launch of a missed pre-flight phase; a token written while the trading process runs is not taken up by it; a VM boot before 08:00 IST leaves a clean exit 0 that holds the watcher for the rest of the day.
- FACT: no tool takes a lock; the refresh and the PC login save in place, the morning copies write the final name, and only the FIX-040 copy replaces it atomically (A03 E-11, G-11, kept). INTERPRETATION: a reader can meet an empty or partial file, and a `.tmp` left by a failed copy stops every action of the watcher with no log line.

### 4.4 Adapter order actions, retries and uncertain outcomes (STUDY 6)

- FACT: `_translate_kite_exception` logs the original at ERROR and maps, in a fixed order, `TokenException` and `PermissionException` to `BrokerAuthError`, `NetworkException` and the built-in timeouts to `BrokerTimeoutError`, `InputException` and `OrderException` to `OrderRejectedError`, `GeneralException` and anything else to `BrokerError`. INTERPRETATION and UNKNOWN: an HTTP-library timeout that the SDK does not wrap would reach callers as a plain `BrokerError` (OA-01).
- FACT: a broker 429 on `place_order`, a GTT action or a read freezes the category's bucket and raises `BrokerRateLimit429Error`; on cancels and modifications it is reported only as `success=False`; the adapter never retries.
- FACT: `place_order` validates its inputs, snaps prices to the tick, coerces and resolves the product, takes the CNC lock and registers the order (PENDING), then takes a limiter token and calls the SDK: SUBMITTED on a return, with the SDK's answer turned into the broker order id unchecked; FAILED on any SDK exception; PENDING left if the limiter raises. The GTT actions validate nothing; no action validates the broker's answer; the tag is cut to 16 characters (A01 M-16).
- FACT and INTERPRETATION: `place_order` and `place_gtt` send no idempotency key; after an exception raised once the request has left the process, the broker outcome is unknown, but the adapter records FAILED, which is terminal in the state machine; the order placer treats `BrokerTimeoutError` as an unknown outcome and any other `BrokerError` as a definite failure (A10).

### 4.5 Adapter reads and the translation of broker state (STUDY 7)

- FACT: no read maps a broker order status into a system status; `get_open_orders` keeps `OPEN` and `TRIGGER PENDING` only. Shape conventions differ: data classes, unconverted dictionaries, the SDK's own object and a bare float; the symbol key differs; no read returns an exchange.
- FACT: product codes are passed through with different defaults for an absent key; a field present with the value `None` and converted with `str()` becomes the string "None" in five places.
- FACT: `get_margins` raises the translated exception on an SDK failure, returns all zeros for a `None` or non-dictionary response and 0.0 for an absent field, with no mark; `get_live_margin_pct` caches a fraction per symbol and intent for 300 s, and a missing `total` is cached as 0.0. The position sizer is built without the adapter, so its live-margin path is not reached in the `main.py` build and the static leverage table decides.

### 4.6 The broker call-site map (STUDY 8)

### 4.7 Rate limits and concurrency (STUDY 9)

### 4.8 The order monitor and the order state machine (STUDY 10)

- FACT: one in-memory order state machine of nine states (PENDING, SUBMITTED, OPEN, PARTIAL, COMPLETE, CANCELLED, FAILED, EXPIRED, UNKNOWN_IN_FLIGHT) refuses any transition outside its table, has no persistence and is queried by no non-test code; UNKNOWN_IN_FLIGHT and EXPIRED are never entered.
- FACT: one monitor polls `get_order_history` once per watched order every cycle; two global counters count failed polls, not cycles; the authentication counter fires the critical callback, wired to a hard kill, at a fixed 3, the general counter at `max_api_failures`, and the thread then ends and is not restarted.
- FACT: the mapping covers seven broker strings and is silent for every other; an OPEN-set row with a positive fill records no fill; six paths cancel an order, none re-reads the broker after a cancel and none passes `variety`; a cancel that fails in the fill-timeout path sets FAILED, stops polling and fires the orphan callback.
- FACT: on restart the state machine, the watch list and the counters are lost; `rehydrate_from_store` reloads open `orders` rows and registers each in PENDING, from which only SUBMITTED is allowed, so a reloaded order whose broker status is COMPLETE, CANCELLED or PARTIAL meets a refused transition on every cycle (MO-09). The force-close date lives only in memory.
- FACT: three status vocabularies meet (the broker's strings, the nine states, which the schema names for `orders.status`, and extra strings at the storage boundary and in consumers); the "broker open", terminal and "still open" sets differ by file (A03-34 holds the stored-status side).

### 4.9 Product resolution and the position helpers (STUDY 11)

- FACT: `ProductResolver` translates four intents fixed in code into the broker's codes from `product_map` (BRACKET_ORDER mapped to the empty code); its constructor checks only that the map is non-empty; `resolve` raises `ValueError` for an unknown intent and `ProductNotSupportedError` for an unknown broker or an empty code; a non-empty code is returned unchecked.
- FACT: in `place_order`, while `force_intraday_only` is on, every intent other than the exact string "INTRADAY" is coerced to INTRADAY first; the screener's MIS gate and seven order-placer sites resolve the uncoerced intent. The exchange is the literal "NSE"; 121 lines in 30 non-test files hold product-code literals outside the resolver (A02 K-06, A01 M-29).
- FACT: `broker_net_qty` sums the `qty` of every positions row of the symbol, whatever its product, and returns `None` on any failure; `determine_close_direction` falls back to the caller's side and quantity when the read failed, with no record; `Position` keeps one row per broker row and drops the "day" list. ### 4.10 Costs and slippage (STUDY 12)

- FACT: one calculator is built at `main.py` L2350 and passed to the adapter (which never reads it), the order placer, the CNC GTT monitor and the reconciler; every call is at a close; no caller passes `exchange`, `is_fno` or `fno_kind`.
