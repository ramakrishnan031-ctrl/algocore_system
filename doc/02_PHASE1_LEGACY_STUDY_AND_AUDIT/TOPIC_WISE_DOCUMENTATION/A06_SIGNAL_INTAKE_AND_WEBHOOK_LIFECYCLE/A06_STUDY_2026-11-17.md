## 1. Purpose, scope, exclusions and fixed baseline

This STUDY establishes, from the code at the fixed baseline, how an incoming scanner signal travels from its external ingress boundary to the accepted or queued signal event handed to A07: scanner and webhook ingress, authentication and validation, deduplication, throttling, queueing, expiry and signal-event creation (Document 08, section 3, coverage item 5). ### 1.5 Method

The legacy repository was read only from a local read-only clone at the baseline, with `git show`, `git grep` (every repository-wide search excluding `config/accounts.csv`, `.env*` files, `*.local.yaml` files and token files), `git log`, `git diff`, `git blame` (hashes and dates only), `git ls-tree` and `git rev-list`; source text was parsed with Python's `ast` module, and configuration text with `yaml.safe_load`, both of which execute nothing. Nothing was run, imported, built or written; no broker, API, database, scanner URL, webhook or Chartink page other than Chartink's public help pages was contacted.

The fieldwork was divided into eleven parts (P01 to P11, section 20). Each part was written by a read-only helper and then checked statement by statement against its sources, and corrected, by a separate read-only helper; the check log of each part is the last section of its evidence file. At most two helpers ran at a time, a new pair starting only when both of the previous pair had finished (the method Rama approved on 17-Nov-2026; the Topic Completion Register, entry A06). Working drafts were backed up after each section to the temporary branch `wip/a06-fieldwork`, which holds the working drafts, notes and helper tools, is never merged into `main`, and is deleted when A06 no longer needs it. Claude prepared the briefs, had the STUDY assembled by a read-only helper, and had it checked independently against the evidence and the code. ## 2. Signal intake in brief

A summary for orientation, for a reader new to A06; each point is established in the section named, with its evidence. Nothing here says what ran in production: every runtime fact is UNKNOWN / NOT ESTABLISHED (section 1.6).

```
 Chartink alert --POST /webhook/<scanner_name>--> waitress (8 threads) --> WebhookReceiver
   per-IP limit -> authenticate (sha256= header or ?token=) -> scanner key -> [eod: PB-01 capture worker (A18)]
   -> kill switch -> backpressure (240/300) -> entry window -> parse -> per symbol:
      alias -> excluded? -> price, age -> claim (symbol) -> TTL key -> fingerprint INSERT signals QUEUED
      -> put_nowait 5-tuple --> signal_queue (300, FIFO, memory) --> sp-dispatcher --> executor (5 workers)
   webhook_audit row per audited request                        |
                                                                 v
   _process_one: PROCESSING -> kill switch -> window -> age (600 s) -> shadow guard -> strategy lookup
      -> strategy control, window, governor -> screen() (A07) -> prices, sizing, risk, reserve (A09)
      -> INTRADAY SIGNAL alert (A14) -> late checks -> EntryThrottle.admit -> place() (A10)
   finally: release_in_flight(symbol) to the receiver
```

- **The receiver.** One Flask app with two routes, `POST /webhook/<scanner_name>` and an authenticated `GET /health`, served by waitress in a daemon thread with a fixed pool of eight worker threads on all interfaces, port 5000 (repository values). It is built at boot before the processor, starts its in-flight sweeper at construction, and is reachable only once the server starts, last. Its `stop()` only sets two events; the server is never stopped (section 3) (P01-S009, P01-S017, P01-S025, P01-S064, P01-S065, P01-S068, P01-S072, P01-S080).
- **Authentication.** At the repository value `require_hmac: false`, a request passes with a correct `sha256=` signature over the raw body or with a `token` query parameter equal to `WEBHOOK_SECRET`, which start-up requires; nothing else in the code restricts who may connect. The A02-13 history stays OPEN (section 4) (P02-S015, P02-S016, P02-S040, P02-S042).
- **Validation and answers.** The scanner name is the URL path segment, which must be a map key; the body must be JSON with `stocks`, `trigger_prices` and `triggered_at` (taken as IST); unknown keys are ignored; the kill switch, back-pressure and entry window are checked before the body is parsed; end-of-day alerts go to the PB-01 capture worker and skip those gates. Each audited request writes one `webhook_audit` row, but several kinds of request write none (section 4) (P01-S034, P01-S052; P02-S043, P02-S049, P02-S055, P02-S069).
- **Duplicates, limits and claims.** Three duplicate layers with different keys and windows (a per-symbol in-flight claim, a 300-second TTL cache, a stored fingerprint per five-minute slot and day); one per-IP token bucket (60, then 5 per second); a request-level 503 at a depth of 240 and a per-symbol `QUEUE_FULL` at 300. With no heartbeat wired, the sweeper evicts every claim older than 60 s. A provisional KNOWN DEFECT: claims kept after an exception in the fingerprint-conflict handler (section 5) (P03-S001, P03-S020, P03-S034, P03-S037; P01-S079).
- **The event and the queue.** The signal event is one `signals` row (status `QUEUED`, the scanner name also written as the strategy), committed before a 5-tuple is put on an in-memory FIFO queue of 300 that only the processor drains. The dispatcher moves each item at once into an unbounded executor queue for five workers, so the receiver's back-pressure sees only the dispatcher's buffer. Nothing re-reads queued rows at start-up (sections 6 and 8) (P01-S008; P05-S001, P05-S006; P04-S014, P04-S050; P04-S020).
- **The processor, up to the screening call.** Each worker writes `PROCESSING`, re-checks the kill switch and the window, rejects signals older than 600 s from `triggered_at` (the receiver applies the same limit), applies the shadow guard, resolves the strategy from the scanner map and runs the strategy-level gates, then calls A07's screening. Where A06 ends and A07 begins (at the dequeue, or at the screening call) is OPEN FOR RAMA (sections 6, 13 and 17) (P04-S028 to P04-S033, P04-S036; P05-S030, P05-S031).
- **After the handoff, at the interface.** Price derivation, sizing, risk and reservation (A09), the `INTRADAY SIGNAL` alert (A14), the entry throttle (A06's module: at most one admit per 20 s, three per 60 s and one per symbol per 300 s at the repository values, counted at the admit before `place()`), placement (A10), and the S&R, V3 and allocator hooks (A08, A18). A04's limiter is never called by A06 code under `main.py` (sections 9 and 13) (P05-S036, P05-S048; P06-S008, P06-S021, P06-S034).
- **Chartink and the scanner checks.** Sixteen scanner keys, each equal to its strategy name, with placeholder-pattern screener URLs used only by an outbound reachability check (a GET with 2xx success at boot, a warning only; and the operator script, exit code 1), which shows nothing about whether alerts reach the receiver (section 10) (P07-S009, P07-S011, P07-S033, P07-S042, P07-S047).
- **Storage and consumers.** A06 writes `signals`, `webhook_audit` and the `pb01_capture` heartbeat; the audit counts and the stored rows do not reconcile on several routes; rows left `QUEUED`, `QUEUE_FULL`, `PASSED` or `RESERVED` are never reaped; `/metrics` reports the queue as 0, so A20's back-pressure check always passes (sections 8 and 14) (P11-S025, P11-S034, P11-S050).
- **The main unknowns.** Whether any request arrived or any signal was processed; the effective configuration (no overlay read); the installed library versions; the network path in front of port 5000 (the deployment document describes a loopback bind behind a proxy, the configuration an all-interfaces bind); Chartink's retry behaviour and payloads; and whether production ran the commits after `7d4970a` (section 18.2) (P01-S109, P01-S110; P10-S188; P07-S051).

**The single authentication decision, `_authenticate` (B6).** FACT (L298 to L354; one decision since the C6 refactor of 2026-07-25): in this order (P02-S015):

| Step | Lines | Condition | Result |
|---|---|---|---|
| a | L330 to L331 | the secret is empty or `None` | authenticated without a check (the comment calls this test-only, as the secret is a required start-up secret) |
| b | L333 to L334 | reads the header `X-Webhook-Signature` and the query parameter `token` | — |

| d | L343 to L349 | otherwise, `require_hmac` true | 401 (token not accepted) |
| e | L350 to L353 | otherwise, a `token` is present | `hmac.compare_digest(token, secret)`; mismatch 401 "Invalid token" |

- FACT: on `/webhook` the signed payload is the raw body exactly as read; no timestamp, nonce, expiry or request identifier is signed or checked; the token is a fixed value in the URL. INTERPRETATION: a copy of an accepted request authenticates again if re-sent; repeats are then subject only to deduplication, in-flight claims and expiry (P02-S019; section 5). Current external context: `hexdigest()` gives hexadecimal digits (letter case not stated on the page read; INTERPRETATION: a signature differing in case would not match); with several `token` parameters only the first is compared (P02-S020, P02-S021).

**The `admit(symbol)` algorithm (C11).** FACT: when enabled, the whole decision runs under one `with self._lock:`; it reads the clock once and tests three gates in a fixed order, returning at the first that blocks (P06-S008):

| Order | Gate | Applies when | Blocks when | Category |
|---|---|---|---|---|
| 1 | global minimum gap | gap > 0 and an earlier admit exists | `now - _last_entry < _min_gap` | `min_gap` |
| 2 | global burst | burst count > 0 | after removing times strictly older than `now - window`, `len(_recent) >= burst_max` | `burst` |
| 3 | per-symbol cooldown | cooldown > 0 and `symbol` truthy | `now - _per_symbol_last[symbol] < cooldown` | `per_symbol` |

- FACT: if no gate blocks it records `_last_entry`, appends to `_recent`, records the symbol (if truthy), counts an admit and returns allowed. A blocked call records nothing; exactly one counter rises per call. INTERPRETATION: rejected attempts extend no gap, window or cooldown; the precedence matches the docstring's "global takes precedence" (HISTORICAL) (P06-S008, P06-S009). The time recorded is the time of the `admit()` call, which the module calls "the placement" (HISTORICAL); the module cannot know whether an order follows (P06-S010).
- FACT and INTERPRETATION (boundaries): the gap and cooldown tests are strict; an entry exactly one window old still counts and the `burst_max`-th entry is the last admitted; the first admit of the process meets no gap or cooldown; an empty symbol skips the per-symbol gate; the per-symbol key is the exact symbol text, with no case folding, stripping, prefix or suffix handling (at the fused site it is the receiver's post-alias symbol, kept in its received case on an alias miss) (P06-S011). `_recent` is pruned only inside the burst gate, so with the burst gate off and another gate on it grows for the life of the process; `_per_symbol_last` is never pruned (P06-S012; not at the file values). The reason text rounds the configured settings (`:.0f`) (P06-S013).
- INTERPRETATION (arithmetic at the repository values gap 20 s, window 60 s, burst 3, cooldown 300 s): any two admits are at least 20 s apart, so the burst gate can block only in the exact case of four attempts exactly 20.0 s apart; in effect the gap gate and the cooldown do the work. HISTORICAL: a legacy decision file reports "Of 139 throttles, 132 are that one gate (7 per-symbol, 0 burst)", a report, not proof (P06-S014). The cooldown runs from one admitted entry to the next attempt for that symbol text and has no input from fills, exits or positions; HISTORICAL: a legacy verification of 2026-08-07 reached the same reading (P06-S015). HISTORICAL: a unit test commented "4th in 60s -> burst" asserts only `not allowed`; by the code that attempt is blocked by the gap gate (P06-S016).
