## 2. The storage system in brief

- **One engine, two files.** FACT: the only database engine in non-test code is SQLite through Python's `sqlite3`; the code defines two database files, the trading database `data_store/trading_system.db` and the analytics database `analytics.db`, which always sits beside whatever main path is opened and is attached to main connections as schema `analytics` (connections evidence, P01-S001 to P01-S003). No configuration key names either file for the trading application (P01-S006).
- **Working-directory paths.** FACT: the trading process opens the store with the relative literal `data_store/trading_system.db` (`main.py` L2233 to L2237); 13 other openers and the heartbeat helper also use relative defaults, while most scripts anchor the path to the project root (P01-S007, P01-S132). INTERPRETATION: which file a relative path reaches depends on each process's working directory (P01-S008).
- **Per-thread connections with WAL and FULL sync.** FACT: `StateStore` keeps one connection per thread (`threading.local`), opened with `isolation_level=None`, `timeout=30` and the PRAGMAs `journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`, `temp_store = MEMORY`, `busy_timeout = 30000` (P01-S018 to P01-S020). `transaction()` is `BEGIN IMMEDIATE` with `COMMIT` or `ROLLBACK` and no nesting or retry (P01-S033 to P01-S044). `close()` closes the calling thread's connection only (P01-S046).
- **Many openers, several connection styles.** FACT: 26 non-test `StateStore(...)` constructions in 26 files, of which only `main.py` may migrate (migrations evidence, P03-S032, P03-S066); 21 files outside `core/` open SQLite otherwise, 12 of them with a raw `sqlite3.connect`, without the store's PRAGMAs (P01-S029, P01-S030, P01-S133). Every heartbeat write constructs a full `StateStore` (P01-S164).
- **Schema.** FACT: `core/schema.sql` declares 45 tables (577 columns), 73 named indexes, one trigger and no view; every CREATE uses `IF NOT EXISTS`; the file's only data statement stamps `schema_version` to `'45'` with `INSERT OR REPLACE` (schema evidence, P02a-S455; P02b-S431 to P02b-S436, P02b-S404). `core/analytics_schema.sql` declares 3 tables and 4 indexes and has no version marker (analytics evidence, P07-S053 to P07-S056).
- **Schema applied on every open; migration only from the boot path.** FACT: every `StateStore` construction initialises the analytics schema, reads the stored version, refuses a newer database, refuses a pending migration unless `allow_migrate` is true and the market is closed, and then runs the whole `schema.sql` with `executescript` (P03-S001 to P03-S010). Migrations rebuild whole tables to the current definition, one transaction per table, with no backup first (P03-S076 to P03-S087, P03-S124, P03-S145).
- **The store API.** FACT: about 120 query and write helpers; each write method runs one `transaction()`; few methods catch errors; `_best_effort_insert` swallows every exception for the three slippage tables (store API evidence, P04-S012 to P04-S015; P05-S148; records check, P10-S240). Many writes bypass the typed methods through `transaction()` or `execute` with SQL held in the calling module (runtime SQL evidence, P06a-S185; scripts SQL evidence, P06b-S373).
- **Files.** FACT: logs are daily JSON-lines files written through a queue by `core/logger.py`, with no rotation or retention in code (runtime files evidence, P08a-S094, P08a-S143); other families under `data_store/` (sentinels, evidence, V3 and allocator JSONL, state files, locks, pre-flight and security files) use three write disciplines: temporary file plus rename, append, or in-place overwrite, with `fsync` in three writers only (P08a-S139; script files evidence, P08b-S012, P08b-S033).
- **Backups, retention and checkpoints.** FACT (declarations; A16): the two databases are backed up nightly by the `sqlite3` command-line `.backup` into `data_store/backups/`; the six A03 scripts copy the evidence JSONL files, drill-restore the newest main backup into a temporary copy, prune backups by count, delete old rows from six tables, prune report and log files, and run a PASSIVE WAL checkpoint (backup evidence, P09a-S003 to P09a-S007; retention evidence, P09b-S008 to P09b-S010). FACT: every backup lands under the project's `data_store/`; no line read copies any artefact to another machine (backup evidence, concern 20).
- **Runtime.** UNKNOWN / NOT ESTABLISHED: whether any database existed, at which version and with which rows, and whether any job ran (section 14.2).

### 3.3 `transaction()`, `execute`, `fetch_one` and `fetch_all`

- FACT: `transaction()` (L505 to L543) takes the calling thread's connection, runs `BEGIN IMMEDIATE`, yields a cursor, runs `COMMIT` on normal exit and, on any `Exception`, `ROLLBACK` (a `sqlite3.Error` from the `ROLLBACK` itself is swallowed) and re-raises; the cursor is closed in `finally` (P01-S033). HISTORICAL: `BEGIN IMMEDIATE` takes the write lock at the start to serialise writers (H-5; P01-S034).
- FACT: there is no nesting support (no `SAVEPOINT`, no check for an open transaction; the docstring says nesting is not supported), no retry anywhere in L1 to L617, and `TransactionError` is defined but never raised or caught in non-test code (P01-S036, P01-S039, P01-S044).
- INTERPRETATION (SQLite and Python semantics): a held write lock makes `BEGIN IMMEDIATE` wait 30 seconds and then raise `sqlite3.OperationalError`; a nested `transaction()` on the same thread would fail at the inner `BEGIN` and its `ROLLBACK` would undo the outer work; a `KeyboardInterrupt` or `SystemExit` in the body skips the `ROLLBACK` and leaves the transaction open on that connection (P01-S035, P01-S037, P01-S038). HISTORICAL against INTERPRETATION: the docstring says foreign-key violations roll back at `COMMIT`; in SQLite an immediate foreign key fails the statement itself (P01-S040).
- FACT: `execute(sql, params)` returns the connection's cursor with no handling, commit or close; `fetch_one` and `fetch_all` close their cursor in `finally`; none catches or retries (P01-S041, P01-S043). INTERPRETATION: outside a transaction an `execute` commits by itself; an unread SELECT cursor keeps a WAL read snapshot (P01-S042).
- FACT: `table_names` reads the unqualified `sqlite_master` (the main catalogue only); `row_count` accepts a name only if it is alphanumeric apart from underscores and builds its SQL by string formatting (P01-S045).

### 3.4 `close()`, `checkpoint_wal()` and `checkpoint()`

- FACT: `close()` closes only the calling thread's connection; the next call on that thread re-opens lazily. Its docstring says other threads' connections "remain open until they close themselves" and that each thread should call `close()` before exiting (P01-S046, P01-S047). FACT: `store.close()` appears only in `main.py`, one report, scripts and `utils/cron_heartbeat.py`; no runtime worker module calls it, and `main.py`'s `_shutdown` closes the main thread's connection only (P01-S048, P01-S049).
- FACT: `checkpoint_wal()` runs `PRAGMA wal_checkpoint(PASSIVE)`; `checkpoint(live_feed=None)` runs `PRAGMA wal_checkpoint(TRUNCATE)` unless it is called from the live feed's ticker thread with that feed passed (FIX-088), in which case it returns zeros with `skipped: True` without running the PRAGMA; otherwise both return `{busy, log, checkpointed}`, and neither has error handling (P01-S051, P01-S052).
- FACT: callers: `checkpoint_wal` in `main.py` `_shutdown` L1816 (a failure is logged as a warning) and in `scripts/wal_checkpoint.py` L33; `checkpoint` in `orders/eod_squareoff.py` `EodSquareoff._fire` L501, with no argument (a failure is logged and the EOD run continues). `_fire` is reached from the EOD poll thread, the daily-loss breach callback and the start-up restart recovery, so the checkpoint runs on whichever of those threads reaches it (P01-S053, P01-S055). INTERPRETATION: the FIX-088 guard cannot activate at the baseline (P01-S054).
- INTERPRETATION (SQLite semantics): PASSIVE copies what it can without waiting; TRUNCATE waits up to the 30-second busy wait and reports a block as `busy = 1` in its result row rather than raising; an unqualified `wal_checkpoint` also checkpoints the attached `analytics.db`, while the returned figures describe `main` (P01-S056, P01-S057).
- FACT: the pre-flight auto-fix whitelist names `wal_checkpoint_passive`, but no pre-flight check declares that fix (P01-S061). The restore drill's own PASSIVE checkpoint runs on its temporary copy (P01-S062).

## 5. Migrations and schema versioning (C)

### 5.1 How the schema is applied on open

FACT (migrations evidence, P03-S001 to P03-S010): migration happens inside the `StateStore` constructor; there is no separate migrate call.

1. `__init__` stores `allow_migrate` and `market_open` (both default False), creates the database's parent folder and calls `_initialize_schema` (L172 to L198).
2. `schema.sql` must exist, else `StateStoreError`; it is read as text (L363 to L369).
3. `db_connect.init_analytics_schema` creates or updates `analytics.db` on its own connection (L375).
4. The calling thread's store connection is opened, with its PRAGMAs and the analytics ATTACH (L377).
5. The stored version is read before anything is applied: `SELECT value FROM schema_meta WHERE key = 'schema_version'`; a missing table, a missing row or a non-integer value gives `None` (L379 to L383, L457 to L474; P03-S012).
6. Newer-database gate: a stored version above `EXPECTED_SCHEMA_VERSION` (45, L102) raises `SchemaVersionMismatch`, whatever the flags (L398 to L405).
7. Older-database gate: a stored version below 45 calls `_refuse_migration` (CRITICAL log, attempted sentinel, `MigrationNotPermitted`) unless `allow_migrate and not market_open`; otherwise `run_migrations` and then `relocate_analytics_tables` run (L420 to L440).
8. `conn.executescript(schema_sql)` runs (L446), reached only when both gates pass.
9. `get_schema_version()` is compared with 45; a difference raises `SchemaVersionMismatch` (L449 to L455).

- FACT: no non-test code uses `PRAGMA user_version`; the target exists as two literals, the constant at `core/state_store.py` L102 and the text in `core/schema.sql` L1610, which agree at the baseline and are compared only after the stamp is written (P03-S014 to P03-S017). `core/analytics_schema.sql` has no version marker (P03-S018).

### 5.2 Outcome by database state

FACT (P03-S019 to P03-S025, P03-S221):

| Database state at open | What the code does |

IF NOT EXISTS` skips them and the three `DROP ... IF EXISTS` run. ### 5.5 Atomicity, idempotency, failure and restart

- FACT: each table rebuild is one transaction; the whole run has no enclosing transaction, and the relocation commits table by table; `executescript` runs with no `BEGIN` in `schema.sql`; the version is recorded only by the last statement of `schema.sql` (P03-S122, P03-S124, P03-S126, P03-S127). INTERPRETATION (SQLite semantics): DDL is transactional, so a failed rebuild leaves that table as it was; the relocation's commit spans two WAL files and is atomic per file, not across them; under `executescript` each statement commits on its own (P03-S123, P03-S125, P03-S126).
- FACT and INTERPRETATION: the skip test compares a target text that ends with `;` (the extractor keeps it and the normaliser does not remove it) with the stored text, which SQLite keeps without the `;` (shown on SQLite 3.53.1 by synthetic tests); on that reading every listed table in range is rebuilt on every migration run, even when it already matches (P03-S130, P03-S131).
- INTERPRETATION: the copy keeps only columns present in both definitions; a new NOT NULL column without a default, or data breaking a new CHECK, makes the copy fail when the table has rows; for the six rebuilt AUTOINCREMENT tables the counter restarts from the highest copied id (P03-S102, P03-S133, P03-S134).

| Failure route | What the code leaves | Evidence |
|---|---|---|
| Rebuild of table k fails (constraint, lock beyond 30 s, FK check) | table k rolled back; tables rebuilt earlier in the run stay rebuilt; no relocation, no `executescript`; version unchanged; `MigrationError` out of the constructor | P03-S135, P03-S136 |
| Relocation of table t fails | t rolled back; tables moved earlier stay moved; version unchanged; the raw exception (not wrapped) | P03-S106, P03-S137 |
| `executescript` fails after a migration | rebuilds and relocation committed; statements before the failing one applied; version unchanged; raw `sqlite3` error | P03-S138 |
| Post-check mismatch | stamp already written; `SchemaVersionMismatch` | P03-S139 |
| Process killed mid-rebuild | INTERPRETATION: the open transaction is rolled back at the next open; the leftover temporary table is dropped by the next attempt | P03-S140 |
| Restart after a failure | the stored version is still old: an allowed opener runs the whole range again; a non-allowed opener refuses again | P03-S141, P03-S142 |

- FACT (boundary, A17): the repository's unit declares `Restart=on-failure`, `RestartSec=10` and `RestartPreventExitStatus=3 4 5` (P03-S143). INTERPRETATION: a deterministic migration failure (exit 2) or a market-hours refusal (exit 1) would be followed by a new start every 10 seconds while the start window allows; the first restart after 15:30 would see the market closed and migrate (P03-S144).
- FACT: no backup or copy is taken by the code before migrating; HISTORICAL: deploy notes describe operator backups before deploys (P03-S145, P03-S146).

## 6. The state-store API and persistence contracts (D)

### 6.1 Shape of the API

- FACT: L618 to L1901 define 46 methods (31 read-only, 15 writing) and three class constants of status sets; L1902 to L3355 define 74 methods (with `__repr__`) and five column tuples (store API evidence 1, P04-S009; store API evidence 2, P05-S001). The records check counts 137 methods in the class, about 120 of them query or write helpers (records check, P10-S240).
- FACT: the read methods of L618 to L1901 use `fetch_one` or `fetch_all` outside a transaction (P04-S010); in L1902 to L3355 four read methods run their SELECT inside `transaction()`: `get_all_gate_state`, `get_all_retest_state`, `get_pb01_watchlist_for_date` and `get_daily_symbol_stats` (P05-S157). INTERPRETATION: those four take the write lock for a read; other reads are separate autocommit snapshots, so two reads in a row are not one snapshot (P04-S011; P05-S157).

### 6.2 Transactions and atomicity across calls

- FACT: each write method runs one `transaction()` with one write statement (`bump_tgt_retry` adds a SELECT); the only multi-statement atomic writes are `release_gate_state` and `release_retest_state` (delete the parking row and set the signal status) (P04-S012, P04-S014, P04-S242; P05-S167).
- FACT: L618 to L1901 hold no `try`, `except`, `raise` or logging; outside `_best_effort_insert`, no method of L1902 to L3355 catches database errors; every SQLite error propagates after the transaction rolls back (P04-S015; P05-S168). No method retries; retries exist only in callers (P04-S151; P05-S169).
- FACT: callers combine separately committed calls that are not atomic as a whole, for example the reconciler's manual-close sequence, the recovery adoption, the EOD write-ahead log, the screener's status-then-row writes, the gate add, the GTT exit and recreate sequences, the PB-01 and retest confirmations (P04-S153; P05-S171 to P05-S172, P05-S221 to P05-S224). INTERPRETATION: a crash or failure between them leaves the earlier commits in place; for the GTT exit, a stop after the close and before the financials leaves a closed trade without exit price or P&L, which the next pass treats as a duplicate (P05-S172).
- FACT: no non-test caller calls a range method lexically inside a `with ... transaction()` block; dynamic nesting was not traced (P04-S019). Three `update_signal_status` calls and the fund manager's rehydration reads run while the fund manager's re-entrant lock is held (P04-S243).

## 16. Questions for Rama about intent

The code shows what is implemented; these questions concern what was intended, where the code and its own comments or documents differ or are silent. They are not decisions, and none is answered by this STUDY. Questions that belong to other topics, are already open, or fall under the security instruction are listed at the end of section 13.

1. Database path: was the trading process meant to rely on its working directory for `data_store/trading_system.db` and its other files, when most scripts anchor the path to the project root; and was the heartbeat of a script run with `--db` meant to go to that same database (P01-S146; P08a-S174; P08b-S266)?
2. Read-only use: were report, check, cron, research and dry-run processes meant to open the live database write-capable (and, where they open through `StateStore`, re-apply both schema scripts on every open and create `analytics.db` if it is missing), rather than read-only (P01-S147; P06b-S444; P07-S186; P09b-S174)?
