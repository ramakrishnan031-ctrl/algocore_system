## 3. `transaction()`, `execute`, `fetch_one`, `fetch_all` and the introspection helpers

| ID | Statement | Label | Evidence |
|---|---|---|---|
| P01-S033 | `transaction()` is a `@contextmanager`: it takes the calling thread's connection, makes a cursor, runs `BEGIN IMMEDIATE`, yields the cursor, runs `COMMIT` on normal exit; on `except Exception` it runs `ROLLBACK`, swallows any `sqlite3.Error` from that `ROLLBACK`, and re-raises the original exception; `finally` closes the cursor. | FACT | `core/state_store.py` L505 to L543 |
| P01-S034 | The comment gives the reason for `BEGIN IMMEDIATE` (H-5): take the write lock at the start to serialise writers and avoid the deadlock of two deferred transactions upgrading at once. | HISTORICAL | `core/state_store.py` L527 to L530 |
| P01-S035 | If another connection (any thread or process) holds the write lock, `BEGIN IMMEDIATE` waits up to 30 seconds, then raises `sqlite3.OperationalError` ("database is locked"); the `ROLLBACK` in the handler then fails (no transaction) and is swallowed, and the caller receives the original `OperationalError`. | INTERPRETATION | `core/state_store.py` L531, L534 to L541; SQLite semantics |
| P01-S036 | There is no nesting support: no `SAVEPOINT` anywhere in the file and no check for an open transaction. The docstring says nested transactions are not supported. | FACT; HISTORICAL (docstring) | `core/state_store.py` L516 to L519; text search |
| P01-S037 | A nested `transaction()` on the same thread would fail at the inner `BEGIN IMMEDIATE` ("cannot start a transaction within a transaction"); the inner handler's `ROLLBACK` would then succeed and undo the OUTER transaction's work so far before re-raising. If the outer body caught that error and carried on, its later statements would autocommit one by one and the outer `COMMIT` would fail with "no transaction is active". Whether any caller nests is for parts P04, P05, P06a and P06b. | INTERPRETATION | `core/state_store.py` L531 to L541; SQLite semantics |
| P01-S038 | An exception that is not an `Exception` subclass (`KeyboardInterrupt`, `SystemExit`) raised in the body skips the `ROLLBACK`; the cursor is closed but the transaction stays open on that thread's connection, holding the write lock, until a later `COMMIT` or `ROLLBACK` on the same connection or its close. The next `transaction()` on that thread would fail at `BEGIN` and its `ROLLBACK` would discard the left-over work. | INTERPRETATION | `core/state_store.py` L534, L542 to L543; Python `contextlib` semantics |
| P01-S039 | `TransactionError` ("A transaction failed; the caller should treat its work as not committed") is defined but never raised or caught in non-test code; callers of `transaction()` receive raw `sqlite3` exceptions. | FACT | `core/state_store.py` L142 to L143; text search |
