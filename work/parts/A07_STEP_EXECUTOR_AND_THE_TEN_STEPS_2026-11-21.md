## 5. The pool rotation (M-S3), `shutdown`, and the effects on concurrent signals

### 5.1 `_rotate_executor`

- P04-S043 FACT: `_rotate_executor(self, stale)` (L78 to L112) takes the lock (L97); if `_executor_shutdown` is set or the current pool is not `stale`, it returns without action (L98 to L99); otherwise it installs a new single-worker pool (L100), increments `_executor_rotations` (L101) and copies the count (L102). After the lock it logs a WARNING "step_executor: replaced the worker pool after a step timeout (rotation #%d)" (L103 to L108) and calls `stale.shutdown(wait=False, cancel_futures=True)` inside `try`, discarding any exception (L109 to L112, "best-effort; never fail a screening run"). It is called only from the TIMEOUT route (L180).
- P04-S044 HISTORICAL (the docstring, L79 to L96): "`future.result(timeout=...)` abandons the WAIT, not the WORK — Python cannot interrupt a running function, and `future.cancel()` is a no-op once a task has started"; without the rotation "every remaining step of THIS signal, and every step of every LATER signal, queues behind it and times out in turn"; "swap in a fresh pool and let the stale one go ... `shutdown(wait=False)` returns immediately and the stale pool disappears when its task finally returns"; "(A genuinely never-returning step would hold up interpreter exit either way ...)"; "Idempotent under concurrency: if another caller already rotated the same stale pool, or shutdown() has been called, this is a no-op".
- P04-S045 FACT (current external context, read 2026-11-21): the Python documentation states for `Executor.shutdown(wait=True, *, cancel_futures=False)`: "Calls to Executor.submit() and Executor.map() made after shutdown will raise RuntimeError"; "If wait is False then this method will return immediately"; "Regardless of the value of wait, the entire Python program will not exit until all pending futures are done executing"; "If cancel_futures is True, this method will cancel all pending futures that the executor has not started running. Any futures that are completed or running won't be cancelled"; "Changed in version 3.9: Added the cancel_futures parameter". For `Future.cancel()`: "If the call is currently being executed or finished running and cannot be cancelled then the method will return False". The CPython source (`Lib/concurrent/futures/thread.py`, branch `main`) raises `RuntimeError('cannot schedule new futures after shutdown')` in `submit` once the pool is shut down, and with `cancel_futures` drains the work queue and calls `work_item.future.cancel()` on each queued item.
- P04-S046 INTERPRETATION (code with P04-S045): on a timeout the step that overran keeps running on the abandoned worker and its eventual result is discarded; the timed-out signal's next step and every later submission go to the new pool (L163 reads the replaced attribute), as the docstring states.
- P04-S047 INTERPRETATION (code with P04-S028 and P04-S045; not stated in the docstring or in the M-S3 record): when a step overruns, steps that other processor threads have already submitted to the same pool are queued behind it. At the rotation, `cancel_futures=True` cancels those queued futures; each thread waiting on one of them at L167 then receives `CancelledError` (P04-S041), which the `except Exception` route (L182) records as an ERROR step, so that other signal's `error_steps` is non-empty and the screener rejects it `REJECTED_STEP_ERROR` (`secondary_screener.py` L266 to L286). A thread whose own wait times out before the rotation reaches its future takes the TIMEOUT route instead (0.5); of the threads that time out on the same pool, the first to take the lock replaces it, and the later calls of `_rotate_executor` with that pool return without action (L97 to L99) (sentence corrected in the check: the first version said that the thread timing out first finds the pool already replaced). A thread that snapshotted the old pool at L163 just before the swap and submits at L166 just after its shutdown receives `RuntimeError` (P04-S045), also recorded as ERROR. The M-S3 record describes only the timed-out signal and "every later signal" running normally after the rotation (`docs/audit/ma2_ms3_md1_25jul2026.md` L221 to L226). Basis (added in the check; current external context, read 2026-11-21): the CPython source shows how the waiting thread is woken: `Future.cancel` sets the state to `CANCELLED` and calls `self._condition.notify_all()`, and `Future.result`, after `self._condition.wait(timeout)`, raises `CancelledError()` (`Lib/concurrent/futures/_base.py`, branch `main`); a cancelled work item is not run (`_WorkItem.run` returns when `set_running_or_notify_cancel()` is false, `Lib/concurrent/futures/thread.py`, branch `main`). The label stays INTERPRETATION: the code (L163 to L195, L97 to L112), the documentation (P04-S041, P04-S045) and that source establish the mechanism for current Python (the `cancel_futures` parameter dates from 3.9), but the production Python version is UNKNOWN / NOT ESTABLISHED (P04-S164; under a Python older than 3.9 the keyword would be refused and L111 would discard the error, INTERPRETATION), and whether two signals ever overlapped a timeout is UNKNOWN / NOT ESTABLISHED (P04-S054).
- P04-S048 FACT: `_executor_rotations` has no reader other than the WARNING message (search `_executor_rotations` with the four exclusions and `tests` excluded: `screening/step_executor.py` L72, L101, L102 only). Neither a timeout nor a rotation is counted in any metric, telemetry handle or persisted field of the executor; they appear only in the log lines of L171 to L175 and L103 to L108, and a timeout appears as `TIMEOUT` in `step_statuses` (which the screener sends to the evidence recorder, `secondary_screener.py` L672; P03's).

### 5.2 `shutdown` and its place in the stop sequence (A06 PQ-02, A01 C20 at the interface)

- P04-S049 FACT: `shutdown(self)` (L221 to L241) takes the lock (L233); if `_executor_shutdown` is already set it returns (L234 to L235); it sets the flag (L236) and takes the current pool (L237); after the lock it calls `executor.shutdown(wait=True, cancel_futures=False)` in `try`, discarding any exception (L238 to L241). Pools abandoned by earlier rotations are not touched. The docstring says it is "Called by signal_processor.stop() or main.py shutdown sequence" and is "Idempotent" (L223 to L226).
- P04-S050 FACT (callers, interface only): the screener's `shutdown()` calls the executor's `shutdown()` if the attribute exists (`secondary_screener.py` L697 to L705). The only non-test call of the screener's `shutdown()` is in the processor's `stop()` (`signals/signal_processor.py` L342 to L344), which runs after the dispatcher join with `timeout=10.0` (L335 to L336) and after the processor's own `self._executor.shutdown(wait=True, cancel_futures=False)` (L338 to L340); `main.py` reaches it through `signal_proc.stop()` (L1689 to L1692) in its shutdown sequence, after the webhook receiver is stopped (L1684 to L1688). `main.py` has no direct call of the step executor's or the screener's `shutdown()` (search of `main.py` for `step_executor` and `shutdown()` calls on these objects).
- P04-S051 INTERPRETATION (PQ-02's A07 side): because the processor waits, without a limit (A06 AUDIT PQ-02), for every submitted signal before it shuts the screener down, every drained or backlogged signal that reaches screening finds the step executor open and is screened normally; the step executor's `shutdown()` is reached when no processor thread is inside `run_all`, so its `wait=True` waits only for the current pool's idle worker. The step executor adds no time limit of its own to the stop sequence; inside each drained signal's `run_all` the per-step timeout bounds each wait at 5 s (P04-S023), so ten steps can add at most about 50 s of waiting to one signal only when every step overruns (INTERPRETATION; whether any step ever overran is UNKNOWN, P04-S054). A worker abandoned by a rotation is not joined by `shutdown()`, but per P04-S025 and P04-S045 it is joined before the interpreter exits, so a step that never returned would delay the exit, as the docstring L91 to L92 states.
- P04-S052 FACT (A19, stated expectation only; not run): `tests/unit/test_ms3_step_timeout_bounds_caller.py` L175 to L181 expects that `run_all` after `shutdown()` leaves `_executor_shutdown` true and returns ten statuses ("never raises (SE5)"). INTERPRETATION (code with P04-S045): after `shutdown()` every `submit` at L166 raises `RuntimeError`, so all ten steps would be ERROR and the screener would return `REJECTED_STEP_ERROR`; by P04-S050 no `screen()` call is made after the processor has stopped, so this route is not reached on the `main.py` path.

The screener builds the thresholds dictionary from three strategy fields only, `min_volume_surge`, `min_adr_pct` and `max_spread_pct` (`secondary_screener.py` L235 to L239 and L461 to L465; section 8). The clock (A01's code, interface only): `now_ist()` returns `datetime.now(tz=_IST)` (`core/time_authority.py` L94 to L99), where `_IST_OFFSET = timedelta(hours=5, minutes=30)` (L58) and `_IST = timezone(_IST_OFFSET, name="IST")` (L59) (the two lines quoted as written in the check), a timezone-aware value with a fixed +05:30 offset. ### 7.1 Step 1 `volume_surge` (L247 to L256)

- P04-S068 FACT: inputs `md.get("avg_volume_20d")` (L251; corrected in the check from `md["avg_volume_20d"]`), `md.get("volume", 0)` (L254) and `thr.get("min_volume_surge", 1.5)` (L255). If `avg_volume_20d` is falsy (missing, `None` or 0) the step returns 0.0 (L252 to L253) before reading the volume or the threshold; otherwise it returns 1.0 if `volume > avg_vol * min_surge`, else 0.0 (L256). Boundary: strict `>`; equality gives 0.0. Output: 0.0 or 1.0. No log on any route. Docstring: "Volume > avg_volume_20d * min_volume_surge (audit fix c: missing/0 -> 0.0)" (L250).
- P04-S069 FACT (threshold source): the screener always supplies `min_volume_surge` from `strategy.min_volume_surge` (L236, L462), so the step's own default 1.5 (L255) never applies on the screener's routes. A02's schema default is 1.3 and the value must be > 0 (`strategies/schema.py` L117, L265 to L270). The 16 committed strategy files set 1.2 (one file), 1.3 (eight), 1.5 (three), 1.8 (two) and 2.0 (two) (path-limited search of `config/strategies/`). Units: Kite defines `volume` as "Volume traded today" (P04-S058); `avg_volume_20d` has no producer anywhere in the code (P04-S061, P04-S063) and its unit is stated only as "volume vs 20-day avg" (`config/scoring_weights.yaml` L11); `min_volume_surge` is a multiplier.
- P04-S070 INTERPRETATION (live route): `avg_volume_20d` is always `None` (L417), so step 1 always returns 0.0 with status `REJECTED`, and `min_volume_surge` is never read; the committed per-strategy values have no effect on the live route. HISTORICAL: the legacy integrity audit records the same ("`min_volume_surge` ... and `min_adr_pct` ... have ZERO effect", `docs/audit/integrity_audit_2026.md` L674 to L684). P9a (c) asked that step 1's "'allow through' on insufficient data" become `REJECTED_INSUFFICIENT_DATA` (P04-S014); no such status exists in the screening, processor or core code (search `INSUFFICIENT_DATA` in `screening/`, `signals/`, `core/`: no match); the step scores 0.0 instead.
- P04-S071 OPEN QUESTION (meaning, not settled by any source): whether `avg_volume_20d` was meant as a full-day average to be compared with Kite's part-day cumulative `volume` at the moment of the quote is not stated by SE4, SS7 or the weights file; the comparison never runs on the live route (P04-S070).

### 7.2 Step 2 `vwap_position` (L258 to L269)

- P04-S072 FACT: inputs `md.get("ltp", 0.0)` (L262), `md.get("vwap")` (L263) and `direction`. If `vwap is None or ltp is None or ltp == 0.0` it returns 0.0 (L264 to L265; comment "No VWAP data (ETFs, bonds) -> fail gate"). Otherwise, for `"LONG"` it returns 1.0 if `ltp > vwap`, else 0.0 (L266 to L267); for any other direction ("else:  # SHORT") 1.0 if `ltp < vwap`, else 0.0 (L268 to L269). Boundary: strict; `ltp == vwap` gives 0.0. Output: 0.0 or 1.0. No threshold, no log. Units: two prices from the same quote, compared directly (the Kite page states no currency for its price fields; "in rupees" removed in the check).
- P04-S073 INTERPRETATION (live route): `vwap` is the quote's `average_price` ("The volume weighted average price of a stock at a given time during the day", P04-S058), or `None` when that field is absent or zero (P04-S057); a missing VWAP scores 0.0 (counts against the signal), unlike the neutral 0.5 that steps 4, 6, 8 and 10 give for missing input; an absent last price (0.0) also scores 0.0. Since directions are validated as `LONG` or `SHORT` (P04-S030), the `else` branch is reached only for `SHORT` on the live route.

### 7.3 Step 3 `atr_filter` (L271 to L281)

- P04-S074 FACT: inputs `md.get("atr")` (L275), `md.get("ltp", 0.0)` (L276) and `thr.get("min_adr_pct", 0.5)` (L280). If `atr` or `ltp` is falsy it returns 0.0 (L277 to L278); otherwise `adr_pct = (atr / ltp) * 100.0` (L279) and it returns 1.0 if `adr_pct >= min_adr`, else 0.0 (L281). Boundary: `>=`. Output: 0.0 or 1.0. No log. Units: `adr_pct` is ATR as a percentage of the last price; docstring "ADR% >= min_adr_pct. Missing/zero ATR -> 0.0" (L274).
- P04-S075 FACT (threshold source): the screener supplies `strategy.min_adr_pct` (L237, L463), so the step's default 0.5 never applies on its routes; schema default 0.005, validated only `>= 0` (`strategies/schema.py` L118, L251 to L256); all 16 committed strategy files set 0.005. The unit of that value is discussed in section 8.
- P04-S076 INTERPRETATION (live route): `atr` is always `None` (L413), so step 3 always returns 0.0 with status `REJECTED`, and `min_adr_pct` is never read. The step's name says ATR while its docstring and variable say ADR; it divides an ATR value by the last price and calls the result "ADR%"; no ATR producer feeds it (P04-S063).

### 7.4 Step 4 `rsi_range` (L283 to L316)

- P04-S077 FACT: input `md.get("rsi")` (L296). `None` returns 0.5 (L297 to L298). A value that `float()` cannot convert logs a WARNING ("is not numeric; treating as missing") and returns 0.5 (L299 to L305). A value below 0.0 or above 100.0 logs a WARNING ("outside [0,100]; treating as missing") and returns 0.5 (L306 to L312). Otherwise, for `"LONG"` it returns 1.0 if `40.0 <= rsi_f <= 80.0`, else 0.0 (L313 to L314); for any other direction 1.0 if `20.0 <= rsi_f <= 60.0`, else 0.0 (L315 to L316). Boundaries inclusive. Output: 0.0, 0.5 or 1.0. The bands are constants of the code; no threshold key is read. Units: the RSI scale 0 to 100. The docstring (L286 to L295, the "I.3" fix of 2026-04-25) gives the reason for treating out-of-range values as missing.
- P04-S078 INTERPRETATION and current external context: a NaN value converts with `float()` and, because "Any ordered comparison of a number to a not-a-number value is false" (https://docs.python.org/3/reference/expressions.html, "Value comparisons", read 2026-11-21), it passes the range test at L306 and fails both band tests, so it scores 0.0, not the neutral 0.5 given to other unusable values.
- P04-S079 FACT: the WARNING at L307 to L311 logs `signal.get("symbol")` and `signal.get("scanner")`; the signal dictionary built by the screener has the key `"scanner_name"`, not `"scanner"` (`secondary_screener.py` L244, L467), so that field of the log line would read `None`.
- P04-S080 INTERPRETATION (live route): `rsi` is always `None` (L414), so step 4 always returns 0.5 with status `PASSED`.

### 7.5 Step 5 `price_action` (L318 to L329)

- P04-S081 FACT: inputs `ltp = md.get("ltp", 0.0)` (L322), `open_price = md.get("open", ltp)` (L323), `day_high = md.get("day_high", ltp)` (L324), `day_low = md.get("day_low", ltp)` (L325). It computes `body = abs(ltp - open_price)` (L326), `range_ = day_high - day_low + 1e-9` (L327), `body_pct = body / range_` (L328) and returns `min(1.0, body_pct * 2.0)` (L329). No threshold and no log; `direction` is not used. Units: a ratio of price differences (dimensionless). Docstring: "Body% rewards strong directional candle bodies" (L321).
- P04-S082 FACT and current external context: the `ltp` defaults apply only when a key is absent; `dict.get` returns "the value for key if key is in the dictionary, else default" (https://docs.python.org/3/library/stdtypes.html, read 2026-11-21), and `_build_market_data` always includes `open`, `day_high` and `day_low`, possibly with the value `None` (P04-S061). With `None` in any of the three, `abs(ltp - None)` or `None - day_low` raises (P04-S008: `TypeError`), the step takes the ERROR route (L182 to L195) and the screener rejects the signal `REJECTED_STEP_ERROR` (P04-S039).
- P04-S083 INTERPRETATION (output range and boundaries): when `day_high >= day_low` the value lies in [0.0, 1.0]; it is 0.0 (status `REJECTED`) exactly when `ltp == open_price`, and 1.0 whenever the day's body is at least half the day's range; when `day_high == day_low` any non-zero body gives a quotient of order 1e9 and so 1.0; if `day_high - day_low` were below −1e-9 the value would be negative and, being non-zero, recorded `PASSED` (P04-S035). With an absent last price (0.0) and the OHLC fields present, `body` equals the open price, so the value is normally 1.0.
- P04-S084 INTERPRETATION (semantics against intent sources): the "candle" is the day so far (the day's open to the last price, over the day's high-low range), not the bar that triggered the signal; the step is direction-blind (`abs`; `direction` unused), so a LONG signal on a stock trading below its open scores the same as on one trading above it. SE4 (L2891) gives the same formula without the code's `+ 1e-9` term (`body_pct = |ltp-open|/(day_high-day_low)`; qualified in the check). The weights file describes the step as "candle structure + swing confirmation" (L15); no swing logic is in the code.

### 7.7 Step 7 `time_of_day` and `_minutes_since_open` (L338 to L370)

- P04-S087 FACT: `_minutes_since_open(now)` (L338 to L357) sets `open_today = now.replace(hour=self._market_open.hour, minute=self._market_open.minute, second=0, microsecond=0)` (L343 to L348) and returns `(now - open_today).total_seconds() / 60.0` (L349 to L350); a negative value is logged at DEBUG ("signal_age clamped negative to zero") and returned as 0.0 (L351 to L356). Step 7 calls it with `now_ist()` (L363) and returns 0.5 if minutes `< 15` ("too early"), 1.0 if `< 60` ("prime time"), 0.8 if `< 180` ("good window"), else 0.5 ("afternoon") (L364 to L370). Boundaries strict `<`. Output: 0.5, 0.8 or 1.0; never 0.0, so the step is never `REJECTED`. No market data, threshold or direction is read; the bucket limits are constants of the code; the open time is the constructor's (section 3).
- P04-S088 INTERPRETATION (at the file value `market_open` 09:15, P04-S021): 09:15 to 09:30 gives 0.5, 09:30 to 10:15 gives 1.0, 10:15 to 12:15 gives 0.8, from 12:15 gives 0.5, and before 09:15 the clamp gives 0.5. The committed global entry window is 10:00 to 15:00 (`config/system_config.yaml` L28, L47; A01's window, checked by the processor at `signals/signal_processor.py` L911 before screening), so a signal screened inside it can score 1.0 only between 10:00 and 10:15. The step measures the time at which it runs, not `triggered_at`.
- P04-S089 FACT: `_minutes_since_open` is called only by step 7 (search of `screening/` for `_minutes_since_open`: L338 definition, L363 call); its DEBUG text names "signal_age" (L353), a step that does not call it. HISTORICAL: the weights file describes step 7 as "entry time quality (later in session = lower weight)" (L17); the code also gives the lower value 0.5 to the first 15 minutes.

### 7.8 Step 8 `spread_check` (L372 to L395)

- P04-S090 FACT: inputs `md.get("bid")`, `md.get("ask")` (L379 to L380) and `thr.get("max_spread_pct", 0.1)` (L394). If either is `None` it returns 0.5 (L381 to L382). Otherwise `mid = (ask + bid) / 2.0` (L385); if `mid <= 0.0` it logs a WARNING ("mid_price <= 0 ... returning neutral") and returns 0.5 (L386 to L391); otherwise `spread_pct = ((ask - bid) / mid) * 100.0` (L393) and it returns 1.0 if `spread_pct <= max_spread`, else 0.0 (L395). Boundary: `<=`. Output: 0.0, 0.5 or 1.0. Units: `spread_pct` is a percentage of the mid price. Docstring: "FIX-043: Spread <= max_spread_pct using mid-price denominator" (L376); comment "Use mid-price instead of LTP (LTP can be stale)" (L384).
- P04-S091 FACT (threshold source): the screener supplies `strategy.max_spread_pct` (L238, L464), so the step's default 0.1 never applies on its routes; schema default 0.005, validated only `>= 0` (`strategies/schema.py` L119, L251 to L256); all 16 committed strategy files set 0.005.
- P04-S092 INTERPRETATION (live route, with P04-S057 and P04-S059): the adapter never supplies `None` for `bid` or `ask` (an empty side becomes 0.0), so the `None` branch is not reached on the live route; both sides 0.0 give `mid == 0` and the neutral 0.5 with a WARNING; a bid of 0.0 with a positive ask gives a spread of +200 % and 0.0, while an ask of 0.0 with a positive bid gives −200 % and 1.0 (corrected in the check: the first version gave 200 % and 0.0 for either side; arithmetic of L385 and L393); a crossed quote (`ask < bid`) gives a negative spread and 1.0, and a locked quote (`ask == bid`) gives 0 and 1.0; no step checks that `ask >= bid`. At the file value 0.005 the step passes only when `ask - bid <= 0.00005 × mid` (algebra of L393 and L395).
- P04-S093 HISTORICAL: SE4 (L2894) defined `spread_pct=(ask-bid)/ltp*100`; the code uses the mid price since FIX-043 (`ad610333548deff4d10a1f21fc40fec9484c89bb`, 2026-05-14). The weights file describes the step as "bid-ask spread vs ATR" (L18); the code uses no ATR.

### 7.9 Step 9 `circuit_check` (L397 to L404)

- P04-S094 FACT: input `md.get("circuit_state", "")` (L401); returns 0.0 if the value is `"upper_circuit"` or `"lower_circuit"` (L402 to L403), else 1.0 (L404). Output: 0.0 or 1.0. ### 7.10 Step 10 `signal_age` (L406 to L423)

- P04-S096 FACT: input `signal.get("triggered_at")` (L410); `None` returns 0.5 (L411 to L412). With `now = now_ist()` (L413): a naive `triggered_at` with an aware `now` is given `now`'s time zone without conversion (L414 to L415); an aware `triggered_at` with a naive `now` loses its zone (L416 to L417). Then `age_sec = (now - triggered_at).total_seconds()` (L418); it returns 1.0 if `age_sec <= 30` (L419 to L420), 0.5 if `age_sec <= 60` (L421 to L422), else 0.0 (L423). Boundaries inclusive at 30 s and 60 s. Output: 0.0, 0.5 or 1.0. Units: seconds. The limits 30 and 60 are constants of the code; no threshold key is read. Docstring: "Signal freshness: >60s -> 0.0, >30s -> 0.5, <=30s -> 1.0 (P9a add, SE4)" (L409).
- P04-S097 FACT (the input at the interface): the screener's signal dictionary carries the `triggered_at` argument of `screen()` (L246, L468), which the processor passes unchanged from its queued signal (`signals/signal_processor.py` L883 or L886, L999). A06 records the queued time as IST-aware ("the queued time is IST-aware", A06 AUDIT PQ-08 (1)), while the processor's docstring says "naive datetime (IST)" (L874); before screening the processor itself calls `triggered_at.replace(tzinfo=ist_timezone())` for its own age check (L915 to L921), which requires a `datetime`.
- P04-S098 INTERPRETATION: on the live route both values are aware (P04-S067, P04-S097), neither branch at L414 to L417 runs, and the age is a true elapsed time; if the queued value were naive, as the processor's docstring says, L414 to L415 would attach the step clock's fixed +05:30 zone, the same zone the processor's own check attaches (L915; `ist_timezone()` returns the same `_IST`, `core/time_authority.py` L102 to L104), and the age would be the same (added in the check); a `triggered_at` later than the step's clock gives a negative age and 1.0 (no lower bound); a value that is not a `datetime` would raise at L414 (no `tzinfo` attribute) and take the ERROR route, which the processor's earlier `.replace` call makes unreachable on that route. The age is measured when step 10 runs, after the queue wait, the processor's checks, the quote fetch and steps 1 to 9.
- P04-S099 HISTORICAL: P9a asks for a reject "if now - signal.triggered_at > 90s" (L389); the weights file says "now - triggered_at ≤ 90s, P9a" (L20); `config/scoring_weights.yaml` L41 sets the V3 gate's `v3_freshness_max_sec: 60.0` with the comment "matches OLD signal_age>60s reject"; SE4 (L2896) gives 30 s and 60 s as the code does. The screener's own age reject, and whether it carries P9a's 90 s, is in section 9 and section 11 (A02 T-20; A06 PQ-08 (6)).
