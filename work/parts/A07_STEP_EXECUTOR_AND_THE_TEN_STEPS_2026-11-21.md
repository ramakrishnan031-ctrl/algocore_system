### 3.2 The single-worker pool (FIX-100)

- P04-S024 FACT: `_new_executor()` returns `ThreadPoolExecutor(max_workers=1, thread_name_prefix="step-exec")` (L74 to L76). One pool is created at construction (L70) and replaced only by `_rotate_executor` (L100, section 5). The FIX-100 comment (L62 to L66) says the executor "is single-worker (steps run sequentially per signal) but persists across calls to avoid create/destroy churn"; the M-S3 comment (L67 to L68) says "run_all() may be entered by several signal workers at once".
- P04-S025 FACT (current external context, read 2026-11-21): the Python documentation describes `ThreadPoolExecutor` as "An Executor subclass that uses a pool of at most max_workers threads to execute calls asynchronously" and states "All threads enqueued to ThreadPoolExecutor will be joined before the interpreter can exit" (https://docs.python.org/3/library/concurrent.futures.html). The CPython source of `ThreadPoolExecutor.__init__` creates its work queue as `self._work_queue = queue.SimpleQueue()` (`Lib/concurrent/futures/thread.py`, branch `main`), and the `queue` documentation describes `SimpleQueue` as "Constructor for an unbounded FIFO (first-in, first-out) queue" (https://docs.python.org/3/library/queue.html).
- P04-S026 FACT: the only non-test callers of `run_all` are `screening/secondary_screener.py` L253 (the default route, all ten steps) and L474 (the V3 enforce route, `exclude_steps=self._v3_gate_steps`) (search `run_all(` with the four exclusions and `tests` excluded; the other hits are in `docs/`). The only non-test call of the screener's `screen()` is `signals/signal_processor.py` L998, inside `_process_one` (search `\.screen\(` in `*.py` with the four exclusions and `tests` excluded).
- P04-S027 FACT (A06's and A01's code, interface only): the processor runs `_process_one` on a `ThreadPoolExecutor` with `max_workers=self._worker_count` (`signals/signal_processor.py` L311), where `_worker_count = max(1, worker_count)` (L220) and `main.py` passes `sp_cfg.worker_count` (L3590; `sp_cfg = app_config.system.signal_processor`, L3574); the committed file sets `signal_processor.worker_count: 5` ("ThreadPoolExecutor workers (1-50)", `config/system_config.yaml` L345). Effective value UNKNOWN / NOT ESTABLISHED.
- P04-S028 INTERPRETATION (code reading with P04-S024 to P04-S027; nothing run): up to `worker_count` processor threads (5 at the file value) can be inside `run_all` at the same moment, and all of them submit their steps to the one worker thread of the current pool (L163 to L167). Each thread submits one step and waits for its result before submitting the next (L158 to L167), so a signal's own steps run one after another, while the steps of concurrent signals are executed one at a time in the order in which they were submitted (FIFO), interleaved. The pool therefore serialises all step execution of the process; it adds no parallelism.
