### 3.2 The single-worker pool (FIX-100)

- P04-S024 FACT: `_new_executor()` returns `ThreadPoolExecutor(max_workers=1, thread_name_prefix="step-exec")` (L74 to L76). - P04-S025 FACT (current external context, read 2026-11-21): the Python documentation describes `ThreadPoolExecutor` as "An Executor subclass that uses a pool of at most max_workers threads to execute calls asynchronously" and states "All threads enqueued to ThreadPoolExecutor will be joined before the interpreter can exit" (https://docs.python.org/3/library/concurrent.futures.html). The CPython source of `ThreadPoolExecutor.__init__` creates its work queue as `self._work_queue = queue.SimpleQueue()` (`Lib/concurrent/futures/thread.py`, branch `main`), and the `queue` documentation describes `SimpleQueue` as "Constructor for an unbounded FIFO (first-in, first-out) queue" (https://docs.python.org/3/library/queue.html).
- P04-S026 FACT: the only non-test callers of `run_all` are `screening/secondary_screener.py` L253 (the default route, all ten steps) and L474 (the V3 enforce route, `exclude_steps=self._v3_gate_steps`) (search `run_all(` with the four exclusions and `tests` excluded; the other hits are in `docs/`). - P04-S027 FACT (A06's and A01's code, interface only): the processor runs `_process_one` on a `ThreadPoolExecutor` with `max_workers=self._worker_count` (`signals/signal_processor.py` L311), where `_worker_count = max(1, worker_count)` (L220) and `main.py` passes `sp_cfg.worker_count` (L3590; `sp_cfg = app_config.system.signal_processor`, L3574); the committed file sets `signal_processor.worker_count: 5` ("ThreadPoolExecutor workers (1-50)", `config/system_config.yaml` L345). Effective value UNKNOWN / NOT ESTABLISHED.
- P04-S028 INTERPRETATION (code reading with P04-S024 to P04-S027; nothing run): up to `worker_count` processor threads (5 at the file value) can be inside `run_all` at the same moment, and all of them submit their steps to the one worker thread of the current pool (L163 to L167). Each thread submits one step and waits for its result before submitting the next (L158 to L167), so a signal's own steps run one after another, while the steps of concurrent signals are executed one at a time in the order in which they were submitted (FIFO), interleaved. The pool therefore serialises all step execution of the process; it adds no parallelism.

- P04-S035 FACT (normal route, L197 to L211): the latency is recorded (L197 to L198) and the returned value stored as the step result (L200); if it equals `0.0` the status is `"REJECTED"` and `rejected_at` is set if still `None` (L201 to L204); otherwise the status is `"PASSED"` (L205 to L206); a DEBUG line logs the score and latency (L208 to L211).
- P04-S036 FACT: `run_all` returns `StepExecutorResult(step_results, step_statuses, rejected_at, error_steps, latencies_ms)` (L213 to L219). Every route of the loop writes the step's name into `step_results`, `step_statuses` and `latencies_ms` (L176 to L178, L189 to L192, L198 to L206), so each step that was run appears in all three dictionaries; on the default route all ten names are present.
- P04-S037 INTERPRETATION (from P04-S033 to P04-S035): the step status vocabulary is `PASSED`, `REJECTED`, `ERROR`, `TIMEOUT`. `PASSED` means only "returned a value other than 0.0": a step that finds its input missing and returns the neutral 0.5 (steps 4, 6, 8, 10; section 7) is recorded `PASSED`, as is any non-zero value, including a negative one (section 7.5). `REJECTED` means "returned exactly 0.0" and does not by itself reject the signal (section 9). The screener's `ScreeningResult.step_statuses` comment lists only `"PASSED"|"REJECTED"|"ERROR"` (`secondary_screener.py` L51), without `TIMEOUT`.
- P04-S038 FACT: `rejected_at` is the first step, in run order, that was ERROR or returned 0.0 (L193 to L194, L203 to L204); a TIMEOUT never sets it. No tracked non-test file reads it: a search for `rejected_at` with the four exclusions and `tests` excluded finds it only in `screening/step_executor.py`, in `docs/` and in an unrelated test name under `ops_dashboard/tests/`. The screener builds its own `rejected_step` (P03's) and never copies `rejected_at`. SE3 (P04-S013) lists `rejected_at` among the result fields.
- P04-S039 FACT: `error_steps` holds the names of ERROR steps only, in run order (L191). The screener's default route rejects the signal with status `REJECTED_STEP_ERROR` whenever `error_steps` is non-empty, with `rejected_step` set to the names joined by ", " (`secondary_screener.py` L266 to L286, a WARNING naming all of them, L267 to L272); the V3 enforce route does the same without the WARNING (L485 to L494). Both are P03's and P05's routes, cited here at the interface.
- P04-S040 FACT and current external context: `latencies_ms[name]` is `(time.monotonic() - t0) * 1000.0` with `t0` read before `submit` and the value taken after `result` returns or raises (L159, L170, L183, L197). The Python documentation states that `Future.result(timeout)` "will wait up to timeout seconds" if the call "hasn't yet completed" (concurrent.futures page, read 2026-11-21). INTERPRETATION: the figure therefore includes the time the step waited in the pool's queue behind steps submitted by other signals (P04-S028), not only its own execution; for a TIMEOUT it is about the timeout. HISTORICAL: the legacy M-S3 record says the same ("`latencies_ms` is taken around `submit()+result()`, so it measures queue wait, not step time", `docs/audit/ma2_ms3_md1_25jul2026.md` L189 to L190).
- P04-S041 FACT and current external context: the Python documentation states for `Future.result`: "If the call hasn't completed in timeout seconds, then a TimeoutError will be raised"; "If the future is cancelled before completing then CancelledError will be raised"; "If the call raised an exception, this method will raise the same exception"; and for `concurrent.futures.TimeoutError`: "A deprecated alias of TimeoutError ... Changed in version 3.11: This class was made an alias of TimeoutError" (read 2026-11-21). The CPython source (`Lib/concurrent/futures/_base.py`, branches `main` and `3.13`) has `class Error(Exception):`, `class CancelledError(Error):` and `TimeoutError = TimeoutError # make local alias for the standard exception`. INTERPRETATION: the name imported at L13 is the exception that `result()` raises on a timeout, so a timeout takes the L168 route; an exception raised inside a step and a `CancelledError` are both `Exception` subclasses (P04-S008) and take the L182 route.
- P04-S042 FACT: SE7's "no short-circuit" holds in the code: every route ends with `continue` or falls through to the next iteration (L181, L195, L211), and no route leaves the loop early. On the V3 enforce route only the eight steps not in `exclude_steps` run (P04-S029, P04-S031).

## 5. The pool rotation (M-S3), `shutdown`, and the effects on concurrent signals

### 5.1 `_rotate_executor`

- P04-S043 FACT: `_rotate_executor(self, stale)` (L78 to L112) takes the lock (L97); if `_executor_shutdown` is set or the current pool is not `stale`, it returns without action (L98 to L99); otherwise it installs a new single-worker pool (L100), increments `_executor_rotations` (L101) and copies the count (L102). After the lock it logs a WARNING "step_executor: replaced the worker pool after a step timeout (rotation #%d)" (L103 to L108) and calls `stale.shutdown(wait=False, cancel_futures=True)` inside `try`, discarding any exception (L109 to L112, "best-effort; never fail a screening run"). It is called only from the TIMEOUT route (L180).
- P04-S044 HISTORICAL (the docstring, L79 to L96): "`future.result(timeout=...)` abandons the WAIT, not the WORK — Python cannot interrupt a running function, and `future.cancel()` is a no-op once a task has started"; without the rotation "every remaining step of THIS signal, and every step of every LATER signal, queues behind it and times out in turn"; "swap in a fresh pool and let the stale one go ... `shutdown(wait=False)` returns immediately and the stale pool disappears when its task finally returns"; "(A genuinely never-returning step would hold up interpreter exit either way ...)"; "Idempotent under concurrency: if another caller already rotated the same stale pool, or shutdown() has been called, this is a no-op".
- P04-S045 FACT (current external context, read 2026-11-21): the Python documentation states for `Executor.shutdown(wait=True, *, cancel_futures=False)`: "Calls to Executor.submit() and Executor.map() made after shutdown will raise RuntimeError"; "If wait is False then this method will return immediately"; "Regardless of the value of wait, the entire Python program will not exit until all pending futures are done executing"; "If cancel_futures is True, this method will cancel all pending futures that the executor has not started running. Any futures that are completed or running won't be cancelled"; "Changed in version 3.9: Added the cancel_futures parameter". For `Future.cancel()`: "If the call is currently being executed or finished running and cannot be cancelled then the method will return False". The CPython source (`Lib/concurrent/futures/thread.py`, branch `main`) raises `RuntimeError('cannot schedule new futures after shutdown')` in `submit` once the pool is shut down, and with `cancel_futures` drains the work queue and calls `work_item.future.cancel()` on each queued item.
- P04-S046 INTERPRETATION (code with P04-S045): on a timeout the step that overran keeps running on the abandoned worker and its eventual result is discarded; the timed-out signal's next step and every later submission go to the new pool (L163 reads the replaced attribute), as the docstring states.
- P04-S047 INTERPRETATION (code with P04-S028 and P04-S045; not stated in the docstring or in the M-S3 record): when a step overruns, steps that other processor threads have already submitted to the same pool are queued behind it. At the rotation, `cancel_futures=True` cancels those queued futures; each thread waiting on one of them at L167 then receives `CancelledError` (P04-S041), which the `except Exception` route (L182) records as an ERROR step, so that other signal's `error_steps` is non-empty and the screener rejects it `REJECTED_STEP_ERROR` (`secondary_screener.py` L266 to L286). A thread whose own wait reaches the timeout first takes the TIMEOUT route instead (0.5), and its call of `_rotate_executor` with the already-replaced pool returns without action (L98). A thread that snapshotted the old pool at L163 just before the swap and submits at L166 just after its shutdown receives `RuntimeError` (P04-S045), also recorded as ERROR. The M-S3 record describes only the timed-out signal and "every later signal" running normally after the rotation (`docs/audit/ma2_ms3_md1_25jul2026.md` L221 to L226).
- P04-S048 FACT: `_executor_rotations` has no reader other than the WARNING message (search `_executor_rotations` with the four exclusions and `tests` excluded: `screening/step_executor.py` L72, L101, L102 only). Neither a timeout nor a rotation is counted in any metric, telemetry handle or persisted field of the executor; they appear only in the log lines of L171 to L175 and L103 to L108, and a timeout appears as `TIMEOUT` in `step_statuses` (which the screener sends to the evidence recorder, `secondary_screener.py` L672; P03's).

### 5.2 `shutdown` and its place in the stop sequence (A06 PQ-02, A01 C20 at the interface)

- P04-S049 FACT: `shutdown(self)` (L221 to L241) takes the lock (L233); if `_executor_shutdown` is already set it returns (L234 to L235); it sets the flag (L236) and takes the current pool (L237); after the lock it calls `executor.shutdown(wait=True, cancel_futures=False)` in `try`, discarding any exception (L238 to L241). Pools abandoned by earlier rotations are not touched. The docstring says it is "Called by signal_processor.stop() or main.py shutdown sequence" and is "Idempotent" (L223 to L226).
- P04-S050 FACT (callers, interface only): the screener's `shutdown()` calls the executor's `shutdown()` if the attribute exists (`secondary_screener.py` L697 to L705). The only non-test call of the screener's `shutdown()` is in the processor's `stop()` (`signals/signal_processor.py` L342 to L344), which runs after the dispatcher join with `timeout=10.0` (L335 to L336) and after the processor's own `self._executor.shutdown(wait=True, cancel_futures=False)` (L338 to L340); `main.py` reaches it through `signal_proc.stop()` (L1689 to L1692) in its shutdown sequence, after the webhook receiver is stopped (L1684 to L1688). `main.py` has no direct call of the step executor's or the screener's `shutdown()` (search of `main.py` for `step_executor` and `shutdown()` calls on these objects).
- P04-S051 INTERPRETATION (PQ-02's A07 side): because the processor waits, without a limit (A06 AUDIT PQ-02), for every submitted signal before it shuts the screener down, every drained or backlogged signal that reaches screening finds the step executor open and is screened normally; the step executor's `shutdown()` is reached when no processor thread is inside `run_all`, so its `wait=True` waits only for the current pool's idle worker. The step executor adds no time limit of its own to the stop sequence; inside each drained signal's `run_all` the per-step timeout bounds each wait at 5 s (P04-S023), so ten steps can add at most about 50 s of waiting to one signal only when every step overruns (INTERPRETATION; whether any step ever overran is UNKNOWN, P04-S054). A worker abandoned by a rotation is not joined by `shutdown()`, but per P04-S025 and P04-S045 it is joined before the interpreter exits, so a step that never returned would delay the exit, as the docstring L91 to L92 states.
- P04-S052 FACT (A19, stated expectation only; not run): `tests/unit/test_ms3_step_timeout_bounds_caller.py` L175 to L181 expects that `run_all` after `shutdown()` leaves `_executor_shutdown` true and returns ten statuses ("never raises (SE5)"). INTERPRETATION (code with P04-S045): after `shutdown()` every `submit` at L166 raises `RuntimeError`, so all ten steps would be ERROR and the screener would return `REJECTED_STEP_ERROR`; by P04-S050 no `screen()` call is made after the processor has stopped, so this route is not reached on the `main.py` path.
