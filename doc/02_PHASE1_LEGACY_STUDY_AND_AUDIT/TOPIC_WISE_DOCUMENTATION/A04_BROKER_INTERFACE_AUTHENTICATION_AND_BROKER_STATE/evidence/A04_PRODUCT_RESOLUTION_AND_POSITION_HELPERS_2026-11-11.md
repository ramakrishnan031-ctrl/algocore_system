## 2. `broker/product_resolver.py`: stated contract and construction (`ProductResolver.__init__`)

- **P09-S008** HISTORICAL (module docstring, 2026-04-17, `bcf03b5`): the stated purpose is "Single source of truth for translating semantic product intents into broker-specific product codes. Eliminates hardcoded "MIS"/"CNC"/"CO" strings from the rest of the codebase (audit Issue #29)" (L4 to L7). Locked decisions PR1 to PR10 follow (L9 to L20), among them PR2 "Four valid intents", PR3 the Zerodha codes with `BRACKET_ORDER->""` ("empty = not supported, raises ProductNotSupportedError"), PR5 the reverse lookup "for reconciler", PR6 construction checks, PR8 "product_map ... injected from cfg.system.product_map" and PR10 "No silent fallbacks". "What This Module Does NOT Do" (L22 to L26): it reads no configuration file, hardcodes no product code, implements no retry, and "Does not support BSE segment codes (NSE equity scope only for now)".
- **P09-S009** FACT: the module imports only `from __future__ import annotations` and `from core.exceptions import ProductNotSupportedError` (L28 to L30), as PR9 states. It has no logger, no file or network I/O and no environment read.
- **P09-S010** FACT: `_VALID_INTENTS` is a module-level `frozenset` of the four strings "INTRADAY", "DELIVERY", "COVER_ORDER", "BRACKET_ORDER" (L36 to L41). It is fixed in code and is not derived from the configuration.
- **P09-S011** FACT: `ProductResolver.__init__(product_map)` (L63 to L93) raises `ValueError` when `product_map` is falsy (an empty dict or `None`; message "product_map must not be empty; check system_config.yaml product_map section", L72 to L76), and raises `ValueError` when any broker entry is not a `dict` (L77 to L82). It performs no other check: it does not test the broker names, the intent keys against `_VALID_INTENTS`, whether an inner map is empty, whether the codes are strings, or whether two intents share a code.
- **P09-S012** INTERPRETATION (from L72 to L82): a map such as `{"zerodha": {}}`, or one with an intent key outside the four, is accepted at construction; the first is detected only when `resolve` is called (every intent then raises `ProductNotSupportedError`), the second never by `resolve` (which rejects the unknown intent before looking it up).
- **P09-S013** FACT: the constructor raises `ValueError`, not `ProductNotSupportedError`, for a bad map (its docstring L69 to L70 says so). `ProductNotSupportedError` is raised only by `resolve` (L118, L130). INTERPRETATION: PR7 (L17) "Raises ProductNotSupportedError (BrokerError, SEVERITY='ERROR') on bad mapping" can match the code only in the resolve-time cases (unknown broker, empty or missing code); for a bad map at construction the code raises `ValueError`.
- **P09-S014** FACT: the constructor stores a copy: a new outer dict whose values are `dict(mapping)` copies of each inner dict (L90 to L93). The comment (L84 to L89, FIX-115, 2026-05-18, `d12fe15`) says the source "typically comes from SystemConfig.product_map (Pydantic, immutable), making this copy technically unnecessary", and labels the copy "(PR9)", while PR9 in the docstring is the import-layer rule (L19).
- **P09-S015** FACT: `SystemConfig` declares `model_config = ConfigDict(extra="forbid")` (`core/config_loader.py` L1988), and `git grep` finds no `frozen` setting in `core/config_loader.py`. INTERPRETATION (pydantic 2 semantics): the configuration object is not frozen, and the contents of a `dict` field stay mutable in any case, so the copy is what isolates the resolver from later changes to the configuration object; the comment's "immutable" is not supported by the schema code.
- **P09-S016** FACT: after construction `_map` is only read (`resolve` L117, L125, L127 to L129; `intent_for` L156, L162, L166). The class has no setter, no reload, no cache and no lock. INTERPRETATION: concurrent callers only read shared state, and a changed YAML value reaches the resolver only through a new `ProductResolver`; in the trading process that is a new start (`main.py` L2349, section 5).
- **P09-S017** FACT: `ProductNotSupportedError` subclasses `BrokerError` (`core/exceptions.py` L228) with `SEVERITY = "ERROR"` (L240); `BrokerError` subclasses `TradingSystemError` (L158), whose `__init__(message, **context)` keeps the keyword arguments in `self.context` (L47 to L49). The resolver passes `intent`, `broker` and `available_intents` as context (L118 to L123, L130 to L136). The `BrokerError` docstring names only `broker/zerodha_adapter.py` and `broker/rate_limiter.py` as raisers (L160 to L161); the `ProductNotSupportedError` docstring names `broker/product_resolver.py` (L233).

## 3. Forward resolution: `ProductResolver.resolve(intent, broker="zerodha")`

- **P09-S018** FACT: `resolve` (L95 to L138) checks, in this order: (1) `intent not in _VALID_INTENTS` → `ValueError("Unknown product intent: ... Valid intents: [...]")` (L111 to L115); (2) `broker not in self._map` → `ProductNotSupportedError("Broker ... not found in product_map", intent, broker, available_intents=sorted(_VALID_INTENTS))` (L117 to L123); (3) `code = self._map[broker].get(intent)`; if `not code` → `ProductNotSupportedError("Intent ... is not supported by broker ... (mapped to empty/null code)", intent, broker, available_intents=<keys whose value is truthy>)` (L125 to L136); (4) otherwise `return code` (L138).
- **P09-S019** FACT: an unknown intent and an unsupported product are reported with different exception types: `ValueError` (not a `BrokerError`) for an intent outside the four; `ProductNotSupportedError` (a `BrokerError`) for an unknown broker or an empty or missing code. The docstring (L106 to L109) states the same split.
- **P09-S020** FACT: all three comparisons are exact string tests: "intraday" (lower case) raises `ValueError`; a broker key "Zerodha" raises `ProductNotSupportedError`. A non-empty code is returned exactly as stored, with no trimming, case change or check against a list of codes the broker accepts.
- **P09-S021** INTERPRETATION (from L126 and L138): a mistyped but non-empty code in the YAML (for example "MiS") would be returned unchanged; the resolver cannot detect it. `place_order` would send it to the broker (`broker/zerodha_adapter.py` L645), and before that it would fail silently to match the literals that guard the path: a mistyped INTRADAY code would make the screener's MIS gate return False, so the MIS blocklist would not be consulted (`screening/secondary_screener.py` L570 to L571), and a mistyped delivery code would not trigger the delivery lock (`zerodha_adapter.py` L593). Whether and how the broker rejects such a code is not established by the repository (part P02's rejection path).
- **P09-S022** FACT: the "available" list of the empty-code error is built from the map's own keys with truthy values (L127 to L129), so it can name keys that are not valid intents; at the file values it is `["COVER_ORDER", "DELIVERY", "INTRADAY"]`.
- **P09-S023** FACT: `resolve` does not log, retry, wait, read time or call the broker. INTERPRETATION: for hashable arguments and a map whose keys are strings (as the loader builds it, P09-S034; the sort at L127 needs comparable keys) its only outcomes are the returned code and the three raises of P09-S018; an unhashable intent or broker would raise `TypeError` at the membership tests (L111 or L117, because Python hashes the operand); after the constructor's checks (P09-S011) a `KeyError` or an attribute error from L125 cannot occur.
- **P09-S024** FACT: at the file values (`config/system_config.yaml` L157 to L162) `resolve` returns "MIS" for INTRADAY, "CNC" for DELIVERY and "CO" for COVER_ORDER, and raises `ProductNotSupportedError` for BRACKET_ORDER (code ""). A02 recorded the map reaching the resolver and the BRACKET_ORDER behaviour as MATCH (K-43 and L-40, FACT); that classification is kept.
- **P09-S025** FACT and INTERPRETATION for "stale" products: the resolver keeps the map it was built with and has no expiry or refresh (P09-S016). The only representation of a product the broker no longer offers is an empty code, which the YAML uses for BRACKET_ORDER with the comment "Zerodha discontinued BO; empty = not supported (PR3)" (L162). A product the broker stops accepting while the YAML still holds a non-empty code would be returned by `resolve` and rejected by the broker when the order is sent.
