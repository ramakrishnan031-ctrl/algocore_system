## 3. The closure `_make_sr_fetch_fn` and the `historical` bucket (C1, C3, I3, I4)

P06-S016. FACT (`main.py` L421 to L438): `_make_sr_fetch_fn(market_kite, rate_limiter)` returns the inner function `_fetch(instrument_token, from_date, to_date, interval)` (L428, L438). `_fetch` returns `[]` at once when `market_kite is None` (L429 to L430), before any limiter call; otherwise it calls `rate_limiter.acquire("historical")` (L431) and then returns `market_kite.historical_data(instrument_token=instrument_token, from_date=from_date, to_date=to_date, interval=interval)` (L432 to L437). It passes the four values through unchanged and does not pass `continuous` or `oi`, so the library sends both as `0` (part P02, P02-S063). It has no `try`, no retry, no logging, no `penalize`, no translation of exceptions, no check of its arguments and no check of the result; it returns the library's list as it is. HISTORICAL (docstring L422 to L426): "a rate-limited historical-fetch closure injected into the pure sr_detector package. Routes every call through rate_limiter.acquire("historical") (spec C pacing); fails safe if no kite handle (the OhlcFetcher records a fetch_failed row, never raises)."

P06-S017. FACT (`main.py` L2348; `broker/rate_limiter.py` L148 to L162; `config/broker_limits.yaml` L17 to L19; `core/config_loader.py` L2176 to L2179, L2245 to L2249): the trading process builds one limiter, `RateLimiter(app_config.broker_limits, shutdown_event=_shutdown_event)`, without `max_wait_sec`, so the default `max_wait_sec: float = 30.0` applies (L152, L155). Its `historical` bucket is built from `limits.historical.burst` and `limits.historical.rate_per_sec` (L160). Committed values: `historical: burst: 2`, `rate_per_sec: 2` (committed value; effective value UNKNOWN: which configuration was in force on the legacy machine is not established, A02 RECONCILED TOPIC RECORD L179; no overlay or effective setting was read). `TokenBucketConfig` declares `burst: int` and `rate_per_sec: int` with no validator (also A04 evidence, P05-S048).

P06-S018. FACT (`broker/rate_limiter.py` L76 to L99, L177 to L246): `acquire("historical")` with the default `n=1`: (a) if `n` exceeds the bucket's capacity it raises `BrokerRateLimitError` at once (L190 to L199; not the case at the committed capacity 2); (b) it loops: `bucket.try_acquire(1)` returns False while the bucket is frozen, otherwise refills the bucket from elapsed monotonic time and takes one token if one is there (L90 to L99), and `acquire` then returns (L205 to L211); (c) when 30 s have passed since the call began without a token, it raises `BrokerRateLimitError("Rate limit timeout after 30.0s waiting for 1 token(s) in category 'historical'", ...)` (L201 to L202, L213 to L223); (d) otherwise it sleeps for the estimated time to the next token, capped at the remaining time and at 0.1 s and at least 0.001 s (L225 to L233); with a shutdown event, as here, it waits on the event and raises `RateLimitAbortedError` if the event is set during that wait (L236 to L244).

P06-S019. INTERPRETATION (code reading of `broker/rate_limiter.py` L205 to L244): the shutdown event is looked at only while a caller waits. When a token is available, `acquire` returns at once even if the event is already set, so a fetch that starts during shutdown still goes to the broker when the bucket holds a token; a caller that is waiting ends with `RateLimitAbortedError` within about 0.1 s of the event being set. At the committed rate a lone waiter gets its next token within about 0.5 s (arithmetic: one token at 2 per second). The limiter keeps no queue: several waiting threads each poll, and which of them gets the next token is not defined by the limiter.

P06-S020. FACT (`core/exceptions.py` L30, L158, L243, L284): `BrokerRateLimitError` subclasses `BrokerError`, which subclasses `TradingSystemError`, which subclasses `Exception`; `RateLimitAbortedError` subclasses `TradingSystemError`. INTERPRETATION (Python semantics): both are caught by an `except Exception` clause.

P06-S022.
